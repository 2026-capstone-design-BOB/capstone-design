계획이 지정한 범위 그대로다 — **보안 5층** · **`_dead_end` 계열** ·
**`_NOTHING_HAPPENED_MSG`(그물)** · **BL-12 / 19 / 26 / 35**.

네 가지는 사실 **한 가족**이다. 이 저장소가 반복해서 데인 결함은 전부 같은 모양이다:

> ### 🔑 «확인하지 않고 됐다고 말하는 것»

그래서 판정 기준을 하나로 뒀다 — **«사용자가 원한 일이 실제로 일어났는지를
코드가 확인하는가, 아니면 짐작하는가»**. 확인하지 않는 자리가 «비어 있는 곳»이다.
(이 기준은 내가 만든 게 아니라 [`core/tool_result.py`](../../core/tool_result.py) 머리말에
이미 적혀 있던 것이다 — *"판정 기준은 «예외가 났는가»가 아니라 «사용자가 원한 일이
일어났는가»다."*)

**⚠️ 여기 적은 것은 전부 코드를 읽어 확인한 것이다.** 실기로 재현해 본 것은 없다 —
재현은 사람이 필요하고, 그건 9/20 3차 리허설의 몫이다. 재현 방법은 각 항목에 적었다.

## 3. 🔴 가장 큰 구멍은 **캐시 실행 경로**에 있다

세 개가 한 함수에서 나왔다. [`core/command_cache.py`](../../core/command_cache.py) `execute_sync`:

```python
for call in entry.tool_calls:
    name = call.get("name", "")
    if name not in tools_map:
        continue                                  # ← G-04
    try:
        results.append(str(tools_map[name].invoke(args)))
    except Exception as e:
        print(f"[CommandCache] 동기 실행 오류 ({name}): {e}")   # ← G-02
        results.append(entry.response_template)                # ← G-01
return "\n".join(results) if results else entry.response_template
```

### G-01 — 🚨 **도구가 실패하면 «성공했다»고 말한다**

`entry.response_template`이 무엇인지가 핵심이다. 시드를 보면:

```python
("메모장 열어줘", [{"name": "open_app", …}], "✓ 메모장을 실행했습니다."),
```

**템플릿이 곧 성공 문구다.** 그래서 `open_app`이 예외를 던지면 사용자는
**«✓ 메모장을 실행했습니다»를 듣는다.** 메모장은 안 떴다.

> 🔑 이건 BL-26(«뻥카»)과 **같은 결함이 아니라 그보다 나쁜 판본**이다.
> BL-26은 도구가 «확인을 안 해서» 성공이라고 **믿은** 것이고,
> 여기는 도구가 **실패를 알렸는데도** 코드가 성공 문구로 **바꿔친다.**
>
> ⚠️ 그리고 이 자리는 **`✓`로 시작한다.** [`tool_result.py`](../../core/tool_result.py)의
> 계약상 «성공»이라 [BL-29](../BACKLOG.md)가 만든 판정기 셋(A·B·C)이 **전부 통과시킨다.**
> 판정 계약을 한 자리로 모은 것은 옳았지만, **계약을 우회해 문자열을 지어내는 자리**가
> 남아 있으면 계약은 거기서 끝난다.

- **마지막 줄(`if results else`)도 같은 문제다.** 도구 이름이 `tools_map`에 없어
  `continue`로 전부 빠지면 `results`가 비고 → 역시 **성공 템플릿**이 나간다.
  도구 이름을 바꾸거나 지우면 캐시는 **조용히 «성공»을 계속 말한다.**
- **왜 이렇게 됐는지는 짐작이 간다.** 템플릿은 원래 «LLM 없이도 같은 말투로 답하기»
  용도였다. 그게 **실패 자리에 재사용**된 것이다.

**재현**: `execute_sync`에 예외를 던지는 가짜 도구를 물리면 서버 없이 갈린다.
사람이 필요 없다.

### G-02 — 그 실패가 **로그에 없다**

`print`다. `logs/pluiz.log`는 `core/logger.py`를 거친 것만 받으므로
**캐시 도구 실패는 로그에 한 줄도 안 남는다.** 남는 것은 그 직전의
`[캐시 실행] 패턴=… | 도구=[…]` 뿐이고, 그 줄은 **돌렸다는 사실만** 말한다.

> 🚨 [**BL-39**](../BACKLOG.md)가 정확히 이 모양이었다 — *"ERROR 0건인데 턴 6개가 사라졌다."*
> 그때는 `_dead_end`를 만들어 메웠는데, **캐시 경로는 그 수선의 범위 밖이었다.**
> 지금 상태에서 시연 중 캐시 도구가 실패하면, **로그만 봐서는 영영 모른다**
> (턴 완료 줄에는 `LLM 0회(캐시)` 성공으로 찍힌다).

`fast_path.py:154`의 `except`도 같다 — `print(f"[fast_path] 캐시 오류(무시): …")`.
라우터 오류(`:160`)도 같다.

🚨 **같은 결함이 바로 위 `execute()`(비동기, `:984~1002`)에도 그대로 있다.**
그래프는 sync 경로만 쓰지만(절대규칙 1), **고칠 때 두 곳을 같이 봐야 한다** —
한쪽만 고치면 이 저장소가 여러 번 데인 «같은 사실이 두 곳에 있어 한쪽만 갱신됐다»가 된다.

### G-03 — 캐시 히트 턴은 **그물 넷이 전부 비켜간다**

`output_guard`의 방어 넷을 캐시 히트 기준으로 세어 보면:

| 그물 | 캐시 히트 턴에서 | 왜 |
|---|---|---|
| `watch_notice_to_deliver` | 해당 없음 | 감시 도구는 캐시 대상이 아니다 |
| `detect_watch_lie` | ❌ **명시적으로 제외** | `decision == "fast_hit"`이면 건너뛴다(주석에 근거가 있다) |
| `verify_output` ① 빈 응답 | ❌ 무력 | 응답이 비지 않는다(템플릿이 채운다) |
| `verify_output` ② 도구 오류 | ❌ **구조적으로 무력** | 캐시는 도구를 **그래프 밖에서** 돌려 `ToolMessage`가 없다(절대규칙 2). `tool_errors`가 **항상 빈 리스트**다 |

**즉 캐시 경로는 정직성 검사를 하나도 받지 않는다.** 이건 누가 빠뜨린 게 아니라
**절대규칙 2(캐시 결과도 `messages`에 누적한다)의 그림자**다 — AIMessage 하나만
남기기로 한 설계가 «검사할 재료»도 같이 없앤다.

> ⚠️ **그래서 G-01을 «그물이 잡아 주겠지»로 넘길 수 없다.** 잡을 그물이 없다.
> 캐시 경로에서 유일하게 진실을 아는 자리는 **`execute_sync` 자신**이다.

### G-04 — ⬜ 실행 쪽에는 **도구 게이트가 없다**

`LEARNABLE_TOOLS`(15개)는 **쓰기**에만 걸려 있다 — `learn()`과
`portable.merge_cache_entries()`. 실행은 `name not in tools_map`만 본다 = **도구 41개 전부**.

| 경로 | 게이트 | 결과 |
|---|---|---|
| 학습(`learn`) | ✅ `_is_learnable` | 위험 도구 안 들어온다 |
| 가져오기(`/import`) | ✅ **같은 함수를 쓴다** | ✅ 확인함 — 여기는 안 비었다 |
| **파일 직접 수정** | ❌ 없음 | `cache/command_cache.json`에 `delete_file`을 적으면 **승인 없이 실행된다** |

`fast_path`는 `hitl` 노드를 지나지 않는다(`START → input_guard → fast_path →(hit)→
output_guard → END`). 그러므로 캐시에 위험 도구가 **들어가기만 하면** 3층은 없는 것과 같다.

**⬜로 둔 이유**: 로컬 파일을 고칠 수 있는 사람은 [`core/auth.py`](../../core/auth.py)가
선언한 **위협모델 밖**이다(*"그 수준의 공격자는 이미 PC에서 코드를 실행하고 있다"*).
다만 **방어가 쓰기 쪽에만 있다는 사실**은 적어 둘 값이 있다 — 게이트를 늘릴 때
«어느 쪽에 다느냐»를 정하는 근거가 된다.

## 4. 🔴 3층(승인)이 «삭제»라는 **이름**에 걸려 있다 — 일어나는 **일**이 아니라

```python
DANGEROUS_TOOLS = {"delete_file", "delete_folder", "click_ui_element"}
```

`delete_file`은 **휴지통으로 간다**(되돌릴 수 있다). 그런데 승인을 안 받는 도구 중에
**되돌릴 수 없는 것이 둘** 있다.

### G-05 — 🚨 `create_file`이 기존 파일을 **말없이 덮어쓴다**

```python
with open(path, "w", encoding="utf-8") as f:   # ← 있으면 통째로 날아간다
    f.write(content)
return f"✓ '{name}' 파일을 {location}에 생성했습니다."
```

- **승인이 없다**(`DANGEROUS_TOOLS` 밖).
- **휴지통이 없다.** 삭제보다 **되돌리기 어렵다.**
- **문구가 틀렸다.** 덮어썼는데 *"생성했습니다"* 라고 한다 — 사용자는 옛 내용이
  사라진 걸 **응답만 봐서는 알 수 없다.**

> 🔑 *"메모 저장해줘"* 를 두 번 하면 첫 번째 내용이 사라진다. 이건 공격이 아니라
> **평범한 사용**이다. 3층의 기준이 «삭제라는 이름»이라 여기에 안 걸린다.

⚠️ **판단이 필요한 자리다.** 존재하면 무조건 승인을 받게 하면 *"메모 저장해줘"*
마다 승인이 뜬다. 값이 있는 쪽은 **«내용이 있는 파일을 덮어쓸 때만»** 일 것이다 —
빈 파일 덮어쓰기는 잃는 게 없다. **ADR 감이다**(시연 뒤).

### G-06 — ⬜ `save_excel`도 같다

`wb.save(path)` — 같은 덮어쓰기. 덧붙여 **`_is_secret_path` 검사가 없다**
(`create_file`에는 있다). `.xlsx` 비밀 파일은 드물어 ⬜로 둔다.

### G-07 — 🚨 `close_app`이 **종료를 확인하지 않는다** (대본 2장면)

```python
proc.terminate()
killed.append(proc.info["name"])
…
if killed:
    return f"✓ {name}{eul_reul} 종료했습니다."
```

`terminate()`는 **요청이지 결과가 아니다.** 프로세스가 안 죽어도 `killed`에 들어가고
«종료했습니다»가 나간다. 확인(`proc.wait(timeout=…)`)이 없다.

> 🚨 **`open_app`은 이걸 이미 고쳤다.** BL-26이 `_await_window()` + `_launched_or_honest()`를
> 만들어 *"실행을 시도했지만 창이 나타나지 않았습니다"* 를 말하게 했다.
> **그 대칭인 `_await_gone()`은 만들어지지 않았다.** 여는 쪽만 정직해졌다.

**그리고 이건 데이터 손실 경로이기도 하다.** `terminate()`는 Windows에서
`TerminateProcess`라 **저장 대화상자를 띄우지 않는다** — 저장 안 한 메모장 내용은
승인 한 번 없이 사라진다. 대본 **2장면이 «그거 꺼줘»** 다.

**재현**: 메모장에 글자를 치고 저장하지 않은 채 *"메모장 꺼줘"*.
3차 리허설에서 **한 번만** 보면 갈린다(실기 목록에 넣을 값이 있다).

## 5. 🟡 BL-12·BL-26 계열이 **아직 남아 있는 자리**

고친 것은 `type_text`(포커스)와 `open_app`(창 확인)이다. **같은 결함이 같은 모양으로
남아 있는 곳**이 넷 더 있다.

### G-08 — 유령 창 검사가 **두 곳에 안 붙었다**

BL-26 원인③의 `is_window_cloaked()`는 `_is_real_window`(`:108`)와
`find_hwnd_for_app`에만 붙었다. 그런데:

```python
# maximize_window (:625)  ·  minimize_window (:683)
if not ctypes.windll.user32.IsWindowVisible(h):
    return True                      # ← cloaked 창이 여기서 True를 준다
…
ctypes.windll.user32.ShowWindow(h, SW_MAXIMIZE)
return f"✓ {app} 창을 최대화했습니다."      # ← ShowWindow 반환값도 안 본다
```

**BL-26이 «세는 기준이 틀리면 검증을 넣어도 소용없다»고 적어 둔 그 자리**가
두 함수에 그대로 남아 있다. 정지된 UWP 앱(설정·계산기)에 «최대화해줘»를 하면
아무 일도 없이 «✓ 최대화했습니다»가 나갈 수 있다.

⚠️ 이 둘은 **`LEARNABLE_TOOLS`에 있다** — 즉 캐시가 학습해 **오프라인에서도** 같은
거짓말을 한다.

### G-09 — `press_key`에 포커스 확인이 **없다**

BL-12은 `type_text`에 `_ensure_target_focused()`를 넣어 *"확인이 안 되면 입력하지
않는다"* 로 고쳤다. **`press_key`는 그 수선을 못 받았다.**

```python
pyautogui.hotkey(*parts)          # 또는 press()
return f"✓ '{key}' 키 입력 완료"   # 어느 창에 갔는지도 안 말한다
```

- `target` 인자 자체가 없다. **어디로 가는지 모르고 누른다.**
- `type_text`는 최소한 «어느 창에 넣었는지»를 밝히는데 여기는 그것도 없다.
- `alt+f4`·`ctrl+s`·`ctrl+w`가 **엉뚱한 창에서** 눌릴 수 있고, 되돌릴 수 없다.

> 🔑 BL-12의 실기 사고가 정확히 이것이었다 — 글자가 **Pluiz 오버레이 입력창**에 들어갔다.
> 키도 같은 길로 간다.

### G-10 — ⬜ `type_text(target="")`는 **아무도 검증하지 않는다**

`build_visual_question()`은 `target`이 비면 `None`을 돌려준다 — **일부러 그렇게 했다**
(활성창을 찍으면 순환이라 거짓 성공에 증거를 붙여 준다). 판단은 옳다.
다만 **그 경우 검증이 0이 된다**는 사실은 목록에 있어야 한다.
👉 값이 있는 쪽은 «target 없이 부르지 않게 하는 것»(프롬프트·도구 설명)이지 검증이 아니다.

### G-11 — 밝기·볼륨이 **실패를 안 본다**

```python
def _set_brightness(level):
    try:    … wmi …
    except Exception:
        subprocess.run(["powershell", …], capture_output=True)   # ← returncode를 안 본다
```

`brightness_up`은 그 뒤 **무조건** `✓ 밝기: 40% → 50%` 를 말한다.
`_set_volume_level`도 마찬가지로 **항상 `True`** 를 돌려준다(keybd_event 폴백은
성공 여부를 알 수 없다). `set_volume`은 되읽기조차 없다.

> ⚠️ **읽을 수 있는 PC에서는 되읽기가 싸다.** `volume_up`은 **실행 전** 값만 읽고
> **실행 후** 값은 안 읽는다 — 그래서 보고하는 `→ 50%`는 **의도이지 결과가 아니다.**
> [BL-47](../BACKLOG.md)이 `wmi`를 깔아 «읽을 수 있는 PC»로 만들어 놨으므로,
> 여기는 **한 줄 되읽기로 정직해질 수 있는 몇 안 되는 자리**다.

### G-17 — 브라우저 열기 폴백이 **실패해도 조용하다**

```python
try:    os.startfile(url)              # ← 이건 실패하면 예외를 낸다(정직)
except Exception:
    subprocess.Popen(["start", url], shell=True)   # ← 실패해도 예외가 안 난다
    return url
```

`Popen`은 셸을 띄우는 데만 성공하면 돌아온다. 브라우저가 안 열려도
`open_url`은 `✓ {url} 열었습니다.` 를 말한다. `web_search`·`youtube_search`도 같은 함수를 쓴다.

## 6. 🟡 그물 자신에 난 구멍 둘

### G-12 — `_SUCCESS_LIKE_RE`가 **해요체만** 본다

```python
_SUCCESS_LIKE_RE = re.compile(
    r'(?<!못)(?:했어요|켰어요|열었어요|닫았어요|실행했어요|설정했어요|만들었어요|저장했어요|됐어요|완료했어요|완료)[!.]?\s*$')
```

`verify_output`의 **둘째 그물**(도구는 실패했는데 AI가 성공처럼 답함)은 이 정규식이
걸려야 발동한다. 그런데 **«했습니다»·«실행했습니다»·«열었습니다»가 목록에 없다.**

🚨 **하필 도구 문구가 전부 합쇼체다** — `✓ 메모장을 실행했습니다.` `✓ 볼륨을 올렸습니다.`
LLM은 도구 결과를 보고 답을 쓰므로 **말투를 따라갈 이유가 충분하다.**
그리고 시스템 프롬프트에는 *"응답은 항상 한국어로 해요"* 뿐 — **말투 지정이 없다.**

> 즉 «도구가 ✗를 냈는데 LLM이 성공처럼 답한 턴»이 **말투 하나로 그물을 빠져나갈 수 있다.**
> 확률을 못 박을 프롬프트조차 없으니 이건 «확률이 낮다»가 아니라 **«모른다»** 다.

**재현**: 서버 없이 된다 — `verify_output`에 「도구 ✗ + "메모장을 열었습니다."」를
넣어 `None`이 나오는지 보면 끝이다. 🔑 **2-2(응답 품질·말투 통일)와 같은 자리를 건드린다** —
말투를 손보면 이 그물의 적중 범위가 **같이 움직인다.** 따로 고치면 안 된다.

### G-13 · G-14 — 4층 마스킹이 **한 자리에만** 있고, 예외가 **그대로 낭독**된다

`mask_sensitive_output()`의 호출 지점은 **전 저장소에 한 곳**이다
(`graph_agent.py:694`, 정상 완료 경로). 아래는 **거치지 않는다**:

| 나가는 말 | 마스킹 | 무엇이 실릴 수 있나 |
|---|---|---|
| `_dead_end(kind="error")` | ❌ | **예외 원문**(`f"… 오류가 발생했어요: {exc}"`) |
| 승인 질문(`interrupt`) | ❌ | 파일 **전체 경로** |
| 제안 수락 실행 결과 | ❌ | 도구 출력 그대로 |
| 감시 알림(`_broadcast`) | ❌ | 화면에서 읽은 텍스트 |

- **ARCHITECTURE의 «4층 — 출력 마스킹»은 실제로는 «정상 응답 마스킹»이다.**
  문서와 코드가 어긋난 건 아니고(문서는 «응답»이라고만 쓴다), **범위가 좁다는 사실이
  어디에도 안 적혀 있다.**
- **G-14는 시연에서 보일 수 있다.** 예외 문자열에는 길이 상한이 없고, TTS로도
  **그대로 간다**(`main.py:366`에 자르는 곳이 없다). Gemini 400 에러 한 번이면
  **영어 수백 자가 낭독된다.**
- ✅ **키 유출은 관측된 적 없다** — `logs/` 전체를 `AIza…` 로 훑어 **0건**이다.
  가능성만 남아 있고 실측 근거는 없다. 과장하지 않는다.
