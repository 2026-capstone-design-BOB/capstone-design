## 0. 왜 이걸 먼저 만드나

2026-09-17에 사용자가 Windows 음성 액세스를 써 보고 말했다 —
*"확실히 느껴졌어, 우리 프로젝트가 부족하다는 것을. 좀 더 **디테일적인 부분**도 그렇고 **기능적 부분**도 그렇고."*

**그 «디테일»의 정체를 숫자로 찍는 것이 이 문서다.** 느낌으로 두면 개편안이 취향이 된다.

### 🔑 **«디테일이 부족하다»의 정체 — 텍스트 영역이 통째로 없다**

**9~13번이 음성 액세스 명령의 60%**(명령부 851줄 중 517줄)이고, **우리는 그 칸이 0이다.**

> *"메모장 열어줘"* 는 되는데 *"이 문장 굵게 해줘"* · *"방금 쓴 단어 지워"* ·
> *"세 번째 줄로 가"* 는 **도구가 없어서 안 된다.**
> 🚨 **«모델이 못 알아들어서»가 아니다. 부를 게 없다.**

그리고 **5·7번이 얇은 것**이 두 번째 구멍이다 — 클릭 하나, 키 누르기 하나뿐이라
**스크롤·드래그·토글 같은 평범한 조작이 통째로 빠져 있다.**

|---|---|---|

| 🎯 | **질문에 답하기** — 시간 · 배터리 · 실행 중인 앱 · 날씨 | 명령 실행 도구라 «답»이라는 개념이 없다 |
| 🎯 | **웹에서 읽어 오기** — `fetch_web_info` `crawl_page` | 검색은 열어 줄 뿐, **읽어 주지 않는다** |
| 🎯 | **파일 생성·삭제 · Excel 쓰기** | 찾기만 있다 |
| 🎯 | **화면을 «이해»한다** — `describe_screen` · 포인팅 · 감시 | 오버레이는 **사람이 번호를 읽는** 방식이다 |

> 🔑 **두 목록이 거의 안 겹친다.** 이게 «다른 물건이다»의 실제 근거다 —
> 저쪽은 **입력 장치**(컨트롤·텍스트), 우리는 **대리인**(의도·응답·안전).

## 4. 🚨 그런데 빈 칸을 **도구로 메우면 안 되는 이유** — 토큰 절벽

**«텍스트 편집 명령 40개를 만들자»가 답이 아니다.** 우리 구조가 그걸 못 견딘다.

| 사실 | 근거 |
|---|---|
| 매 턴 **시스템 프롬프트 + 도구 41개 정의 + 히스토리**가 통째로 올라간다 | [캐시 절감액](2026-09_캐시_절감액.md) |
| *"메모장 열어줘"* 한 마디에 **13,000 토큰** | 같은 문서 |
| **입력이 비용의 90.7%** | 같은 문서 |
| 🚨 **입력이 커지자 출력이 0이 된 적이 있다** | [BL-57](../BACKLOG.md) — 도구 41개만 바인딩하면 정상, **시스템 프롬프트까지 얹자 `out=0`**. `thinking_budget=0`으로 막았다 |

> **도구를 100개로 늘리면** 모든 턴이 비싸지고 느려지고, **선택 정확도가 떨어지고**,
> 저 절벽으로 다시 간다. 🔑 **그래서 선결 과제는 «도구 추가»가 아니라
> «도구를 어떻게 고르느냐»** — 계층 · 라우팅 · 동적 바인딩이다.

### 그리고 실패면이 **곱으로** 커진다

이 저장소가 고친 결함의 큰 줄기가 **«확인하지 않고 됐다고 말하는 것»**
(BL-12·19·21·23·26·35·58)이다. **오늘 본 [BL-58](../BACKLOG.md)이 정확히 그 모양**이다 —
도구(브라우저 열기)는 성공했는데 **보고가 거짓**이었다.

> ⚠️ 그리고 [분석 §6-4](2026-09_음성액세스_대조표.md)의 뒷면이 이것이다 —
> 저쪽은 **안전한 동작만 주니** 승인이 필요 없다.
> **우리가 표면을 넓히는 순간 안전망을 더 크게 쳐야 한다.**

## 5. 🔍 그래서 **진짜 질문은 «어떤 표면을 쥐느냐»다**

음성 액세스가 편집 명령 300개를 **손으로 만든 게 아니다.**
**UI Automation + 키보드**라는 **범용 표면 둘**을 쥐고 그 위에 문법을 얹은 것이다.

### 🚨 우리가 화면을 짚는 방식 — 실측으로 확인했다

```
click_ui_element → locate_ui_element (Vision · 픽셀 추정) → pyautogui 좌표 클릭
```

`requirements.txt`에 **`pywinauto`도 `uiautomation`도 없다.** `win32gui`는 **창 열거에만** 쓴다.

| | 음성 액세스 | Pluiz |
|---|---|---|
| 컨트롤을 아는 방법 | **UI Automation 트리** — 이름·타입·상태를 **정확히** 안다 | **화면 픽셀을 보고 추정**한다 |
| 그래서 | *"동물 친구 클릭"* 이 그냥 된다 | *"추정한 위치예요"* 라벨이 **필요했다** |
| 비용 | 사실상 0 | 화면 1장 = 약 1,000~1,800 토큰 |
| 텍스트 편집 | `TextPattern`으로 커서·선택을 안다 | **알 방법이 없다** → §2의 9~13번이 빈 이유 |

> 🔑 **우리 포인팅의 부정확성은 «모델 문제»가 아니라 «경로 문제»일 수 있다.**
> 그리고 이건 [동향점검](2026-09_동향점검.md)에서 **Anthropic Computer Use가 스스로 밝힌 한계**와
> 같은 모양이다 — *좌표 스케일 불일치 · 축소로 인한 작은 글자 손실* → **키보드 단축키 권장.**
>
> ⚠️ **아직 «가설»이다.** UIA를 실제로 돌려 정확도·속도를 재 봐야 한다 → **W-1**.
