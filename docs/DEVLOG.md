## 2026-09-08 — 📄 **교수님 미팅 자료 — `docs/meetings/` 신설**

> **📌 다음 진입점은 그대로 두 개다.** ① 「플루이즈」 2분 30초 녹음(⚠️ 사용자) ·
> ② **BL-20 — 안전 호출 실행**(사용자가 접근 방식을 확정했다 → [TASKS](TASKS.md) ②)

**목표**: 방학 이후 진행 상황·현재 되는 수준·남은 것·앞으로의 계획을, **교수님이 알아야 할 것**과
**이쪽에서 여쭐 것**이 같이 드러나도록 한 장에 모은다.

**한 일**: `docs/meetings/`를 신설하고 같은 내용을 두 형식으로 냈다 —
저장소 기록본(`.md`)과 미팅에서 띄워 볼 한 장(`.html`, 아티팩트로도 배포).
`docs/README.md`의 문서 목록·라우팅 표에 `meetings/` 한 줄씩 추가했다.

### 새로 쓴 것은 없다 — 골라내 재구성했다

재료는 전부 저장소에 있었다: `ROADMAP`(계획 대비 실제) · `README 상태표`(숫자의 유일 출처) ·
`BACKLOG`(한계) · `planning/제품_방향.md` §3(⏸️ 열린 결정 3건) · **2026-09-07 DEVLOG**
(mock 808개가 초록인데 라이브에서만 결함 셋이 드러난 사례). 흩어져 있었을 뿐이다.

**미팅 질문 6개**는 열린 결정 3건에 세 개를 더해 만들었다 —
④ computer use 차별화 서사가 심사에서 통하는가 ⑤ RAG를 채울 것인가 *(구조상 retrieval이지
RAG가 아니라는 점을 같이 적었다)* ⑥ 팀 브랜치 7,606줄 처리. 각 항목에 **현재 기울어 있는 답**을
같이 적어, 교수님이 **판단만** 하시면 되게 했다.

### 정한 것 둘

**① 동결 스냅샷이다.** 날짜가 붙어 있고 **이후 갱신하지 않는다.** 그래야 「한 사실은 한 문서에만」과
충돌하지 않는다 — 살아 있는 사실은 `README 상태표`·`TASKS`·`ROADMAP`이 계속 책임진다.
같은 내용이 `.md`와 `.html` 두 벌 있는 것도 **동결이라 어긋날 여지가 없기 때문**에 허용한다.

**② ✅/⚙️/❌를 표의 한 칸으로 만들었다.** 이 프로젝트의 규율(*"코드가 들어갔다 ≠ 동작한다"*)이
그대로 보이게. 웨이크워드와 BL-13 설정 화면은 ⚙️(코드만)로 정직하게 적었다 —
**추측으로 ✅를 붙이지 않는다.**

### 검증

- 숫자는 전부 `docs/README.md` 상태표와 대조(도구 39 · mock 31파일 808개 ·
  CI 30파일 776개 · 승인 필수 3 · 5층 보안). 미푸시 커밋 **60개**는
  `git rev-list --count origin/main..HEAD`로 실측.
- HTML — 태그 균형·안 닫힌 태그 0, 토큰 밖 하드코딩 색상 0(라이트/다크 전부 토큰 경유),
  아티팩트 skeleton과 겹치는 태그 없음.
- 코드 변경 없음 → 테스트 스위트는 돌리지 않았다.

## 2026-09-07 (계속 6) — 🎙️ **웨이크워드 설정 UI** (BL-13)

> **📌 다음은 웨이크워드 녹음 2분 30초 — ⚠️ 사용자만 할 수 있다.**
> 그게 9월의 **마지막 항목**이고, 녹음만 있으면 학습 → 런타임 교체까지 이어진다.

Phase 2가 닫혔고 9월에 남은 건 웨이크워드뿐인데, 그 트랙의 시작점(녹음)은
사용자 몫이다. **기다리는 동안 할 수 있는 것**을 했다.

`POST /api/wakeword`는 **2026-09-02부터 열려 있었다.** 입력란이 없어서 사용자가
`.env`를 직접 열어야 했을 뿐이다. ⚙️ 설정 화면에 호출어 입력란과 사용 토글을 붙였다.

### 정한 것 셋

**① API 키 저장과 분리했다.** 같은 버튼에 묶으면 호출어만 바꾸려는 사람이 API 키를
다시 넣어야 하고, `POST /api/config`가 **에이전트를 재초기화**하며 WebSocket도 끊는다.
호출어 하나 바꾸려고 치를 값이 아니다. 상태줄도 따로 뒀다 — 한쪽 메시지가 다른 쪽을
덮으면 무엇이 저장됐는지 알 수 없다.

**② "10초 안에 반영돼요"를 저장 응답에 넣었다.** 웨이크워드는 Electron이 띄운
**별도 프로세스**라 서버가 직접 못 바꾸고, 그쪽이 `.env`를 주기적으로 다시 읽는다.
이걸 말하지 않으면 사용자는 저장 직후 불러 보고 **고장이라고 생각한다.** 껐을 때는
대체 수단(Alt+Space)을 알려 준다 — 웨이크워드가 없으면 부를 방법이 없다고 오해한다.

**③ 플레이스홀더에 `wake_words_default`를 쓴다.** 비워 두면 **실제로** 그 값이
쓰이므로, 빈 칸이 "아무 말에도 안 뜬다"로 읽히면 안 된다.

### 회귀 — 프런트와 서버는 다른 파일이다

`tests/test_wakeword_ui.py` **25건 신설.** 어긋나도 아무도 안 알려 주는 자리라
소스를 대조한다:

- **필드 이름**이 `WakeWordRequest`와 같은가 — 다르면 **422**고 프런트는 조용히 실패한다.
  서버 모델에서 필드를 **읽어 와** 대조하므로, 서버가 필드를 바꾸면 여기서 걸린다.
- **`${API}` 템플릿**으로 부르는가 — `window.fetch` 래퍼가 그 접두사에만 토큰을
  붙인다(BL-14). 절대 URL을 쓰면 **그 기능만 401**이 난다.
- **키 저장과 얽히지 않는가** — `api-key-input`·`/api/config`·`ws.close()`를 안 쓰는지.
- **고지 문구**가 살아 있는가 — "10초", "Alt+Space".

> BL-16(`/voice`의 `Form(...)` 누락)이 **평범한 경우엔 멀쩡해 보이다가** 맥락이
> 필요한 순간에만 무너졌던 게 이 계열이다. 프런트-서버 계약은 **양쪽을 같이 읽어야**
> 검증된다.

### 검증

- `node --check`로 렌더러 스크립트 문법 확인, 설정 오버레이 `<div>` 짝 18/18.
- **전체 mock 31파일 808개 통과, 실패 0.**
- ⚠️ **실기 미검증** — 마우스로 눌러 본 적은 없다. `launch.bat` → ⚙️ → 호출어를
  바꾸고 저장 → 10초 뒤 그 말로 불러 보면 된다.

## 2026-09-07 (계속 5) — 🏁 **Phase 2 종료 — 다섯 기능이 전부 실기를 통과했다**

> **📌 다음은 [BL-13](BACKLOG.md) 웨이크워드 설정 UI.** 9월에 남은 건 웨이크워드뿐이고,
> 전용 모델 학습은 **사용자 녹음 2분 30초**에 걸려 있다.

감시의 마지막 두 경우를 사용자가 확인했다. 둘 다 *"조용히 끝나지 않는가"* 를 보는 항목이다.

```
15:20:51 감시 시작 | 창=메모장 | 최대 1분 · Vision 3회
15:21:01 감시 종료 | 사유=capture_failed | Vision 0회   ← 최소화하자 멈추고 알렸다
15:21:21 감시 시작 | 창=계산기
15:22:21 감시 종료 | 사유=timeout | Vision 0회          ← 상한에서 "못 봤어요"
```

- **최소화 함정** — *"창을 볼 수 없어서 감시를 멈췄어요"*. **창이 깜빡이지 않았다** —
  감시가 대상 창을 붙잡지 않는다는 뜻이다.
- **조용한 종료 없음** — 1분 상한에서 *"못 봤어요 (화면 확인 0회)"*.
  **`Vision 0회`가 요점이다**: 변화가 없으면 화면이 한 장도 밖으로 나가지 않는다.
  픽셀 프리필터가 전송량 방어라고 적어 둔 것이 라이브에서 확인됐다.

### Phase 2가 닫혔다 — 이번엔 "코드가 들어갔다"가 아니다

| 기능 | 실기 |
|---|---|
| `describe_screen` | 2026-09-02 |
| `visual_verify` | 2026-09-04 (라이브 회귀 V-01~V-04) |
| `find_ui_element` | 2026-09-03 |
| `click_ui_element` | **2026-09-07** — 승인 후 실제로 눌렸고 없는 요소는 거절 |
| `watch_screen` | **2026-09-07** — 알림 도달 · `capture_failed` · `timeout` |

2026-09-04에 *"로드맵이 닫혔다는 말은 코드가 들어갔다는 뜻이지 동작을 확인했다는
뜻이 아니다"* 라고 써 뒀다. **오늘 그 문장을 지웠다.**

가는 길에 결함 셋을 만났고 다 고쳤다 — **BL-22**(프리필터가 타이핑을 못 봤다) ·
**BL-21 ②**(실패한 계획이 캐시에 굳었다) · **BL-21 ①**(건너뛴 단계를 완료로 셌다).
셋 다 mock이 초록인 채로 살아 있던 결함이고, **전부 라이브에서만 드러났다.**

### 곁들여 관측된 것

`"메모장 열고 글자가 쓰여질 때까지 감시해 줘"` 가 `도구=['open_app', 'watch_screen']`,
`계획 0단계`로 돌았다. 감시 요청은 `_is_plannable`이 **일부러 제외**하는데
(계획 턴은 `detect_watch_lie`의 "이번 턴 도구 0개" 조건을 깨뜨린다 — M3 §6-3),
그런데도 **한 턴에 두 도구를 다 불러 정상 처리됐다.** 게이트가 좁아서 놓쳐도
착지점이 오늘의 정상 경로라는 ADR §7-6의 주장이 실제로 그랬다.
같은 줄에 `[BL-21] 복합 명령은 학습하지 않는다`도 찍혔다 — 오후에 넣은 그물이 돈다.

### 남은 것

9월 항목 중 **웨이크워드만** 남았다. 전용 모델은 사용자 녹음 2분 30초가 시작점이고,
그전에 할 수 있는 건 **BL-13(설정 UI)** 이다 — API는 이미 열려 있다.

> **📌 다음은 [TASKS.md](TASKS.md) ①의 「화면 감시」 3·4번**(최소화 함정 · 상한 알림).
> 그 둘이면 **Phase 2가 닫힌다.**

BL-21을 고친 직후 사용자가 바로 돌렸다. **세 경우가 다 나왔고 다 맞았다.**

```
15:10:45 [Plan] 메모장 최소화 / 계산기 닫기
15:10:46 턴 완료 | 도구=['minimize_window'] | 계획 2/2   ← 도구 1 · 커서 2 → 보고
15:11:06 턴 완료 | 도구=['open_app','open_app'] | 계획 2/2  ← 도구 2 → 조용
15:11:38 턴 완료 | 도구=['open_app','delete_file'] | 계획 2/2 ← 승인 넘어 완주
```

### 이번 수정이 실제로 잡아낸 것

`"메모장은 최소화 하고 계산기는 닫아줘"` 에서 모델이 **"이제 계산기를 닫을게요"라고**
**말해 놓고 도구를 부르지 않았다.** 어제까지는 그대로 성공이 됐을 자리다. 지금은
`min(커서 2, 호출 1) = 1` 이라 뒤에 **"다만 이건 못 했어요: '계산기 닫기'."** 가 붙었다.
사용자가 `"그래"` 하자 그때 닫혔다.

### 응답 문구만 봤으면 오판할 뻔했다 (A 경우)

`"메모장 열고 계산기 열어줘"` 의 응답은 **`"✓ 계산기를 실행했습니다."` 뿐**이었다.
메모장을 빠뜨린 것처럼 읽힌다. 그런데 로그는 `open_app` **2개**다 — 메모장은 앞선 턴에서
**최소화만 됐지 닫힌 게 아니라** 기존 창 전면화로 처리됐고, 모델이 새로 뜬 계산기만
요약한 것이다. **둘 다 됐으므로 문구가 안 붙은 게 맞다.**

> 이게 M3-1이 A 경우를 테스트로 못 박은 이유다. 여기서 문구가 붙었다면 **거짓 실패**이고,
> 그건 이 프로젝트가 고쳐 온 거짓 성공과 방향만 반대인 같은 결함이다.
> **판정은 문구가 아니라 상태로** — 라이브에서 다시 한 번 값을 했다.

### 기본값을 켰다

`config/settings.py` `plan_enabled: False → True`. 2026-09-04의 규칙(*"라이브 증거가
생기기 전엔 켜지 않는다"*)을 지켰고, **증거가 생겼으므로** 켠다.
지연은 실측 턴 3~5초로 계획 없는 턴(4초)과 비슷했다 — ADR §7-1이 걱정한 만큼은 아니었다.
되돌리려면 `.env`에 `PLAN_ENABLED=false` 한 줄이면 된다.

### 남은 거슬림 (고치지 않았다)

응답이 *"이제 계산기를 닫을게요. 다만 이건 못 했어요: '계산기 닫기'."* 로 **모순되게**
읽힌다. 앞은 모델의 말이고 뒤는 상태가 붙인 사실이다. 후미 문구는 **판정하지 않는다**는
것이 M3 §3-4의 결정이라 그대로 뒀다 — 모델의 말을 지우려면 후미가 앞 문장을 해석해야 하고,
그건 이 그물이 피하려던 바로 그 일이다. 거슬리지만 **틀린 말은 하나도 없다.**

### 검증

- 기본값을 바꾼 뒤 **전체 mock 30파일 783개 통과, 실패 0**(테스트는 `FakeSettings`를
  명시로 넘겨서 제품 기본값과 무관하다).

## 2026-09-07 (계속 3) — 🧭 **BL-21 ① — 커서는 진행률이 아니었다** (M3-1 ADR)

> **📌 다음 세션은 [TASKS.md](TASKS.md) ①의 「계획 수립」 재확인.** 이번엔 **두 문장을**
> **같이** 봐야 한다 — *"메모장이랑 계산기 열어줘"* 는 「못 했어요」가 **붙어야** 하고,
> *"메모장 열고 계산기도 열어줘"* 는 **안 붙어야** 한다. 통과하면 기본값을 정한다.

BL-21의 남은 절반이다. ②(캐시 오염)는 앞 항목에서 막았고, 여기서는
**"못 했다고 말하지 못하는 것"** 을 고쳤다. 설계 문서를 먼저 썼다 —
[design/M3-1_단계완료판정.md](design/M3-1_단계완료판정.md).

### 설계가 예측하고 대가로 받아들인 자리였다

[M3 §6-3](design/M3_계획수립노드.md)에 이렇게 적혀 있었다:

> **단계 완료 판정은 "도구를 안 불렀다"이다.** … 대가는 LLM이 그 단계에서 아무것도
> 안 하고 잡담만 해도 완료로 센다는 것이고, 그건 `[Plan] n/m 단계 완료` 로그로 남긴다.

라이브가 보여준 건 **그 대가가 기능 자체를 무효화한다**는 점이다. 못 한 단계를
말하려고 만든 기능이 못 한 단계를 완료로 세면 남는 게 없다. M3를 고쳐 쓰지 않고
**대체 ADR**을 따로 남겼다 — 무엇을 알고도 감수했는지가 지워지면 같은 판단을 또 한다.

### 한 신호만 보면 반드시 하나가 깨진다

`agent`가 어떤 단계에서 도구를 안 불렀을 때 겉보기가 같은 두 경우가 있고,
**같은 날 라이브에서 둘 다 나왔다.**

```
A 앞 패스가 한 배치에 [open_app, open_app]을 불러 이미 끝냈다   커서 2 · 호출 2
B 모델이 그 단계를 그냥 건너뛰었다                              커서 2 · 호출 1
C 승인을 거부해 중단됐다 (호출은 나와 있고 실행만 안 됐다)        커서 1 · 호출 2
```

커서만 보면 **B**가 깨지고(커서는 무조건 전진한다), 도구 호출 수만 보면 **C**가 깨진다.
A를 B로 오판하면 다 해 놓고 *"계산기 열기는 못 했어요"* 라는 **거짓 실패**가 된다 —
이 프로젝트가 고쳐 온 게 거짓 성공인데 방향만 반대인 같은 결함을 새로 만드는 꼴이다.

**두 신호의 `min`이 셋을 다 통과하는 유일한 자리다.**

```python
covered = min(plan_cursor, 이번 턴 도구 호출 수)
못 한 단계 = plan[covered:]
```

LLM 호출이 늘지 않고, 판정이 **순수하게 상태**다 — `detect_watch_lie`(BL-19 그물)와
같은 규율이다. 정규식도 모델 의견도 끼지 않는다.

### 실행을 강제하지 않기로 한 것이 이 ADR의 핵심이다

오늘 아침 BL-19에 쓴 `tool_choice` 강제를 여기에도 쓸 수 있었다. 쓰지 않았다.
**A를 오판한 채 강제하면 같은 일을 두 번 한다.** `open_app`은 창 규칙 덕에 무해하지만
단계는 임의의 도구이고 그중엔 `DANGEROUS_TOOLS`도 있다. 감시 강제가 안전했던 건
감시가 **멈추면 끝나는** 동작이기 때문이고, 여기엔 그 비대칭이 없다.

M3의 값어치는 완주가 아니라 **보고**다([§1-2](design/M3_계획수립노드.md)).
보고가 돌아오면 기능은 제 몫을 한다.

`plan_cursor`도 이름값을 정리했다 — 진행률이 아니라 **자기루프를 끝내려고 무조건
전진하는 루프 제어 값**이다. 전진 의무(무한루프 방지)는 그대로 두고, **그걸 보고에
그대로 믿던 것**만 바꿨다. 로그도 `n/m 단계 완료` → `n/m 단계 넘어감`.

### 검증

- `tests/test_plan_node.py` **28 → 37**. §9가 A·B·C를 **세 경우 다** 고정한다.
  A는 *"거짓 실패를 만들지 않는가"* 를 보는 자리다 — 이게 없으면 다음 사람이
  「도구 수만 보면 되잖아」로 되돌리고 C를 깬다.
- **전체 mock 30파일 783개 통과, 실패 0.**

### 남은 것

**라이브 미검증이다.** `PLAN_ENABLED`는 여전히 기본 꺼짐이고, 재확인에서 **두 문장을**
**같이** 봐야 한다 — 붙어야 할 곳에 붙는지, **안 붙어야 할 곳에 안 붙는지.**
후자를 안 보면 거짓 실패를 켜 놓고 고쳤다고 믿게 된다.

## 2026-09-07 (계속 2) — 🧊 **BL-21 ② — 틀린 결과가 캐시에 굳는 것을 막았다**

> **📌 다음 세션은 [BL-21 ①](BACKLOG.md)** — 완료 판정. **ADR이 먼저다.**

라이브에서 나온 BL-21 중 **영구화만 먼저** 끊었다. 설계는 건드리지 않았다.

### 한 줄

`_maybe_learn`이 **복합 명령을 학습하지 않는다**(`core/graph_agent.py`).
계획이 선 턴이거나 `is_compound_command`면 그 자리에서 멈춘다.

### 통째로 막아도 잃는 게 없다 — 이게 이 수정의 핵심 논거다

`_is_learnable`은 `len(tool_calls) != 1`을 이미 거절한다. 그러니 계획이 **제대로**
실행된 턴(도구 2개 이상)은 애초에 학습 대상이 아니었다. 즉 **학습까지 도달하는**
**복합 턴은 단계를 건너뛴 실패 턴뿐**이다. 넓게 막는 대신 정상 동작을 하나도 잃지 않는다.

```
"메모장이랑 계산기 열어줘"  계획 2단계 · 도구 1개  → 학습 안 함  ← 어제 굳던 것
"메모장 띄워봐"            계획 없음 · 도구 1개   → 학습함      ← 그대로
"메모장 열고 계산기도"      도구 2개              → 원래도 학습 안 함
```

계획이 **꺼져 있어도** 같은 일이 나므로 발화로도 본다(`is_compound_command`).
읽는 쪽에서 *"잔여 명령이 있으면 캐시를 포기한다"* 고 정한 **BL-15의 쓰기 쪽 짝**이다.
부정어까지 넓게 잡히는데 여기서는 넓은 게 안전하다 — 학습을 덜 할 뿐이고,
부정어 학습 거부는 **BL-02가 바라던 것**이다.

### 검증

- `tests/test_cache_wire.py` **8 → 13**. 실기에서 실제로 굳었던 두 문장을 그대로 쓴다.
  단일 명령이 여전히 학습되는지(회귀)도 같은 자리에서 본다.
- **전체 mock 30파일 774개 통과, 실패 0.**

### 남은 것

**①(완료 판정)은 그대로다.** 결함이 굳지는 않지만 여전히 *"계산기는 못 열었어요"* 라고
**말하지는 못한다.** 그건 완료 판정을 바꾸는 일이고 M3 설계의 뼈대라 ADR이 먼저다.
`PLAN_ENABLED`는 그때까지 기본 꺼짐이다.

## 2026-09-07 (계속) — 🔬 **첫 라이브 확인 — 3건 실패, 그중 하나는 캐시에 굳고 있었다**

> **📌 다음 세션은 [BACKLOG BL-21](BACKLOG.md)부터.** 계획이 건너뛴 단계를 완료로
> 기록하고 **그게 캐시에 학습된다.** ADR이 필요한 변경이다.

사용자가 TASKS ①을 처음으로 돌렸다. **좌표 클릭만 통과했다.** 나머지는 로그와
실측으로 원인을 갈랐는데, **셋 중 둘은 내가 오늘 아침에 고친 것과 무관한 결함**이었다.

### ① 감시 — BL-19이 아니었다 (→ BL-22, 고침)

```
13:20:07 [Monitor] 감시 시작 | 대상='글자 생기면' | 창=메모장
13:20:08 [Agent] 턴 완료 | 도구=['watch_screen']         ← 첫 패스에서 정상 호출
13:22:28 [Monitor] 감시 종료 | 사유=stopped | Vision 0회   ← 2분 21초 동안 0회
```

오늘 아침 넣은 강제 재시도는 **쓰이지도 않았다.** 감시는 정상으로 돌았고
**프리필터가 타이핑을 변화로 보지 않았다.** 1000x700 창을 그려 재보니
`_CHANGED_RATIO = 0.02`는 **글자 한 줄(1.27%)을 통째로 놓치는** 자리였다 —
주석대로 *대화상자* 기준(5% 이상)으로 잡혀 있었기 때문이다.

**0.02 → 0.01.** 한 줄은 걸리고 커서 깜빡임(0.20%)과는 6배가 벌어진다. 회귀는
실측 셀 수로 못 박았다(§4). ⚠️ **글자 1~2자(0.29%)는 여전히 못 잡는다** —
커서와 구분되지 않아 구조적으로 불가능하다. 그런데 고지는 여전히 *"글자 생기면
알려드릴게요"* 라고 받는다. **BL-19 계열이 그만큼 남아 있다**(BL-22에 적었다).

> **교훈**: 같은 증상("감시가 안 된다")에 원인이 두 개였다. 아침에 고친 것은
> *도구를 안 부르는* 결함이고, 실제로 사용자를 막은 것은 *부르고도 못 보는* 결함이다.
> 로그의 `Vision 0회` 한 줄이 둘을 갈랐다.

### ② 계획 — 계획은 정상. 완료 판정이 거짓 완료를 만든다 (→ BL-21, **미수정**)

```
13:23:22 [Plan] 계획 2단계 | 메모장 열기 / 계산기 열기
13:23:26 턴 완료 | 도구=['open_app'] | 계획 2/2        ← open_app 1번인데 2/2 완료
13:26:03 턴 완료 | 도구=없음        | 계획 2/2        ← 도구 0개인데 2/2 완료
```

`"메모장이랑"` 이 안 먹은 게 아니다. **계획은 네 번 다 제대로 섰고**, 모델이 2단계를
건너뛰었는데 완료 판정(*"도구를 안 불렀다 = 단계 끝"*, ADR §6-3)이 그걸 **성공으로
읽었다.** M3가 막으려고 만들어진 바로 그 실패다.

**그리고 캐시가 그 실패를 학습했다.** 되돌리기 전 `cache/command_cache.json`에서:

```
"메모장이랑 계산기 열어줘"          → [open_app(메모장)]     ← 계산기가 없다
"메모장 열고 testing.txt 지워달라고"  → [open_app(메모장)]     ← 삭제가 없다
```

다음부터 같은 말을 하면 **캐시 히트라 LLM을 아예 거치지 않는다.** 틀린 답이
고쳐질 기회 없이 굳는다. BL-12·BL-15·BL-19이 *말로* 거짓말하는 결함이었다면
이건 **상태에 남는 판본**이다. `git checkout`으로 되돌렸고, `PLAN_ENABLED`가
기본 꺼짐이라 지금 새는 경로는 없다.

### ③ 실행 중인 앱 — 판정 도구 자체가 못 믿을 물건이었다 (고침)

`get_running_apps`가 `APP_PROCESS_MAP`을 두고 **자기만의 12개 화이트리스트**를
들고 있었고, 거기에 **계산기가 없었다.** `open_app("계산기")`는 되는데
`get_running_apps`는 계산기를 모르는 상태였다 — *같은 사실이 두 곳에 있어 한쪽만
갱신된*, 이 저장소가 반복해서 데인 모양 그대로다.

TASKS가 *"응답 문구 말고 `get_running_apps` 상태로 판정하라"* 고 적어 둔 그 도구라서,
**②의 판정 근거 자체가 틀려 있었다.** 사용자가 이걸 먼저 고치자고 한 이유다.

- `APP_PROCESS_MAP` **단일 출처**만 본다. 목록을 여기서 다시 갖지 않는다.
- `wt.exe`도 실제 프로세스는 `WindowsTerminal.exe`라 못 잡고 있었다(실기 확인).

TASKS ②의 다음 항목(`plan_enabled` 기본값)은 **사용자의 라이브 확인이 있어야** 정할 수

### 무엇이 문제였나 — 겹 2가 확률만 올리고 있었다

BL-19의 방어는 세 겹이다: ① 프롬프트 재배치 ② 도구 미호출 시 1회 재시도
③ 정직성 그물. 그런데 ②는 **한 번 더 설득하는 것**이었다. 2026-09-04 실측에서
나쁜 구간(`watch_screen` 0/10)에는 **재시도도 같이 실패**했다 — 같은 모델이 같은
이유로 두 번 말로 때우기 때문이다. 확률을 두 번 곱했을 뿐이다.

### 무엇을 바꿨나

재시도 패스만 `llm.bind_tools(tools, tool_choice="watch_screen")`로 묶는다
(중단 요청이면 `stop_watching` — `needs_watch_retry`와 **같은 정규식**으로 고른다.
엉뚱한 도구를 강제하면 안 부르는 것보다 나쁘다). `langchain-google-genai` 4.2.4가
함수 이름 지정을 지원하는 것을 확인하고 썼다.

```
첫 패스(강제 없음) → 도구 0개 + 감시 요청 + 안 보고 있음
  → 재시도(강제=watch_screen) → 도구 호출 → 감시 켜짐 → 재시도 조건이 사라짐
```

**첫 패스는 건드리지 않았다.** 거기에 강제를 걸면 평범한 대화까지 도구를 부른다.
강제가 걸리는 자리는 *"사용자가 감시를 요청했고, 도구를 안 불렀고, 지금 보고 있지도
않다"* 는 세 조건이 동시에 맞을 때뿐이다.

### 폴백을 두 겹으로 둔 이유

`bind_tools(tools, tool_choice=...)`를 **못 받는 상대**가 실제로 많다. 이 저장소의
mock LLM 11개가 전부 `bind_tools(self, tools)` 한 가지 서명이고, provider를 바꾸면
지원하지 않을 수도 있다. 그래서 ⑴ **묶을 때** 예외가 나면 `None`으로 두고
⑵ **부를 때** 예외가 나면 그 자리에서 설득 재시도로 내려온다. 둘 다 **오늘과 글자
그대로 같은 경로**다 — 계획 수립 노드를 만들 때 정한 것과 같은 규칙이다
(*새 기능이 실패하면 착지점은 어제의 정상 경로여야 한다*).

### 검증

  강제가 **재시도 패스에만** 걸리는가 / 중단 요청에 `stop_watching`을 고르는가 /
  `tool_choice`를 모르는 LLM에서 **오늘과 같은 2회 경로**인가 / 강제가 예외를 던져도
  **턴이 죽지 않는가** / 감시가 켜진 뒤 **재시도가 멈추는가**(무한 재시도 방지).
- **전체 mock 29파일 755개 통과, 실패 0**(745 + 10). 실행 후 `git status cache/` 깨끗.

## 2026-09-05 (계속 2) — 🧩 **계획 수립 노드 구현** (M3 ADR §6 1~5단계) · `planner` 신설

> **📌 다음 세션은 [TASKS.md](TASKS.md) ①의 「계획 수립」 라이브 확인부터.**
> `.env`에 `PLAN_ENABLED=true` 한 줄을 넣고 *"메모장 열고 계산기도 열어줘"* 를 돌린 뒤,
> **응답 문구가 아니라 `get_running_apps` 상태로** 판정한다. 그 결과를 보고
> 기본값을 켤지 정한다.

아침에 쓴 [design/M3_계획수립노드.md](design/M3_계획수립노드.md)를 **그대로 구현했다.**
설계에서 바꾼 것은 없고, 설계가 열어 둔 자리 세 개만 정해서 §6-3에 적었다.

### 무엇이 달라졌나

`fast_path`가 캐시를 놓쳤고 그 발화가 복합 명령이면 **`planner`** 로 간다. planner는
분해기를 **턴당 1회** 부르고 결과를 `plan`/`plan_cursor`에 적을 뿐 실행하지 않는다.
실행은 기존 `agent ⇄ tools` 루프가 그대로 하고, `agent`는 단계 지시를
**SystemMessage 교체**로 받는다(`with_step_directive`) — `state.messages`를 건드리지
않으므로 계획 실행 내내 턴 경계가 원래 발화 하나로 유지된다(절대규칙 6).
**노드는 1개 늘었고 실행기는 새로 만들지 않았다.**

```
"메모장 열고 크롬 닫아줘"
 input_guard → fast_path(miss) → planner(계획 2단계)
 → agent[1단계 지시] → tools(open_app) → agent(도구 없음 → cursor=1)
 → agent[2단계 지시] → tools(close_app) → agent(cursor=2) → output_guard
```

### 이 작업의 값어치는 실행이 아니라 **보고**에 있다

지금까지 `"메모장 열고 크롬 닫아줘"` 에서 앞의 하나만 하고 성공했다고 답해도 시스템이
그걸 알 방법이 없었다 — 상태에 "무엇을 하기로 했는지"가 없었기 때문이다. 이제
`output_guard`가 **상태만 읽어** 후미에 붙인다: *"다만 이건 못 했어요: 'test.txt 삭제'."*
BL-12·BL-15·BL-19이 전부 **확인하지 않고 됐다고 말하는** 결함이었고, 이건 그 계열의
마지막 판본이다.

### 설계가 열어 둔 것 — 정한 세 가지

1. **상한(2단계)을 넘는 응답은 잘라 쓰지 않고 통째로 버린다.** 3단계를 2로 자르면
   3번째를 *모르는 채로* 끝나 "못 했다"고 말할 수도 없다 — 이 기능의 존재 이유와
   정반대다. 버리면 착지점이 **오늘의 정상 경로**이고, 계획이 켜져 있으면
   `recursion_limit`이 이미 24라 3단계 명령은 오늘보다 오히려 유리하다.
2. **게이트에서 부정어를 뺐다.** `is_compound_command`는 부정어(BL-02)까지 포함하는데
   `"크롬 말고 메모장 열어줘"` 는 복합처럼 보이지만 실행할 단계가 둘이 아니다.
   감시 요청도 제외한다 — 계획 턴은 `detect_watch_lie`의 "이번 턴 도구 0개" 조건을
   깨뜨린다. **BL-19 그물을 약하게 만드느니 기능을 포기했다.**
3. **단계 완료 판정은 "그 패스에서 도구를 안 불렀다"이다.** 커서가 **반드시** 전진하므로
   `agent` 자기루프는 최대 `len(plan)`회에서 끝난다(전진 없이 되돌리면 HITL 무한루프
   사고와 같은 계열이 된다).

### 위험한 자리는 하나였다 — 승인 경계

`Command(resume=...)`는 `input_guard`를 **거치지 않는다.** 그래서 계획이 승인 중단을
살아남아 완주하고(의도), 그 대가로 `hitl`의 `other_command` 분기에서는 **손으로 지워야**
한다. 안 지우면 승인 대기 중 들어온 `"네이버 열어줘"` 를 처리할 agent가
*"지금은 2단계: test.txt 삭제"* 지시를 받는다 — 취소 플래그가 턴을 넘어 새어
**실제로 삭제해 놓고 "삭제는 취소했어요"라고 답한 사고와 완전히 같은 모양**이다.
전용 회귀가 `tests/test_plan_node.py` [6]이고, `CLAUDE.md` **절대규칙 11**에 못 박았다.

### ① BL-11 해결 — 그런데 방향이 반대인 문제가 더 나빴다

`cache/command_cache.json`은 **git 추적 대상**인데 테스트가 여기에 학습 결과를 써서,
돌릴 때마다 `git checkout`을 해야 했다. BACKLOG가 적어 둔 해결 방향 1번
(`PLUIZ_CACHE_PATH` 류 주입)으로 갔다 — `PLUIZ_CACHE_FILE` 환경변수
(`core/command_cache.py:34`) + `tests/_testenv.py`. **`PLUIZ_LOG_DIR`과 완전히 같은
패턴**이라 새로 배울 게 없고, `import _testenv` 한 줄이면 되므로 **새 테스트는
아무것도 안 해도 안전하다.**

**고치다가 더 나쁜 걸 봤다.** 오염(테스트 → 제품)을 걱정했는데, 실제로는 반대
방향이 이미 새고 있었다:

```
tests/test_bl15_truncation.py:47   cache = get_cache()     ← 사용자의 실제 캐시
```

**43건짜리 스위트가 사용자가 뭘 학습시켰느냐에 따라 결과가 달라질 수 있었다.**
테스트가 제품 상태를 더럽히는 것보다, **테스트가 제품 상태에 의존하는 것**이 위험하다 —
전자는 `git status`에 보이지만 후자는 아무 데도 안 보인다. 이제 시드만 든 새 캐시를
받으므로 결정적이다.

라이브 쪽은 **서버**가 캐시를 쓰므로 `_testenv`로 못 막는다. 서버 기동 시

### 훑다가 나온 것 — **오늘 이미 4단계 복합 명령은 오류로 끝난다**

`core/graph_agent.py:205`의 `recursion_limit: 10`이 이미 시스템을 **순차 도구 호출
3회**로 묶고 있다. 슈퍼스텝을 세어 보면:

```
input_guard(1) → fast_path(2) → agent(3) → tools(4) → agent(5) → output_guard(6)
                                      = 도구 1회에 6, 이후 도구 1회마다 +2
```

도구 3회 = 10, 정확히 상한이다. 4단계짜리는 `GraphRecursionError`를 내고, 그 예외는
`graph_agent.py:232`의 포괄 `except`에 잡혀 **스레드를 지우고**(`_clear_thread`)
*"명령 처리 중 오류가 발생했어요"* 로 끝난다. `visual_verify`가 켜져 있으면 도구
1회마다 +3이라 상한은 더 빨리 온다.

**즉 계획 노드가 대상으로 하는 바로 그 명령들의 현재 실패 방식이 이거다.**
계획을 세우든 안 세우든 **`recursion_limit`은 올려야 한다** — 이걸 모르고
노드부터 만들었으면 mock은 초록인데 실기에서 터졌을 것이다.

### 설계에서 정한 것

| 항목 | 결정 |
|---|---|
| 위치 | `fast_path` → **`planner`** → `agent`. 실행은 기존 `agent ⇄ tools` 루프 재사용, **노드 1개만 는다** |
| replan | **없다.** LLM 호출은 턴당 1회. `visual_verify`의 "판정도 재시도도 하지 않는다"와 같은 절제 |
| 단계 지시 | 메시지가 아니라 **SystemMessage 교체**(`with_watch_directive` 방식). `state["messages"]`를 안 건드리므로 턴 경계가 유지된다(절대규칙 6) |
| 상태 | `plan: list[str]` · `plan_cursor: int`. **리듀서 없음** — 붙이면 지난 턴 계획이 누적된다 |
| 실패 | 계획 수립 실패는 **사용자에게 안 들린다**(오늘 경로로 조용히 수렴). 계획 실행 실패는 **반드시 들린다**(`output_guard`가 상태만 읽어 "…는 못 했어요") |
| 기본값 | **`PLAN_ENABLED=false`.** 라이브 증거 전까지 안 켠다 |
| 병렬 실행 | **미룬다.** 근거 5가지는 ADR §5-2 |

**이 작업의 값어치는 "여러 단계를 실행한다"가 아니라 "몇 단계를 못 했는지 말할 수
있게 된다"에 있다.** `"메모장 열고 크롬 닫아줘"` 에서 앞의 하나만 하고 성공했다고
답해도 지금은 시스템이 그걸 알 방법이 없다 — 상태에 "무엇을 하기로 했는지"가 없기

이건 그 계열의 마지막 판본이다.

어제 적어 둔 교훈("증상이 난 곳과 원인이 있는 곳은 다르다")이 그대로 또 통했다.

### 왜 기존 방어가 못 잡았나

`verify_output()`은 두 가지만 본다 — ① 응답이 **비었을 때** 도구 결과로 복원
② 도구가 `[오류]`를 냈는데 성공처럼 답할 때 교정. 이번 건은 **응답이 비지 않았고
도구가 아예 안 돌았다.** 둘 다 비켜간다. `_NOTHING_HAPPENED_MSG`가 막으려던 거짓말의,
빈 응답이 아닌 판본이다.

### 원인 ① — 금지문이 앞에 서 있었다 (고침)

```
[예전] 화면 감시는 …할 때만 쓰세요. 스스로 판단해서 감시를 시작하지 마세요.
[지금] '~하면 알려줘'라고 하면 반드시 watch_screen을 호출하세요.
       도구를 부르지 않고 '지켜볼게요'라고만 답하면 아무도 화면을 보고 있지 않습니다.
       (다만 사용자가 요청하지 않았는데 스스로 시작하지는 마세요.)
```

도구 docstring에도 같은 억제문이 한 번 더 있어 **이중으로 눌렀다.**
안전을 위해 넣은 문장이 **기능을 통째로 껐다.** 제약은 남기되 **뒤로** 보냈다.

### 원인 ② — 모델 쪽 변동 (못 고침, 정직하게 기록한다)

프롬프트를 고쳐도 **호출률이 시간대에 따라 크게 흔들린다.** temperature=0인데도.

| 구간 | watch_screen 호출 |
|---|---|
| 좋은 구간 | 10/10 · 6/6 · 3/3 |
| 중간 | 4/5 · 2/5 |
| 나쁜 구간 | 0/10 · 0/4 |

같은 구간에 `describe_screen`·`find_ui_element`는 **정상**이었다. 도구를 39개 → 3개로
줄여도, 시스템 프롬프트를 빼도, 서버 대신 in-process로 불러도 달라지지 않았다.
나쁜 구간에서는 모델이 함수 호출 대신 **말로 풀어썼다**(본문에 `**Tool Call` 이라고
텍스트로 쓴 적도 있다). **우리 쪽에서 통제할 수 있는 것이 아니라고 판단했다.**

### 그래서 세 겹으로 갔다 — 마지막 겹이 핵심이다

| 겹 | 무엇 | 보장 |
|---|---|---|
| ① 프롬프트 재배치 | 호출 지시가 먼저, 금지문은 뒤 | 확률을 올린다 |
| ② **1회 재시도** (`needs_watch_retry`) | 감시 요청인데 도구를 안 불렀으면 지시를 덧붙여 한 번 더 묻는다 | 확률을 올린다 |
| ③ **정직성 그물** (`detect_watch_lie`) | **말이 아니라 상태로** 판정해 거짓 보고를 바꾼다 | **보장한다** |

③이 이 작업의 결론이다. 감시는 **진실이 싸게 확인되는** 드문 기능이다 — 모니터가
자기가 켜졌는지 알고 있다. 그래서 네 조건이 다 맞을 때만 응답을 교체한다:
**① 이번 턴 도구 0개 ② 모니터 꺼짐 ③ 사용자가 감시를 요청했다 ④ 응답이 해줬다고 말한다.**
①②가 **상태**라 결정적이고, 정규식은 **범위만** 좁힌다 — 판정하지 않는다.
(손으로 쓴 정규식이 이 프로젝트를 반복해서 무너뜨렸다: BL-02 · BL-15 · HITL 무한루프)

> ⚠️ **`fast_hit` 턴은 제외한다.** `fast_path`는 도구를 **실제로 실행하고도** messages에는
> AIMessage 하나만 남긴다(절대규칙 2). 거르지 않으면 멀쩡히 실행된 캐시 응답을
> 거짓말로 몰아 덮어쓴다. 만들다가 걸린 함정이다.

**범위를 응답 문구가 아니라 사용자 입력으로 잡은 이유**: 실제로 새어나간 거짓말은
*"메모장에서 오류 메시지가 뜨면 바로 알려드릴게요!"* 였다 — `지켜보`도 `감시`도 없다.
응답 문구만 보는 그물은 이걸 통과시킨다. **무엇을 요청했는지가 어떻게 답했는지보다
안정적이다.**

### 곁들여 — 고지가 요약돼 사라졌다

①을 고쳐 도구가 불리기 시작하자 **두 번째 결함**이 드러났다. LLM이 고지를 한 줄로
줄여버렸다:

```
[도구가 만든 것] ✓ '메모장' 창를 지켜볼게요. … 5초마다 화면을 확인하고 …
                 최대 10분(화면 읽기 20회)까지만 … "그만 봐"라고 말씀해 주세요.
[사용자가 본 것] 네, 메모장 창을 지켜보다가 오류 메시지가 보이면 바로 알려드릴게요!
```

간격·상한·중단법이 통째로 사라졌다. **감시를 승인이 아니라 고지로 하기로 한 근거가
바로 그 고지다**(2026-09-03 「설계 전에 정한 것 4가지」). 요약되면 그 근거가 무너진다.
그래서 `watch_notice_to_deliver()`가 도구가 만든 문장을 **원문 그대로** 내보낸다 —
Vision의 답을 요약하지 않는 것과 같은 방침이다.

### V-05는 **말이 아니라 상태로** 검증한다

### 픽셀 프리필터가 전송량 방어의 전부다 (OWASP LLM02)

주기적 캡처는 **화면을 계속 외부 LLM으로 보내는** 일이다. 그래서 5초마다 하는 일은
전부 로컬에서 끝낸다 — 32×32 그레이스케일로 줄여 이전 프레임과 비교하고,
**변화가 있을 때만** Vision을 부른다. 캡처를 몇 번 했든 밖으로 나가는 건 **최대 20장**이다.

**평균 차이가 아니라 바뀐 셀의 비율로 판정한다.** 평균은 화면 일부의 큰 변화가 전체
면적에 나눠지며 묻힌다. 셀 비율(2% ≈ 20셀)이면 시계 초침·커서 깜빡임(1~2셀)은 무시되고
대화상자(보통 5% 이상)는 확실히 걸린다.

변화를 감지하면 **1초 기다렸다 다시 찍어서** 보낸다. 창이 열리는 애니메이션 중간
프레임을 보내면 Vision이 헛것을 본다.

### 🚨 `take_screenshot`을 쓰면 창이 5초마다 깜빡인다

만들다가 발견한 함정이다. `take_screenshot`은 최소화된 창을 만나면 친절하게
`SW_RESTORE` → 캡처 → `SW_MINIMIZE` 한다(`tools/system.py`). 한 번 찍을 땐 좋은
동작이지만 **감시는 5초마다 그걸 한다.** 사용자가 일부러 내려놓은 창이 계속 튀어나온다.

그래서 감시 경로(`tools/vision._capture_image`)는 `IsIconic`을 먼저 보고, 최소화된 창은
**되살리지 않고 못 본다고 답한다** → 엔진이 *"창이 닫혔거나 최소화된 것 같아요"* 라며
감시를 멈춘다. **못 보면 못 본다고 하는 게 맞다.**

창 해석(`resolve_window_hwnd`)과 실제 캡처(`_capture_hwnd`)는 기존 것을 그대로
재사용한다. 따로 구현하면 `take_screenshot`·좌표 계산과 **다른 창**을 볼 수 있다.

### 정직성 — 이 세션의 교훈을 설계에 박았다

이 세션에서 고친 정직성 결함 6건은 전부 뿌리가 하나였다 — **확인하지 않고 됐다고
말하는 것.** 감시는 **사용자가 화면을 보고 있지 않을 때** 도는 유일한 기능이라 그
위험이 가장 크다. 그래서 규칙을 코드로 박았다.

| 규칙 | 왜 |
|---|---|
| **조용히 끝나지 않는다** | 상한 도달·창 사라짐·판독 실패 — **어떤 이유로 멈추든 알린다.** 말없이 사라지면 사용자는 아직 지켜보는 줄 안다 |
| **증거 없는 감지는 알리지 않는다** | Vision이 `detected: true`라면서 무엇을 봤는지 못 말하면 그건 감지가 아니다. 그런 답으로 사용자를 부르지 않는다 |
| **Vision의 말을 그대로 옮긴다** | 요약하지 않는다. 판정을 정규식으로 접지 않는 것과 같은 이유(BL-02 · BL-15 · HITL 무한루프가 전부 손으로 쓴 정규식이었다) |
| **놓쳤을 가능성을 숨기지 않는다** | 종료 알림에 화면을 몇 번 봤는지 적는다 — *"10분 동안 지켜봤지만 못 봤어요. (화면 확인 7회)"* |
| **한 번에 하나만** | 두 개가 돌면 전송량 상한이 두 배가 된다. 이미 감시 중이면 **거절하고 그 사실을 말한다** |
| **멈추라면 멈춘 게 우선** | Vision 호출은 몇 초 걸린다. 그 사이 *"그만 봐"* 가 오면 판정 결과를 버린다 — 방금 "멈췄어요"라고 답해 놓고 어긋나는 말이 뒤늦게 도착하면 안 된다 |
| **`stop_watching`이 "못 봤어요"라고 단정하지 않는다** | 멈추는 순간 화면 확인이 진행 중일 수 있다. *"그동안 화면을 N번 확인했어요"* 라는 사실만 말한다 |

응답 파서(`parse_watch_result`)는 `parse_ui_box`와 같은 방침이다 — **의심스러우면 아무
일도 없던 것으로 본다.** JSON이 아님 · `detected` 필드 없음 · `detected`가 불리언이
아님 · 후보가 여럿 → 전부 "판독 실패"로 처리하고 **알리지 않는다.** 연속 3회면 감시를
멈추고 *"화면을 제대로 읽지 못해서 멈췄어요"* 라고 말한다.

> `detected` 필드가 없을 때 **"안 보인다"가 아니라 "못 알아들었다"로 처리**하는 게
> 중요하다. 둘을 섞으면 모델이 형식을 어길 때마다 조용히 "이상 없음"으로 집계되고,
> 사용자는 감시가 잘 돌고 있다고 믿게 된다.

### 알림은 서버가 밀어넣는다 — 새 채널

감시는 **턴 밖에서** 돌기 때문에 응답으로 돌려줄 곳이 없다. 이 프로젝트에서 서버가
UI에 먼저 말을 거는 건 처음이라 채널을 새로 뚫었다.

```
감시 스레드 ─ set_notifier ─▶ main.py: run_coroutine_threadsafe
                                ├─ TTS mp3 → base64
                                └─ 열린 /ws 전부에 {"type":"notify"}
                                        ▼
                        렌더러: 채팅 버블 + 소리 + 창을 앞으로(show-window IPC)
```

- `notify`는 `start`/`chunk`/`end` 흐름과 **독립된 타입**이라 스트리밍 중에 도착해도
  `streamEl`·`busy`를 건드리지 않는다.
- **붙어 있는 UI가 없으면 알림을 버리지 않고 보관**했다가 다음 연결 때 전한다(최대 5건).
  UI가 잠깐 끊긴 사이 알림이 사라지면, 이 기능이 고치려는 바로 그 문제를 스스로
  저지르는 꼴이다.
- 헤더에 **👁 감시 중 배지**를 띄운다. 재연결하면 서버가 현재 상태를 다시 보내 맞춘다.
  *"켜 둔 걸 잊는 것"* 이 가장 큰 위험이라, 돌고 있다는 걸 항상 볼 수 있어야 한다.
- **서버가 내려가면 감시도 멈춘다.** 알릴 곳도 없이 화면만 계속 나가면 안 된다.

```

### 사용자 결정: 승인 대상으로 (2026-09-03)

클릭은 **되돌릴 수 없고** 좌표는 Vision의 **추정**이다. 둘이 겹치면 "틀린 좌표를
정확히 클릭하는" 도구가 된다 — BL-12(엉뚱한 창에 입력)의 더 나쁜 판본이다.
매번 한 번씩 대답해야 하는 비용을 받아들이기로 했다.

### 세 겹으로 막았다

**1. 좌표를 인자로 받지 않는다.** 이게 제일 중요한 결정이다.
인자는 `(target, window)`뿐이다. `click_at(x, y)` 같은 도구를 두면 **LLM이 좌표를
넘길 수 있고, 넘길 수 있으면 언젠가 지어낸다.** 그래서 찾기와 누르기를 한 도구 안에
묶어, 좌표는 항상 `locate_ui_element`가 **방금 화면을 보고** 계산한 값만 쓴다.

> 대가로 승인 질문에 좌표를 못 보여준다(실행 전이라 아직 모른다). *"'저장 버튼'을
> 찾아서 클릭할까요?"* 까지만 알린다. **지어낸 좌표를 정확히 보여주는 것보다
> 낫다고 판단했다.**

**2. 사람 승인** — `DANGEROUS_TOOLS`에 등록. 질문 문구를 따로 뒀다. 삭제의
*"휴지통으로 갑니다"* 는 클릭엔 **거짓**이라 그대로 쓰면 안 된다. 재질문 문구도
*"삭제하려면 '네'"* → *"진행하려면 '네'"* 로 고쳤다(클릭에도 쓰이므로).

**3. 실행 직전 검사** — 못 찾음 · 화면 밖(다중 모니터 포함) · 창 밖 ·
**캡처 뒤 창이 움직임**이면 누르지 않는다.

> 창 이동 검사가 조용한 함정을 막는다. 좌표는 캡처 시점의 창 위치 기준인데, 승인을
> 기다리는 사이 사용자가 창을 옮기면 그 좌표는 더 이상 그 요소를 가리키지 않는다.
> 그대로 누르면 **엉뚱한 것을 정확히 누른다.** `window_screen_rect`로 대조해 막는다.

**못 찾았을 때 폴백을 넣지 않았다.** "화면 중앙이라도 눌러보기" 같은 건 클릭에선
재앙이다. 아무 데도 누르지 않고 사유를 말한다.

그리고 **클릭했다는 것과 의도한 효과가 났다는 것은 다르다.** 응답도 거기까지만
말한다 — *"원하는 대로 됐는지는 화면을 확인해 주세요."*

### 곁들여: `locate_ui_element` 분리

`find_ui_element`(알려주기)와 `click_ui_element`(누르기)가 **같은 경로**로 좌표를
구하게 내부 함수로 뺐다. 클릭 쪽에서 좌표를 다시 구하면 두 벌이 되어 한쪽만 고쳐진다
— 좌표는 어긋나도 그럴듯해 보이므로 특히 위험하다.

## 2026-09-03 (계속) — 📍 UI 요소 좌표 인식 (`find_ui_element`)

Phase 2의 다음 항목. `describe_screen`은 *"무엇이 보이는지"* 만 답한다. 클릭·자동화로

   크기 72×28. (화면을 보고 추정한 위치예요)
```

### 이 도구는 "좌표를 지어내지 않는 것"이 전부다

`describe_screen`은 설명이 틀려도 사용자가 읽고 거른다. **좌표는 다르다.** 숫자라
그럴듯해 보이고, 다음 항목(좌표 기반 클릭)이 **그대로 믿는다.** 틀린 좌표는 조용히
엉뚱한 곳을 누르고 되돌릴 수 없다 — BL-12(엉뚱한 창에 입력)의 더 나쁜 판본이다.

그래서 못 찾음으로 처리하는 경우를 넓게 잡았다:

| 응답 | 처리 |
|---|---|
| JSON이 아닌 잡담 · 깨진 JSON | 못 찾음 |
| 좌표가 4개가 아님 · 숫자가 아님 · 범위 밖 | 못 찾음 |
| `ymin >= ymax` 처럼 순서가 뒤집힘 | 못 찾음 |
| **화면의 95% 이상을 덮는 박스** | 못 찾음 — "모르겠다"를 그림으로 그린 것이다 |
| **후보가 여럿인 배열** | 못 찾음 + 개수 알림 — 조용히 첫 번째를 고르지 않는다 |
| 객체 하나짜리 배열 | **받아준다** — 형식 문제일 뿐인데 거절하면 그것도 거짓말이다 |

프롬프트에 `[ymin, xmin, ymax, xmax]` 0~1000을 **명시**했다. 모델의 기본 관례에
기대면 조용히 어긋나는데, 좌표는 어긋나도 그럴듯해 보인다.

### 좌표 변환 — 원점을 빼먹으면 통째로 밀린다

정규화 좌표는 **보낸 이미지** 기준이다. 축소는 비율을 유지하므로 **축소 배율은
상쇄되고**, 원본 크기만 있으면 픽셀로 되돌릴 수 있다. 남은 건 **캡처 원점**이다 —
창 캡처면 창의 좌상단이고, 이걸 안 더하면 창이 화면 가운데 있을 때 좌표가 통째로 밀린다.

원점은 `_capture_hwnd`가 찍는 영역과 **같은 함수에서 나와야 한다.** 그래서
`tools/system.py`에서 그 로직을 꺼냈다:
- `window_screen_rect(hwnd)` — DWM 표시 영역. `_capture_hwnd`가 이걸 쓴다
- `capture_origin(window)` — 캡처 이미지의 (0,0)이 화면의 어디인가
- `resolve_window_hwnd(window)` — `take_screenshot`과 좌표 계산이 **같은 창**을 가리키게

따로 구현했으면 조용히 어긋났을 자리다. 그리고 **원점을 캡처보다 먼저 구한다** —
캡처는 됐는데 원점을 못 구하면 창 기준 좌표밖에 없고, 그걸 화면 좌표인 척 내보내면
클릭이 엉뚱한 데를 누른다. 그때는 좌표를 내지 않고 `✗`로 답한다.

## 2026-09-03 (계속) — 🚨 음성과 텍스트가 **서로 다른 대화**였다 (BL-16)

> 앞선 수정 3건은 실기에서 전부 확인됐다(아래 항목). 이번 건은 **삭제 승인만
> 이상하다**는 사용자 보고에서 시작해, 원인이 전혀 다른 곳에 있었던 경우다.

### 증상 — 승인이 승인으로 안 읽혔다

```
👤 그 파일 지워줘            → 🤖 '임시.txt' 파일을 정말 삭제할까요?
🎤 어 삭제해 줘              → 🤖 무엇을 삭제할까요? 파일인가요, 폴더인가요?
   … 100초 뒤, 삭제를 마친 다음 …
👤 메모장 열어줘             → 🤖 '임시.txt' 파일을 찾을 수 없어서 삭제하지 못했어요.
```
> *"실행 해봤는데 삭제가 좀 이상해. 나머지는 괜찮은 것 같아"*

`classify_confirmation("어 삭제해 줘")`는 `approve`다(`_JOIN_AUX_RE`가 `"삭제해 줘"`를
붙이고 `"어"`·`"삭제해줘"` 둘 다 긍정어). 판정 문제가 아니었다.

### 진단 — 어제 넣은 턴 로그가 바로 답을 줬다

```
13:03:58 [Agent] 턴 완료 | 입력='어 삭제해 줘'  | 도구=없음        | 응답 35자
13:05:13 [Agent] 턴 완료 | 입력='메모장 열어줘' | 도구=['delete_file'] | 응답 32자
```
두 번째 줄이 결정적이다 — **"메모장 열어줘"에 `delete_file`이 딸려 있다.** 텍스트 쪽에
승인 대기가 **100초간 살아 있다가** 그 발화를 삼킨 것이다. 즉 음성 turn들은 그
대기를 **보지 못하고 있었다.**

### 원인 — FastAPI 시그니처 한 줄

```python
async def voice_input(audio: UploadFile = File(...), thread_id: str = "default", ...)
```

FastAPI는 `Form(...)` 없는 스칼라를 **쿼리 파라미터**로 읽는다. 그런데 렌더러는
`FormData`로 보낸다(`fd.append('thread_id', threadId)`). 그래서 그 값이 **통째로
무시되고** 음성은 항상 `thread_id="default"`, 텍스트는 `pluiz_<timestamp>` 를 썼다.

**음성과 텍스트가 서로 다른 대화였다.** 기억해서 단정하지 않고 같은 시그니처로
최소 앱을 세워 실행으로 확인했다(테스트 ①에 그대로 남겼다).

이 버그가 위험한 이유는 **조용하기 때문**이다. 평범한 명령은 각자 잘 도니 아무 문제가
없어 보이고, **맥락이 이어져야 하는 순간(승인·"그거"·"거기에")에만** 무너진다.
사용자가 "삭제만 이상하다"고 느낀 것도 그래서다 — 삭제가 승인을 거치는 유일한 경로였다.

**수정** — `thread_id: str = Form("default")`, `use_tts: bool = Form(True)`.
또 지워질 자리라 함수 docstring에 왜 필요한지 못박고 테스트로 고정했다.

### 아직 모르는 것 하나 — BL-17로 남겼다

같은 대화에서 재질문 뒤 `"네"`라고 답한 turn도 승인이 아니라 새 명령이 됐다
(`도구=없음`, 빈 응답 폴백 39자). `"네"`는 `approve`이고 mock의 재질문→승인 경로도
통과한다. BL-16과 얽혀 있어 **이것 때문인지 별개인지 아직 못 가른다.**

로그가 없어서 못 밝혔으므로 관측을 넣었다:

### ③ BL-15 — 캐시가 뒷문장을 삼켰다 (기존 결함, 실기에서 재현)

캐시 파일이 증거다. `hit_count 80 → 82`, `last_used 11:48:34` — **두 번 다 캐시가
가로챘다.** 로그에 `[Vision]`이 없는 것도 같은 이야기다(캐시 히트는 `tools` 노드를
안 탄다).

```
'아니 그냥 새로 메모장 열어서 거기에 회의록이라고 써줘'
   → [S1-intent] ('notepad','open') score=0.90 → open_app(app='메모장')
```
`_COMPOUND_CMD`에 `열고 `는 있는데 **`열어서`가 없다.** 씹은 게 아니라 **문장이 LLM에
도달하지 못했다.** 그래서 "새로"(=새 탭)도 반영될 수 없었다 — 이 두 증상이 한 원인이다.

**수정** — `CommandCache.has_uncovered_command()`. 걸린 entity·action이 차지한 어절을
지우고 **남은 말에 명령형 어미가 있으면 캐시를 포기**한다.

> `열어서`를 정규식에 추가하는 땜질을 하지 않았다. 그러면 `띄워서`·`실행해서`에서 또
> 터진다. **어느 동사인지는 묻지 않는다** — 캐시가 커버 못 한 말에 명령의 꼴이 있으면
> 그걸로 충분하다. 오판의 방향도 안전하다(→ LLM이 문장 전체를 해석. 느릴 뿐 틀리지 않음).

**Stage 1(intent) 히트에만 적용한다.** Stage 2는 문장 전체 유사도(≥0.80)라 뒷문장이
붙으면 점수가 알아서 떨어진다. 이 구분을 빼면 정상 명령이 무더기로 캐시를 못 탄다 —
만들면서 실제로 오탐 5건이 났다: `"볼륨 좀 올려줘"`(트리거 `"볼륨 올"`이 '좀' 때문에
안 걸림) · `"음소거 해줘"`·`"스크린샷 좀 찍어줘"`(entity와 action이 **같은 낱말**이라
뒤따르는 동사가 잔여 명령으로 읽힘).

### 🚨 그런데 네 번째는 **운이 좋았던 것**이었다

```
'새로 메모장 열어줘'  → 캐시 실행 open_app(app='메모장')   ← "새로"가 증발

**어제 사용자가 지적한 바로 그 증상이 아직 살아 있었다** —

`"새로"`는 명령이 아니라 **수식어**다. 캐시 엔트리는 도구 이름만 저장하고 **파라미터를
저장하지 않으므로**(P4 오염 방지 정책) `new=True`를 애초에 표현할 수 없다.

**수정** — 잔여 어절에 `_RESIDUAL_MODIFIERS`(`새로`·`새`·`하나`·`더`·`또`·`따로`…)가
있으면 캐시를 포기한다. 어절 **완전일치**로만 본다 — 부분일치면 `"새로고침"`이 `"새로"`에
걸린다(테스트로 고정).

### 🚨 세 번째 실기 — 수식어 수정은 먹었는데, **폴백 문구가 거짓말을 하고 있었다**

✅ 수식어 수정 확인. 그런데 사용자가 본 응답은:

```

`"명령을 실행했습니다."`는 `verify_output`의 폴백인데, **그 자리에 도달하는 조건이
"LLM 응답도 비었고 이번 턴에 실행된 도구도 없음"** 이다. 즉 **아무 일도 일어나지

**수정** — `_NOTHING_HAPPENED_MSG`:
*"죄송해요, 방금 건 처리하지 못했어요. 다시 한 번 말씀해 주시겠어요?"*
도구가 돌았으면 예전처럼 그 결과로 복원하는 동작은 그대로다(회귀 테스트로 고정).

> **왜 빈 응답이 났는지는 아직 모른다.** Gemini가 도구 호출도 텍스트도 없이 답한
> 것으로 보이는데, **로그로 답할 수 없었다** — 그래프가 턴 단위로 아무것도 남기지
> 않았기 때문이다. 그래서 `PluizGraphAgent`에 턴 요약 로그를 넣었다:
> `턴 완료 | 입력=… | 도구=[open_app] | 응답 NN자`, 빈 응답이면 WARNING.
> **자동 재시도는 넣지 않았다** — 빈 AIMessage가 히스토리에 남은 채로 재실행하면
> Gemini가 또 거부할 수 있고, 빈도부터 재는 게 맞다(BL-15와 같은 원칙).

> **부수 효과 하나는 인정하고 간다** — BL-15 수정으로 `"메모장 새로 열어줘"`가
> **결정적인 캐시 경로에서 비결정적인 LLM 경로로 옮겨졌다.** 그게 맞는 동작이지만
> (캐시는 `new=True`를 표현할 수 없다) LLM의 불안정성에 노출된다. 위 로그가
> 그 빈도를 재 줄 것이다.

### 완료 스텝

**1. `core/graph.py` — `visual_verify` 노드 (동기)**

**2. 증거는 `ToolMessage`를 *교체*해 전달한다** — 이번 설계에서 제일 오래 고민한 부분.

`add_messages` 리듀서가 **같은 `id`를 덮어쓰는** 성질을 쓴다. 대안이 전부 깨졌다:

**3. 판정하지 않는다 — 이번 결정의 핵심**

Vision의 답을 정규식으로 "성공/실패"로 접지 **않고** 원문을 그대로 붙여 agent에게 넘긴다.
자동 재시도도 하지 않는다(사용자 결정: *"정직하게 보고만"*).

> 손으로 쓴 정규식이 이 프로젝트를 반복해서 무너뜨렸다 — BL-02 부정어 오매칭,

**4. 8초를 쓸 값어치가 있을 때만 부른다** (`route_after_tools`, 순수 함수)

대상 도구가 아니거나 · 도구가 이미 `✗`로 실패를 자백했거나 · 이번 턴에 이미 봤으면 건너뛴다.

**6. 설정 — 기본 ON + 스위치**

`vision_verify_enabled: bool = True`. `.env`에 `VISION_VERIFY_ENABLED=false`면

> 피드백 3건 → 그 수정의 회귀 2건. 순서대로 읽어야 왜 이렇게 됐는지가 보인다.

직전 항목(4분류 도입) 직후 사용자가 음성으로 삭제를 시켜 봤더니 **승인이 안 먹었다.**
mock 48개·라이브 9개가 전부 초록인 상태에서 나온 결함이다.

### 🚨 R-1 — 띄어쓰기 하나로 승인이 "다른 명령"이 됐다 (무한 루프)

```
🎤 응 지워 줘        → 🤖 삭제는 취소했어요. 네, '학교문' 폴더를 삭제할게요.
🎤 삭제해 달라니까    → 🤖 '학교문' 폴더를 정말 삭제할까요?
🎤 그래 정말 삭제해 줘 → 🤖 '학교문' 폴더를 정말 삭제할까요?
🎤 그래              → 🤖 (드디어 삭제)
```
> *"왜 내가 여러 번이나 말해야지 그때서야 지워 주지 내 말이 말 같지가 않아"*

`"응 지워 줘"`를 어절로 쪼개면 `[응][지워][줘]`인데 **`줘`가 긍정어 목록에 없다.**
그래서 승인 판정에 실패하고, 하필 명령형 어미(`줘`)로 끝나서 **`other_command`로
분류** → 삭제를 취소하고 그 말을 새 명령으로 재실행 → LLM이 다시 삭제를 호출 →
또 승인 질문. **내가 만든 4분류가 그대로 루프를 만들었다.**

**수정** — `_JOIN_AUX_RE`로 보조용언을 붙이고(`"지워 줘"` → `"지워줘"`),
강조어(`정말`·`그냥`…)는 걷어낸 뒤 **남은 말이 전부 긍정어일 때만** 승인.
강조어만 있으면(`"정말"` 한 마디) 승인이 아니다.

### 🚨 R-2 — 실제로 삭제해 놓고 "취소했어요"라고 답했다

```
🎤 그래 → 🤖 삭제는 취소했어요. 네, '학교문' 폴더를 휴지통으로 옮겼어요.
```

`deletion_cancelled` 플래그를 `output_guard`에서만 껐는데, **승인 질문 상태로 턴이
끝나면 `output_guard`를 거치지 않는다.** 그래서 앞 턴에 켜진 값이 살아남아 다음 턴의
정상 응답에 달라붙었다. 모순이자 위험한 오보다(사용자가 안 지워졌다고 믿는다).

**수정** — `hitl`의 **모든 반환 경로**가 플래그를 명시하고, `input_guard`도 새 턴
시작 시 끈다. `resume`은 `input_guard`를 안 타므로 둘 다 필요하다.

### 창 재사용 규칙 — 사용자가 지적한 것

*"기존에 열려있는 창이 있으면 새 창을 여는 게 아니라 앞으로 가져와야 하는데,
메모장 열어달라니까 새 창을 만든다. 초기에 해결했던 건데 또 이러더라"*

**원인**: `open_app`이 실행 중일 때 **UWP 셸 명령을 먼저** 실행했다. 그런데
`notepad.exe`를 다시 띄우는 건 전면화가 아니라 **새 창을 만드는 것**이다.
그래놓고 *"창을 앞으로 가져왔습니다"* 라고 답했다 — BL-12와 같은 **정직성 문제**다.
(원래 이 순서는 *설정* 앱의 포커스 실패를 우회하려고 넣은 것이었는데, 그 예외가
모든 UWP 앱에 적용되고 있었다.)

**규칙을 정했다** ([ARCHITECTURE § 창 규칙](ARCHITECTURE.md#창-규칙--기존-창-재사용)):

| 상황 | 동작 |
|---|---|
| 이미 열려 있음 + 그냥 "열어줘" | **기존 창을 앞으로** (새 창 X) |
| 이미 열려 있음 + "새로/하나 더/새 탭" | **새 탭** (탭 지원 앱) → 아니면 새 창 |
| 안 열려 있음 | 실행 |
| 탐색기 | **예외** — 항상 새 창 |

- 포커스를 **먼저** 시도하고, 실패했을 때만 셸 명령으로 폴백한다(설정 앱 대응 유지).
- `open_app(app, new=False)` 파라미터 신설. 시스템 프롬프트에 언제 `new=True`를
  줄지 명시했다.
- 새 탭은 포커스 성공을 **확인한 뒤에만** `Ctrl+T`를 보낸다 — 포커스 실패 시 키가

## 2026-09-02 (계속) — BL-14: 로컬 API 접근 제어 (보안 4층 → 5층)

> **다음 세션은 [TASKS.md](TASKS.md) ②로 간다** — `[즉시/위험]`이 0건이 됐으므로
> 남은 건 로드맵상 9월 목표인 **Phase 2(실행 결과 시각적 검증)** 다.
> 실기 확인 2건(리뷰 수정 · UI가 인증 후에도 그대로 도는지)은 ①에 함께 적어 뒀다.

### 발단
사용자가 TASKS ②에서 **BL-14**를 골랐다. 문서에 적힌 해결 방향은
① CORS 축소 ② 토큰 ③ `provider`를 `Literal`로 — 세 가지였다.

### 🚨 착수하자마자 ①이 틀렸다는 게 드러났다

원래 항목은 *"`allow_origins`를 Electron origin으로 축소"* 라고 적고 있었다. **불가능하다.**
렌더러는 `loadFile`(`electron-ui/main.js`)이라 출처가 `file://` → 브라우저가
`Origin: null`을 보낸다. 그 값을 허용해야 **UI 자신이 도는데**, `null`은 아무 사이트의
sandboxed iframe도 받는 값이다.

더 중요한 건 이것이다 — **CORS는 응답을 *읽는* 것만 막고 요청 *처리*는 막지 않는다.**
공격 페이지가 응답을 못 읽어도 **명령은 그대로 실행된다.** 즉 CORS는 이 문제의 해결책이
아니라 곁다리다. **토큰이 유일한 실질 방어**라는 결론에서 설계를 다시 잡았다.

### 🚨 문서에 없던 더 큰 구멍 — `/ws`

**WebSocket에는 CORS가 아예 적용되지 않는다.** 웹페이지가
`new WebSocket('ws://127.0.0.1:8765/ws')`로 그냥 붙어서 명령을 보낼 수 있었다.
BL-14 항목은 `fetch`만 적고 있었지만 **`/ws`가 fetch보다 큰 구멍**이었다.
게다가 HTTP 미들웨어는 WS를 타지 않으므로 엔드포인트 안에서 직접 막아야 한다.
브라우저 WS는 헤더를 못 붙이므로 토큰은 쿼리(`?token=`)로 받는다.

### 하마터면 UI를 통째로 막을 뻔한 것 — 프리플라이트

`X-Pluiz-Token`은 CORS safelisted 헤더가 아니다. 그래서 **렌더러의 모든 요청이 먼저
OPTIONS 프리플라이트를 보내는데, 거기엔 그 헤더가 실리지 않는다.** 인증을 그대로 걸면
프리플라이트가 401을 받고 **UI 자신의 모든 통신이 죽는다.** OPTIONS는 아무것도 실행하지
않고 정보도 주지 않으므로 면제했다. (실측으로 확인 — 아래 검증 참조)

### 무엇을 했나

### 🚨 D-1 — HITL 승인 판정이 일상 명령을 "네, 삭제하세요"로 읽고 있었다

`_APPROVE_RE = r'응|네|예|그래|해\s*줘|진행|…'` 을 `search()`로 훑고 있었다.
**부분 문자열이라 평범한 명령이 승인으로 읽힌다.** 실측(삭제 승인 대기 중 발화):

| 발화 | 옛 판정 | 왜 |
|---|---|---|
| `네이버 열어줘` | 승인 → **삭제 실행** | `네` |
| `음소거 해줘` | 승인 | `해 줘` |
| `그래프 그려줘` | 승인 | `그래` |
| `진행 상황 알려줘` | 승인 | `진행` |
| `응용 프로그램 목록` | 승인 | `응` |
| `예약 확인해줘` | 승인 | `예` |

일상 명령 10개 중 **6개가 오승인**. *"애매하면 취소"* 라는 안전 기본값이
무력화돼 있었다 — 애매한 게 아니라 확신을 갖고 승인으로 넘어갔다.
게다가 승인 대기 중 발화는 `Command(resume)`로 소비되므로
**사용자가 하려던 명령은 실행되지도 않고 사라졌다.**

**수정** — `classify_confirmation()` 신설. 3분류(`approve`/`reject`/`unclear`)로 바꾸고,
승인은 **발화를 어절로 쪼개 모든 어절이 긍정어일 때만** 인정한다(부분 문자열 검사 폐기).
`unclear`면 취소하지 않고 **한 번 더 묻는다**(`hitl` 노드의 interrupt 루프,
최대 2회 → 그래도 애매하면 취소). `interpret_confirmation()`은 bool 하위호환으로 유지.

## 2026-09-02 (계속) — 웨이크워드: Whisper 한계 규명 → 전용 모델로 전환 (진행 중)

> **다음 세션은 [TASKS.md](TASKS.md)의 🔵 항목을 보면 된다.** 재개 절차가 명령어까지 적혀 있다.
> 결정 근거는 [design/M2_웨이크워드_전용모델.md](design/M2_웨이크워드_전용모델.md).

### 무슨 일이 있었나
사용자가 "인식이 안 된다"고 보고 → 콘솔이 cp949라 무엇을 들었는지조차 볼 수 없어서
**UTF-8 로그 파일부터 붙이고** 원인을 하나씩 갈랐다. 그 과정에서 나온 실측이 결정을 만들었다.

### Whisper 경로를 끝까지 밀어붙인 결과 (전부 개선하고 커밋함)
- 청크 경계 문제 → 슬라이딩 윈도우(2초 창 / 0.6초 간격)
- 무음 임계 0.015 → 0.008 (`energy=0.0147`로 간발의 차 폐기되던 발화 관측)
- tiny → **base** (같은 오디오에서 61.1초/환각3 vs **12.9초/환각0**. base가 5배 빠르다)
- hotwords **끔** (켜면 환각 3→11건, 2.4배 느려짐 — 모델이 힌트를 앵무새처럼 뱉는다)
- 오인식 변형 거리 1 → **2** (감지 38% → 69%, 오탐 0/20)
- **환각 필터 신설** — 수백 자 난수 텍스트에 변형이 섞여 실제로 오탐이 났다

### 그럼에도 69%가 천장이다 — 그리고 그게 이 결정의 근거다
edge-tts로 "플루이즈"를 24가지로 합성해 Whisper 출력을 수집했다.
정확히 맞힌 건 **tiny 1/24, base 4/24**. 대부분 `플로이즈`·`플로이드`·`하이퍼노이즈`로 들었다.

유사도 매칭으로 완화도 시도했으나 **신호와 잡음이 겹쳐 분리되지 않았다**:
`'플로이드 모해'`(깨야 함) 0.50 = `'루이비통 검색해줘'`(깨면 안 됨) 0.50.

**"플루이즈"는 한국어에 없는 조어라 ASR이 실제 단어로 끌어당긴다.** 튜닝의 문제가 아니다.
애초에 문장을 받아적는 모델을 키워드 스포팅에 쓴 게 도구 오용이었다.

### 전환 — openWakeWord 임베딩 + 자체 분류기
사용자 승인 후 `openwakeword` 설치(의존성 7개, **torch 없음** — onnxruntime이 이미 있었다).

```
오디오 → melspec → Google 음성 임베딩 → 우리가 학습한 MLP
        └─ openWakeWord 사전학습 ONNX ─┘   └ scikit-learn ┘
```

- 임베딩 추출 **2초에 27ms** — Whisper의 1/15~1/25
- 공식 학습 파이프라인(torch·speechbrain)을 쓰지 않는다. V2에서 torch를 뺐던 결정을 지킨다.
  추론은 행렬곱 몇 번이라 직접 구현 → **런타임 의존성이 늘지 않는다**
- `scripts/wakeword_data.py` · `scripts/train_wakeword.py` 작성 완료
- 하드 네거티브를 의도적으로 넣었다 — 플로이드·블루투스·루이비통·플레이리스트.
  이게 없으면 "플" 소리에 반응하는 모델이 된다

## 2026-09-02 (계속) — 🚨 웨이크워드는 한 번도 실행된 적이 없었다

### 발단
사용자가 알려준 사실 둘: **호출어는 "소윤아"가 아니라 "플루이즈"** 이고
(*"헤이 구글"* 처럼 *"헤이 플루이즈"*), **사용자가 직접 설정할 수 있으면 좋겠다.**

그런데 코드를 열어 보니 그보다 먼저 확인해야 할 게 있었다.

### 🚨 근본 원인 — Electron이 잘못된 python으로 띄우고 있었다

`electron-ui/main.js`는 `spawn('python', [script])` 였다. Windows에서 그 `python`은
**anaconda base**로 잡히는데, 거기엔 `sounddevice`도 `faster_whisper`도 없다.

```
python -c "import sounddevice"    → ModuleNotFoundError
python -c "import faster_whisper" → ModuleNotFoundError
```

`wakeword.py`는 최상위 import 실패 시 `sys.exit(1)` 한다. 그리고 `main.js`는:

```js
wakeProc.on('exit', code => { if (code !== 0) setTimeout(startWakeword, 5000); });
```

**즉 5초마다 조용히 죽고 다시 뜨기를 반복하고 있었다.** 콘솔 로그에만 남고 UI엔 아무
표시가 없었다. 발표자료에는 *"tiny 모델 오탐율 심각 → 포기"* 로 기록돼 있었는데,
**인식률을 평가할 기회 자체가 없었다.** 모델 문제가 아니었다.

> 이 프로젝트가 같은 유형에 데인 게 이번이 세 번째다.
> ① 의존성 8개 미설치로 도구 9개가 죽어 있음 ② 라이브 테스트 미실행
> ③ 웨이크워드 미실행. **공통점: 실패가 조용해서 아무도 몰랐다.**

### 완료

**① 호출어 정정 + 사용자 설정** (`services/wakeword.py`, `config/settings.py`)
- 기본값 `["플루이즈", "pluiz"]`. 부분매칭이라 *"헤이 플루이즈"* · *"플루이즈야"* 도 걸린다
- `.env`의 `WAKE_WORDS`(쉼표 구분) · `WAKE_WORD_ENABLED`로 사용자가 지정
- **재시작 불필요** — `_reload_loop`가 10초마다 `.env`를 다시 읽는다
  (`get_settings.cache_clear()` 필수 — CLAUDE.md 절대규칙 4)
- 설정 로딩이 깨져도 기본값으로 계속 동작한다 (웨이크워드가 설정 때문에 죽으면 안 된다)

**② 오인식 변형 자동 생성** (`_expand`)
Whisper tiny는 고유명사를 흘려 듣는다. 사용자가 `플루이즈` 하나만 적어도
`플루이스`·`블루이즈`·`프루이즈` 등 14개 변형을 만든다.
**한 글자만 바꾼 변형(거리 1)까지만** — 전수 조합은 오탐을 급격히 늘린다.
확인: `블루투스 켜줘` · `루이비통 검색해줘`는 걸리지 않는다.

**③ Electron python 탐색** (`electron-ui/main.js` `resolvePython()`)
후보를 `-c "import sounddevice, faster_whisper"`로 **실제 검사**해서 고른다:
`PLUIZ_PYTHON` → conda `pluiz` 환경 → `python`. 실측에서 pluiz 환경이 선택됐다.
전부 실패하면 **재시도하지 않고** UI에 `unavailable`을 보낸다 —
환경 문제는 재시도로 안 고쳐지는데 예전 코드는 영원히 재시도했다.
뜨자마자 죽는 경우도 **3회까지만** 시도한다.

**④ 실패를 드러낸다** (`_die()`)
무엇이 없는지 · 어떻게 고치는지 · **어떤 python으로 실행 중인지**를 stderr에 찍고,
stdout에는 `WAKEWORD_ERROR`를 보내 Electron이 UI에 표시할 수 있게 했다.

**⑤ API** (`POST /api/wakeword`, `GET /api/config`)
`.env` 기록은 `_write_env()`로 공통화. 실측에서 **기존 키 4개 무손상**, 웨이크워드 2줄만 추가됐다.

### 왜 테스트가 못 잡았나 — 구조적 결함
`INPUT-03`은 이랬다:
```python
if "엔터" in r or "키" in r: ok(...); results["pass"] += 1
else:                        ok("응답 수신"); results["pass"] += 1
```
**두 분기 모두 PASS.** 구조상 실패할 수 없었다. 에이전트가 "눌렀어요"라고 말한 것만
확인했지, 실제로 눌렸는지는 보지 않았다. `WEB-02`도 폴백("가져오지 못했습니다")을
PASS로 셌다.

**기능이 망가졌는데 통과하는 테스트는 없는 것보다 나쁘다.**

## 2026-09-01 (계속) — BL-03 · BL-02 해결 (보안필터 · 캐시 부정어)

### BL-03 — 위험 명령어 공백 없는 변형
- **증상**: `rm-rf`(공백 없이)를 `\brm\s+-[rRfF]`가 놓침.
- **조사 중 추가 발견**: 같은 갭이 **5개 패턴에 더** 있었다 —
  `del/f/s` · `rmdir/s/q` · `taskkill/f` · `shutdown/r` · `schtasks/delete` · `cipher/w`.
  BACKLOG에는 `rm-rf` 하나만 적혀 있었는데 실제로는 8개가 대상이었다.
- **해결**: 명령어–플래그 사이 공백 `\s+` → `\s*` (8개 패턴).
  앞의 `\b`가 `warm-rf` 같은 단어 내부 매칭을 막아 오탐을 방지한다.
  `net user x y`처럼 공백이 의미를 만드는 건 `\s+` 유지.
- **함께 해소**: `check_security`의 위험 명령어 패턴에 **mock 테스트가 아예 없었다**
  (서버가 필요한 `test_commands.py`에만 존재). 이제 CI에서 자동 검증된다.

### BL-02 — 캐시 부정어 오매칭
- **증상**: "계산기 **말고** 다른거 열어" → 캐시가 `계산기 열어줘`로 오매칭해 계산기를 엶.
- **원인**: 캐시는 entity+action만 본다. 부정어는 의미를 뒤집으므로 매칭 자체를 신뢰할 수 없다.
- **해결**: `core/fast_path.py`에 `_NEGATION_CMD` / `has_negation()` 추가 →
  `is_compound_command()`에 연결. 부정어가 있으면 캐시를 **조회조차 하지 않고** LLM으로 보낸다.
- **오탐 방지**: 어절 경계 요구(`말고(?=\s|$)`). 무조건 찾으면 "말고기 검색해줘" ·
  "대신동 지도 보여줘" 같은 정상 입력이 캐시를 못 탄다.
- **메모**: BACKLOG의 해결 위치가 `agent.py`로 적혀 있었으나 그 파일은 M1-P5에서
  `archive/`로 옮겨졌다. 실제 위치는 `core/fast_path.py`였다. → BACKLOG 갱신함.

### ⚠️ 7.6 맥락 버그 진단 정정 (중요)

- 노트의 원인 지목("astream에 thread_id/config 누락")은 **현재 코드와 불일치**.
  현재 `run_async`/`stream` 모두 `config={"configurable":{"thread_id":...}}` 전달 중
  (agent.py:320, 328, 659). 이미 반영돼 있음.
- **실제 원인 가설**: 커맨드 캐시·결정론적 라우터가 LLM 없이 처리 후 즉시 return하여
  해당 명령이 LangGraph 대화 기록(MemorySaver)에 **누적되지 않음**.
  → "메모장 켜줘"(캐시 처리) 다음 "그거 꺼줘"가 실패하는 구조적 원인.
  → M1에서 코드로 재현·확인 후 수정안 보고 예정.
