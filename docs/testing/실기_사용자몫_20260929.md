## 1. 📅 일정이 어느 달력에 있나 — BL-80 (🙋 사용자만 확인 가능)

**G-01 이 «오늘은 일정이 없어요!» 라고 답했는데 사용자에게는 일정이 있었다.**

확인해 보니 `qusthdb0@gmail.com` 의 **기본 달력**은 지난 7일~앞으로 7일 통틀어 **0건**이었다.
즉 도구는 자기가 본 것을 정직하게 옮겼고, **안 본 달력이 있다.**

🚨 **프로그램이 확인할 수가 없다** — 지금 받는 권한이 `calendar.events` 라
달력 목록 조회(`calendarList().list()`)가 **403** 이다.

### 🙋 사용자가 봐 줄 것 (2분)

1. [Google 캘린더](https://calendar.google.com) 를 연다
2. 왼쪽 「내 캘린더」 목록에서 **오늘 일정이 들어 있는 달력의 이름**을 본다
3. 그것이 **기본 달력(내 이름 = `qusthdb0@gmail.com`)** 인지, **다른 달력**인지 알려 준다

| 답 | 그러면 |
|---|---|
| **다른 달력이다**(예: 「학교」·「구독한 달력」) | BL-80 진단이 맞다 → 권한을 `calendar.readonly` 로 넓히고 달력 목록을 돈다 |
| **기본 달력이 맞다** | 진단이 틀렸다 → 날짜 범위·시간대(`timeZone`)를 다시 본다 |

🔑 **어느 쪽이든 ⓑ 는 지금 한다** — *«없어요»* 대신 *«기본 달력에는 없어요»* 로
**무엇을 봤는지 말하게** 한다. 범위를 못 넓히더라도 **거짓말은 지금 멈출 수 있다.**

## 3. 🎙 새 웨이크워드 모델 — 오늘 로그가 실전에서 말해 준 것

**9/28 에 바꾼 모델(임계 0.62)이 실기에서 처음으로 18분을 돌았다.**
아래는 사람의 기억이 아니라 `logs/pluiz.log` 에서 센 것이다.
🔁 **다시 세려면** `python scripts/count_wake.py 217` (신설).

### 잰 구간

| | |
|---|---|
| 구간 | **16:33:38 ~ 16:52:06** = **18분 28초** (0.308시간) |
| 설정 | `backend=model · 임계=0.62 · 에너지=0.0015 · win=2.0s · hop=0.6s` |

### 센 것

| | 횟수 |
|---|---:|
| 🔔 **깨어남(WAKE)** | **25** |
| ㄴ 그중 음성 인식까지 간 것 | 22 |
| ㄴㄴ **말을 알아들은 것** | **15** (google 14 · whisper 1) |
| ㄴㄴ 🚨 **«인식하지 못했다»가 나간 것** | **7** |
| 아깝게 못 깬 구간(0.31~0.62) | 410줄 |
| 무음이라 아예 안 본 구간 | 152 |

### 🔑 읽는 법 — 실험실 숫자가 현장에서 맞았다

깨어난 **25번 중 7번은 그 뒤에 아무 말도 안 잡혔다.** 그 일곱을 **헛깨어남**으로 보면

> 7회 ÷ 0.308시간 = **약 22.7회/시간**

9/28 실측이 임계 0.62 에 대해 예측한 값은 **25회/시간**이었다.
🔑 **실험실에서 고른 운용점이 현장에서 거의 그대로 나왔다** — 자가 맞았다는 뜻이다.

🚨 **그리고 그것이 곧 전시회 목표를 못 맞춘다는 뜻이다.** 목표는 **오탐 ≤1회/시간**이다.
18분 동안 부스에 서 있었다면 **일곱 번 혼자 깨어났을 것**이다.

### ⚠️ 이 숫자를 과하게 읽지 말 것 — 세 가지 유보

| | 무엇 |
|---|---|
| 1 | **일곱이 전부 헛깨어남이라는 보장은 없다.** 말을 했는데 STT 가 실패한 것이 섞였을 수 있다. 가르려면 그 순간의 오디오를 들어야 한다 |
| 2 | **이 18분은 부스가 아니다.** 사용자가 **내내 말하고 있던** 구간이라, 조용한 시간보다 헛깨어남이 나기 쉽다. 반대로 부스는 더 시끄럽다 |
| 3 | 🚨 **로그의 «놓침» 410줄을 「놓친 호출」로 읽으면 안 된다.** `services/wakeword.py` 496행은 **확률 0.31~0.62 인 모든 구간**에 그 말을 붙인다. 대부분은 부르지도 않은 평범한 말소리다 |

### 🔑 가장 큰 발견 — 헛깨어남이 **한 구간에 전부 몰려 있다**

깨어난 25번을 **확률별로 갈라서** 그 뒤에 무슨 일이 있었는지 짝지어 봤다.

| 깬 확률 | 횟수 | 말이 잡힘 | 🚨 인식 못 함 | 연속 WAKE 로 잘림 |
|---|---:|---:|---:|---:|
| **0.90 이상** | 13 | 10 | **0** | 3 |
| **0.62 ~ 0.90** | 12 | 3 | **7** | 2 |

🔑 **헛깨어남 7건이 전부 아래 칸에 있다. 위 칸에는 한 건도 없다.**

아래 칸의 실제 모습(16:45) — *"오 오 오"* 밖에 안 들어간 구간에서 **7초 안에 세 번**
깨어났다(0.73 · 0.75 · 0.64). 바로 뒤 STT 는 빈 결과였다.

### 📌 그래서 다음 수가 정해진다 — 임계를 올리는 게 아니다

임계를 0.90 으로 올리면 **헛깨어남 7건이 전부 사라진다.** 그런데 **진짜 호출 3건도
같이 죽는다**(0.78 *"매일 그만 봐도 돼"* · 0.72 *"메모장 지켜보다가…"* · 0.69 *"오 오 오"*).
놓침률을 도로 올리는 거래라 **그건 답이 아니다.**

🔑 **대신 이 표가 「2단계 확인」을 정확히 어디에 걸어야 하는지 말해 준다**
→ [M7 §4-D](../design/M7_웨이크워드_재구축.md)

> 확률 **0.90 이상은 그냥 통과**시키고(13번 중 틀린 게 0이다),
> **0.62~0.90 인 것만** 2단계로 한 번 더 확인한다.

이러면 ① 확실한 호출은 **느려지지 않고**, ② 비싼 확인은 **애매한 절반에만** 들고,
③ M7 이 2단계의 단점으로 적어 둔 *"FRR 을 더 나쁘게 한다"* 가 **위 칸에는 아예 적용되지 않는다.**

🚨 **다만 표본이 25번뿐이다.** 이 경계(0.90)를 코드에 박기 전에 §17 실기로
**표본을 더 모아야** 한다. 25번으로 정한 경계는 그 25번에만 맞는 경계다.

## 4. 🚨 오늘 새로 드러난 것 — 「메일」이 「내일」·「매일」로 들린다

BACKLOG 에 아직 없는 것이다. 로그에서만 보인다.

```
16:37:59  STT '내일 오면 알려 줘'   → watch_inbox( from:(내일) )   ← 사람 이름으로 잡았다
16:39:41  STT '매일 오면 알려 줘'   → watch_inbox( from:(매일) )
16:40:03  '아니 매일 님한테 아니라 그냥 어떤 메인 메일이간에 오면 알려 달라고'
```

🔑 **도구는 시키는 대로 했다.** 문제는 «메일»이 **STT 에서 「내일」·「매일」로 바뀌는데
그게 그대로 사람 이름이 되는 것**이다. 그리고 취소하는 데 **세 번**이 걸렸다
(*"내일 그만 봐도 돼"* · *"매일 그만 봐도 돼"* · *"내일 알람 꺼 줘"*).

📌 **정할 것** — `watch_inbox` 가 `from:` 을 잡을 때 **「내일」·「매일」처럼 사람 이름일 수
없는 말**을 걸러야 하는가. 🚨 아니면 이것은 STT 쪽 문제로 두는가.
→ 이번 실기에서 **다시 나오는지 먼저 본다**(§17 W-05).
