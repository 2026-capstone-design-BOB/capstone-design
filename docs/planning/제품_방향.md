## 1. 이 프로젝트가 되려는 것

> **"옆에 앉아 있는, 내 화면을 같이 보는 똑똑한 사람 한 명"**

사용자가 쓴 정의를 그대로 옮기면 네 가지다.

| | 무엇 |
|---|---|
| 같이 본다 | 내가 보는 화면을 **함께 이해한다** |
| 내 PC를 안다 | 내 컴퓨터 환경에 **빠삭하다** |
| 대신 한다 | 알아서 클릭하거나 작업을 **해 준다** |
| 찾아 준다 | *"그게 어딨지"* 에 **확대하거나 짚어 준다** |

**넷째가 이 프로젝트의 얼굴이 될 후보다.** 앞의 셋은 대체재가 있지만
(→ [§4 냉정한 평가](#4-냉정한-평가--computer-use와의-비교)), 넷째는 성격이 다르다.

## 2. 기능별 구상

### 2-1. Vision — 여기가 제일 중요하다

사용자 판단: *"vision 기능이 아마 우리 프로젝트의 얼굴이 될테니 가장 신경써서 개발."*
현재 상태(2026-09-07 Phase 2 종료)는 [ROADMAP](../ROADMAP.md) 참조.

**아직 없는 것 둘 — 둘 다 같은 자산 위에 얹힌다:**

- **포인팅 · 확대** — *"그게 어딨지"* 하면 **화면에 표시**한다.
  노안·저시력 등 **접근성 보조**의 성격이다.
- **설정창 길안내** — *"블루투스 어디서 켜?"* → 설정을 열고 **해당 항목을 짚어 준다.**
  사용자가 실제로 겪는 불편에서 나왔다: *"막상 설정창 들어가면 헤메는데."*

> **왜 이 둘이 값어치가 큰가** (Claude 의견)
> ① **카테고리가 다르다.** 클릭 자동화는 *대신 해 주는* 것이고, 포인팅은
>    *사용자가 직접 하게 돕는* 것이다. 범용 에이전트가 대체하지 않는 자리다.
> ② **거의 만들어져 있다.** `find_ui_element`가 이미 창 원점을 포함한 **화면 좌표**를
>    반환하고, Electron에 always-on-top 오버레이 창이 이미 있다. 남은 건 그 좌표에
>    표시를 그리는 것이다.
> ③ **위험이 0이다.** `click_ui_element`는 되돌릴 수 없어 승인이 필요하지만,
>    **포인팅은 아무것도 바꾸지 않으므로 승인이 필요 없다.**

### 2-2. 도구 — "두뇌는 있는데 팔다리가 제대로인지 모르겠다"

사용자 문제의식: *"Agent는 두뇌, 도구는 팔다리. 가능한 많은 도구로 coverage를
확보하고, 두뇌의 판단을 어떻게 할지가 중요."* 그리고 *"현재 도구가 제대로 주어졌는지
모르겠음(판단이나 이런)."*

> **이건 감이 아니라 잴 수 있다** (Claude 의견)
> `logs/pluiz.log`의 모든 턴에 `도구=['open_app', ...]`가 이미 찍혀 있다. 세 가지를
> 뽑을 수 있다 — **① 39개 중 실제로 쓰인 도구 수 ② 도구가 없어서 실패한 턴
> ③ 잘못 고른 턴.** ②가 가장 중요하다. BL-07이 *"UX 문제인 줄 알았는데 기능
> 구멍이었다"* 로 밝혀진 것이 정확히 그 사례다.
> 졸작 문서에 **실측 데이터**로 그대로 들어간다.

### 2-3. 음성

| | 구상 | 현재 자산 |
|---|---|---|
| **웨이크워드** | 실서비스 수준의 **높은 인식률** | 전용 모델 파이프라인 완성, **녹음 대기** → [M2 설계](../design/M2_웨이크워드_전용모델.md) |
| **TTS** | 사람 같은 목소리·억양, 무료, **목소리 선택**, 오프라인 여부 | edge-tts(무료 신경망) 사용 중. `tts_voice` 설정이 **이미 있다** — UI만 없다 |
| **TTS 끄기** | 끄고 싶을 때가 있다 | `/voice`의 `use_tts`가 **이미 있다** — UI 토글만 붙이면 된다 |
| **STT** | *"개떡같이 말해도 찰떡같이"*, 발음 교정, **상시 대기** | `services/stt.py`에 교정 사전이 이미 있다. 상시 대기는 **웨이크워드가 해결한다** |

> 입력 시간이 고정돼 있고 상시 대기가 아닌 것은 **웨이크워드가 완성되면 같이 풀린다.**
> 「완전 백그라운드」(§2-5)도 마찬가지다 — **웨이크워드가 여러 항목의 선행조건이다.**

### 2-4. 답변 형식

사용자 문제의식: *"말이 너무 길면 안 될 것 같으면서도 너무 짧으면 정보 전달이 부족.
막 괄호같은거 그냥 읽더라고."*

> **화면용 텍스트와 TTS용 텍스트를 분리하면 한 자리에서 풀린다** (Claude 의견)
> 화면에는 `✓`·괄호·이모지·줄바꿈을 그대로 두고, TTS에는 정제한 문장을 보낸다.
> 길이 문제도 같은 곳에서 조절된다. 지금은 **한 문자열이 두 목적을 겸하고 있어서**
> 어느 쪽에 맞춰도 다른 쪽이 어긋난다.
>
> 실행 실패·거부·미완료의 **답변 형식을 고정**하는 것은 이미 절반 와 있다 —
> `output_guard`의 *"삭제는 취소했어요"*(접두)와 *"다만 이건 못 했어요"*(접미)가
> 자리를 나눠 쓰는 규칙이 그것이다. → [M3 §3-4](../design/M3_계획수립노드.md)

### 2-5. UI

- **채팅창 전환 버그** — 실행 후 클릭해도 채팅 화면으로 안 바뀌는 경우가 있다.
  ⚠️ **재현 조건 미확인** — 다음 세션에서 한 줄 받아 잡는다.
- **안내 · 사용 매뉴얼** — 즐겨찾기 쪽에 목록으로 붙인다.
- **포인팅 효과** — §2-1과 같은 자산(오버레이 창)을 쓴다.
- **완전 백그라운드** — 안 되면 **최대한 거슬리지 않게** 배치.
  → 웨이크워드가 되면 창이 떠 있지 않아도 부를 수 있으므로 **자동으로 해결된다.**

### 2-6. 피드백 · 결함 발견

사용자 문제의식: *"상용화 관점에서 결함은 신고를 통하지 않으면 발견이 어렵다."*

> **졸작 범위에서는 자동 수집이 더 값어치 있다** (Claude 의견)
> 이미 로그에 정직 신호가 찍힌다 — `[BL-19]`(감시 미호출) · `[BL-21]`(복합 명령
> 학습 차단) · `못 했어요`(미완료 단계). **이걸 세면 신고 없이도 결함률을 안다.**
> 2026-09-07이 그 근거다: **mock 808개가 전부 초록인데 결함 셋이 라이브에서만
> 드러났다.** 사용자 신고에만 의존했다면 셋 다 못 봤다.

## 3. ⏸️ 열린 결정 — 아직 안 정했다

### 3-1. 사용자 데이터를 클라우드로 올릴 것인가

사용자 구상: *"사용자에 맞게 최적화되고 기억하는 게 서비스 기능이라면, 그 데이터를
PC뿐 아니라 클라우드에서 관리해야 하지 않나. 그러면 로그인 시스템도 필요한데
머리아프네 진짜."*

> **Claude 의견: 하지 않기를 권한다.** 셋 다 무거운 이유다.
> ① **정체성과 충돌한다.** [ROADMAP](../ROADMAP.md)이 *"인터넷 없이도 핵심 기능"* 을
>    **핵심 차별점**으로 적어 뒀는데 클라우드 동기화는 정반대 방향이다.
> ② **화면 데이터가 얽힌다.** Vision이 다루는 게 사용자 화면이다. 서버에 두는 순간
>    프라이버시 설계가 졸작 범위를 넘어간다.
> ③ **본체가 죽는다.** 인증·서버·DB에 3주를 쓰면 포인팅도 웨이크워드도 못 한다.
>
> **대안**: `내보내기 / 가져오기` 파일 하나(캐시 + 메모리를 zip으로). 기기 이동
> 요구의 대부분이 해결된다. 심사에서 물으면 *"설계상 로컬 우선이고 이동은 파일로
> 합니다"* 가 **방어가 아니라 선택으로 들린다.**

**상태: 미결정.**

### 3-2. 무엇을 안 하기로 할 것인가

10월까지 3주다. 다 하면 전부 어설프게 끝난다(→ [§5](#5-10월-이전-3주-계획)).
**미루는 것과 «안 하기로 정하는 것»은 다르다** — 후자여야 한계점 분석이 된다.

후보: **장기 메모리 · 루틴 학습 · 클라우드 동기화.**

**상태: 미결정.** 정해지면 「왜 안 했는지」를 이 문서에 남기고 ROADMAP에서 내린다.

### 3-3. 포인팅·확대를 2주차 메인으로 올릴 것인가

**상태: 미결정.** 올린다면 구현 전 ADR을 쓴다
([WORKFLOW § 설계 결정](../WORKFLOW.md) 규칙).

## 4. 냉정한 평가 — computer use와의 비교

사용자 문제의식: *"claude computer use가 너무 잘 되어 있어서 비교되기도 해서 조금
견제를 많이 하는 중. 네가 할 수 있으면 우리도 다 한다 + 너네보다 우리가 이런 면에서
낫더라."* 그리고 *"vision이 제일 베스트, 나머지는 굳이 AI 잘 나온 거 쓰면 되는데
왜 굳이 써야 되지?"*

> **Claude 의견: 「우리도 다 한다」는 지는 싸움이다.** 범용성 경쟁은 이길 수 없다.
> 그런데 **이미 이기고 있는 축 셋**을 안 세고 있다.

| | Pluiz | computer use |
|---|---|---|
| **아는 것은 안 보고 한다** | `open_app`을 **네이티브 Windows API**로 부른다. 창 목록을 *보는* 게 아니라 **안다**. 캐시 히트면 **LLM 호출 0회 · 0.2초** | 매 스텝 스크린샷을 클라우드로 보낸다 |
| **인터넷이 끊겨도 돈다** | 캐시 + 오프라인 STT 폴백 | 불가능 |
| **안 한 걸 안 했다고 말한다** | 도구 실행 **상태**로 판정한다(BL-12·15·19·21 계열) | 없음 |

**정직한 약점**: 범용성. Pluiz는 39개 도구가 덮는 것만 한다.

**심사용 한 문장:**

> **"computer use는 무엇이든 하지만 매번 화면을 봐야 하고,
> Pluiz는 아는 것은 즉시 하고 모르는 것만 봅니다."**

열등감이 아니라 **다른 설계 선택**이고, 근거가 이미 로그에 남아 있다.

## 5. 10월 이전 3주 계획

> **⚠️ 이건 제안이지 확정이 아니다.** 확정되면 [TASKS.md](../TASKS.md)로 옮기고
> 여기서는 링크만 남긴다.

| 주차 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| **1주** | 웨이크워드 완주(녹음 → 학습 → 런타임 교체) + UI 버그 | 9월을 **진짜로** 닫는다. 웨이크워드는 **상시 대기·완전 백그라운드의 선행조건**이라 하나를 풀면 셋이 풀린다 |
| **2주** | **포인팅 · 확대 + 설정 길안내** | 얼굴이 될 기능. **기존 Vision 자산 재사용**이라 싸고, 승인이 필요 없어 위험이 없다 |
| **3주** | 임베딩 캐시(= 심사의 RAG 항목) + 도구 사용 실측 | 강의 개념 매핑의 **마지막 구멍** → [ROADMAP § 강의 개념 매핑](../ROADMAP.md) |

**잘라내는 것**: §3-2 참조.

## 6. 10월 이후 — 졸작 준비

사용자가 정한 항목 그대로다.

- **서류** — 개발 Task 목록 · 문서 · 계획서의 **일치 여부**와 완성도
- **advanced 기능** — 현재 기능의 더 나은 방식·구조
- **SW 품질** — 캐싱 · 반응 속도 · **할루시네이션 억제** · 잘못된 행위 피드백 ·
  Agent 프레임워크가 프로젝트 구조에 적절한지 · 유지보수성
- **SW 검증** — 지속적 테스트와 결과 분석
- **한계점 · 극복 방법 · 어려웠던 점** — ⚠️ *"10월부터가 아니더라도 계속"*
  (오래된 캐시 문제 등)

> **한계점 서술은 이미 재료가 쌓여 있다.** BACKLOG의 BL 항목들이 *"무엇이 왜
> 어려웠고 어떻게 갈랐는가"* 를 시간순으로 담고 있고, 특히 **2026-09-07 하루가
> «mock이 전부 초록인데 라이브에서만 드러난 결함 셋»** 이라는 완결된 사례다.
> 새로 쓰는 게 아니라 **골라내는 작업**이다.

### 개발 외 메모

- **토큰 부족 → 다른 사람 계정 사용?**
  ⚠️ **권하지 않는다** — 계정 공유는 이용약관 위반이다.
  실효가 있었던 것은 ① `CLAUDE.md`의 토큰 규칙(서브에이전트 금지 · 직접 읽기)
  ② **세션을 쪼개고 `docs/`로 인계하기** — 2026-09-07에 실제로 그렇게 진행했다.
