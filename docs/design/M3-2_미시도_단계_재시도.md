## 1. 배경 — 사용자가 리허설에서 적은 말

> *"복합 명령 실행 실패 하면 성공한 것은 성공 했다고 하고 실패한 걸 실행 안 하고
> 실패했다고 하잖아. 이거 솔직히 이렇게 얘기하면 내가 또 한 번 더 해 달라고 얘기 해야 하는
> 번거로움이 있고 또 어차피 해야 하는 일이기도 하니까 실행 시킬 순 없나?
> **물론 실패해서 문구 뜨는 건 그렇다 쳐도, 할 수 있는데 그냥 명령 씹혔다고 안 하는 건
> 좀 그렇잖아.**"*
> — 2026-09-12 1차 리허설, [LAUNCH_CHECKLIST M-01](../testing/LAUNCH_CHECKLIST.md)

🔑 **마지막 문장이 이 ADR의 범위를 정한다.** 사용자가 스스로 둘을 갈랐다:

| | 무엇 | 사용자의 말 | 이 ADR |
|---|---|---|---|
| ① | **시도해서 실패했다** | *"실패해서 문구 뜨는 건 그렇다 쳐도"* | **건드리지 않는다** |
| ② | **아예 안 해 봤다** | *"할 수 있는데 그냥 명령 씹혔다고"* | **여기만 다룬다** |

②는 [BL-19](../BACKLOG.md)(감시를 **부르지도 않고** "지켜볼게요")·
[BL-35](../BACKLOG.md)(*"찾아볼게요"* 하고 아무것도 안 함)와 **같은 계열**이다.
이 저장소는 그 둘을 이미 «1회 재시도»로 막았다 — **계획 안에서만 그물이 없었다.**

## 2. 현행 평가 — 왜 지금은 안 하나

[M3-1 §3-2](M3-1_단계완료판정.md)가 *"이 ADR에서 가장 중요한 결정"* 이라며 강제를 거부했다.
근거 셋은 **지금도 전부 유효하다**:

1. A(했음)를 B(안 함)로 오판한 채 강제하면 **되돌릴 수 없는 동작을 두 번** 한다
2. `watch_screen` 강제가 안전했던 건 감시가 **멈추면 끝나는** 동작이라서다
3. M3의 값어치는 완주가 아니라 **보고**다

§5-3도 못을 박았다 — *"«못 했다»고 말할 뿐 다시 시도하지 않는다. **의도한 것이다.**"*

**그런데 §6이 문을 하나 열어 뒀다:**

> **읽기 전용 도구에 한정한 단계 강제.** `DANGEROUS_TOOLS`도 상태 변경도 없는 단계라면
> **중복 실행이 무해하므로** `tool_choice` 강제를 붙일 수 있다.

근거 1·2가 «되돌릴 수 없음»에 걸려 있으므로, **되돌릴 것이 없는 도구**에는 안 걸린다.
이 ADR은 그 문만 연다.

## 3. 🚨 순진하게 구현하면 생기는 함정 — 설계의 핵심

§6 문장을 글자 그대로 따라 **`tool_choice="any"` + 읽기전용 목록**으로 강제하면
**새 거짓말이 생긴다.**

```
계획 2단계: ① 메모장 열기 ② b.txt 삭제
② 에서 모델이 도구를 안 불렀다 → 재시도 → 읽기전용만 묶인 채 «반드시 부르라»
→ 모델이 delete_file을 못 부르니 find_file('b.txt') 를 부른다
→ 이번 턴 도구 호출 수 +1 → steps_covered +1 → unfinished_notice 가 침묵
→ 🚨 b.txt 는 안 지워졌는데 사용자는 «못 했어요»를 못 듣는다
```

**강제는 «부를 것이 없어도 부르게» 만든다.** 그 헛호출이 `steps_covered`(M3-1 §3-1)의
두 신호 중 하나를 그대로 오염시킨다. 결과는
[BL-26](../BACKLOG.md)(«안 한 걸 했다고 말했다»)·[BL-32](../BACKLOG.md)와 **같은 모양**이고,
[BL-51](../BACKLOG.md)을 고치며 얻은 *"한 곳에서만 판정하게 한다"* 도 무너진다.

> 🔑 **§6은 «강제해도 안전하다»를 도구 기준으로만 따졌다.** 헛호출이 **판정을 오염시킨다**는
> 두 번째 경로를 안 봤다. §6을 쓴 시점에는 `steps_covered`가 막 생긴 참이었다.

## 4. 목표 구조 — 보장은 «구조»가 한다

두 가지를 **각각 다른 구조**로 보장한다. 프롬프트는 어느 쪽도 보장하지 않는다
(BL-19의 교훈: *"프롬프트는 확률을 올릴 뿐이고 보장하는 건 구조다"*).

| 무엇을 막나 | 무엇이 막나 |
|---|---|
| 위험·상태변경 도구가 재시도에서 튀어나오는 것 | **묶는 도구 목록 자체를 좁힌다** — 목록에 없으면 부를 수 없다 |
| 헛호출이 «못 했어요»를 침묵시키는 것 | **`tool_choice`로 강제하지 않는다** — 억지로 부를 이유를 안 만든다 |

**둘째가 이 ADR의 결정적인 한 줄이다.** BL-19·BL-35는 강제했지만 여기서는 안 한다 —
저 둘은 «부를 도구가 정해져 있는» 경우였고(`watch_screen`), 여기는 **부를 것이 없을 수도
있는** 경우다.

### 모든 분기에서 오늘보다 나쁘지 않다

| 단계의 성격 | 오늘 | 이 설계 |
|---|---|---|
| 읽기전용인데 안 해 봤다 | "못 했어요" (사용자가 다시 말해야) | **재시도가 해낸다** ✅ |
| 읽기전용인데 재시도도 안 부른다 | "못 했어요" | "못 했어요" — **똑같다** |
| 위험/상태변경 단계 | "못 했어요" | 목록에 없어 못 부른다 → "못 했어요" — **똑같다** |
| 대화로 끝나는 단계([BL-36](../BACKLOG.md)) | "못 했어요"(거짓 실패) | **그대로 남는다** — 이 ADR의 범위 밖 |

🔑 **최악이 «오늘의 동작»이다.** 그래서 이 변경은 되돌릴 것이 없다.

### 🚨 구현하다 나온 것 — 재시도가 **돈다**

배선하고 그래프를 따라가 보니 루프가 있었다. ADR을 쓸 때는 안 보였다:

```
2단계에서 도구 0개 → 재시도 → get_running_apps 실행 → agent로 되돌아옴
→ 이번 응답도 «도구 0개»(마무리 문장) → 또 재시도 → 도구 → agent → …
```

커서는 **도구를 안 불렀을 때만** 전진하므로(M3 §6-3), 재시도가 성공하는 한
커서가 안 움직여 같은 자리에서 계속 걸린다.

→ `needs_step_retry`에 **`turn_calls <= cursor`** 를 넣었다. `steps_covered`와
**같은 셈**이다 — `cursor`번째 단계를 덮으려면 이번 턴 호출이 `cursor+1`개는 있어야
하고, 그 이하면 이 단계는 아직 안 돈 것이다. 새 상태를 만들지 않고 이미 있는
`turn_tool_call_count`를 쓴다.

> 🔑 **«증상을 먼저 코드로 만든다»가 또 값을 했다**(2026-09-12 BL-51과 같은 교훈).
> 테스트를 먼저 쓰지 않았으면 이 루프는 **2차 리허설에서 사람 앞에** 나왔을 것이다.

### 허용목록은 «위험하지 않은 것»이 아니라 «읽기»다

`DANGEROUS_TOOLS`의 여집합을 쓰지 않는다. `open_app`·`volume_up`·`type_text`는
위험하지 않지만 **상태를 바꾼다.** 빠뜨리면 조용히 새므로 **화이트리스트**로 적는다.

```python
READONLY_RETRY_TOOLS = {
    "find_file", "list_directory",
    "get_running_apps", "get_battery_status", "get_current_time",
}
```

**§6이 예로 든 `describe_screen`은 일부러 뺐다.** §6의 기준은 *"중복 실행이 무해하므로"*
인데, `describe_screen`은 **화면을 한 장 더 외부로 내보낸다.** 그건 무해한 중복이 아니다 —
이 저장소가 `watch_screen`에 고지·상한·Vision 호출 횟수 로그를 붙인 이유와 같다.
같은 이유로 `get_clipboard_text`(개인정보)·`take_screenshot`(파일 생성)·
웹 검색류(검색어가 외부로 나간다)도 뺐다.

⚠️ **좁게 시작한다.** 넓히는 건 언제든 되지만, 새는 건 한참 뒤에 발견된다.

## 6-1. `open_app` 확대 — **2026-09-15 결정 · 적용** (⏸️ 였던 것)

§6의 한계 ①이 남겨 둔 문이다. 사용자가 1차 리허설에서 든 예가
*"메모장 열고 계산기도 열어줘"* 인데 **그 ②가 정확히 이 목록 밖**이었다.

### 🔑 근거를 «무해해서»가 아니라 **«멱등해서»** 로 잡는다

§4가 세운 기준은 *"허용목록은 «위험하지 않은 것»이 아니라 «읽기»다"* 였다.
그 문장의 이유는 **기준이 무를수록 도구가 늘 때마다 조용히 샌다**는 것이다.
`open_app`은 «읽기»가 아니므로 **기준을 무르게 하는 대신 칸을 하나 더 만든다**:

```python
READONLY_RETRY_TOOLS  = {...}            # 읽기
IDEMPOTENT_RETRY_TOOLS = {"open_app"}    # 읽기는 아니나 «다시 해도 같은 자리»
STEP_RETRY_TOOLS = READONLY_RETRY_TOOLS | IDEMPOTENT_RETRY_TOOLS
```

🚨 **합치지 않는 것이 이 결정의 전부다.** 하나로 합치면 다음 사람이 «여기 넣어도
되나»를 물을 때 **읽기인지 멱등인지 기준이 사라진다.** 어느 쪽으로 들어왔는지가
목록에 남아야 한다.

**`open_app`이 멱등인 근거는 코드에 있다** — `tools/app_control.py`의 `open_app`은
이미 실행 중이면 새 창을 만들지 않고 **포커스만** 한다(`_is_running` → `_focus_window`).
2026-09-02 실기에서 **새 메모장이 쌓이던 것**을 고치며 들어간 규칙이다.

### 무엇을 **안** 넣었나 — 이쪽이 더 중요하다

| 도구 | 왜 아닌가 |
|---|---|
| `close_app` | 멱등해 보이지만 **되돌리는 방향**이다. 헛호출의 대가가 다르다 — 안 시킨 창이 닫히면 **사용자가 하던 일이 사라진다** |
| `volume_up`·`volume_down` | 부를 때마다 값이 **누적**된다. 애초에 멱등이 아니다 |
| `type_text` | 같은 이유 + BL-12의 «거짓 성공» 이력 |
| 나머지 | §4 그대로 |

### ⚠️ 알고 넘어가는 것

- **`explorer`는 창 규칙의 유일한 예외다**(`app_control.py` §explorer 전용) —
  탐색기는 항상 새 창을 연다. 다만 M-01 재시도는 **«이 단계를 아예 안 해 봤을
  때»만** 도는 것이라(`turn_calls <= cursor`) 이미 연 것을 또 열지 않는다.
  **예외가 문제가 되려면 커서 회계가 먼저 틀려야 한다.**
- **§3의 함정은 그대로 남는다.** 강제하지 않으므로 모델이 엉뚱한 단계에서
  `open_app`을 헛호출하면 `steps_covered`가 밀려 «못 했어요»가 침묵할 수 있다.
  이 위험은 `find_file`에도 원래 있었고 **`open_app`이 늘린 만큼만 늘었다.**
  ⚠️ **3차 리허설에서 대본 7장면**(*"메모장 열고 b.txt도 지워줘"*)**을 볼 때
  이것도 같이 본다** — 2단계가 삭제라 재시도가 붙을 수 있는 자리다.

**검증**: `test_plan_node` 77 → **82**. ⑩-a가 **두 목록이 섞이지 않았음**을,
⑩-b가 **누적형 도구가 안 들어왔음**을, ⑰~⑲가 **사용자가 든 예**를 못 박는다.
