## 0. 한 문단으로

**«플루이즈»라고 부르면 깨어나는 기능**이다. 지금 **두 가지가 다 나쁘다** — 안 불렀는데
**시간당 74.7번** 깨고, 불러도 놓친다. 원인은 모델 구조가 아니라 **학습 데이터**다.
지금 학습에 쓴 소리가 **전부 합성 음성(TTS)** 이라 **실제 마이크 소리를 한 번도 본 적이 없다.**
10월에 **실제 사람 목소리 + 실제 잡음**으로 다시 학습한다. **학습 자체는 노트북에서 7~45분**이고,
**진짜 오래 걸리는 것은 사람 목소리를 모으는 일**(20~30명 · 마감 10/06)이다.

> ✅ **2026-09-22 — 말뭉치·도구·의존성은 전부 준비됐다**(디스크 확인). **모자란 것은 목소리뿐이고,
> 지금도 «6명짜리 후보»는 바로 만들어 볼 수 있다**(약 7분 · 런타임은 안 건드린다) → §6-③.

## 1. 🧠 «학습»이 실제로 무엇을 학습하는가 — **여기가 제일 헷갈린다**

«모델을 학습시킨다»고 하면 보통 **밑바닥부터 AI를 만드는 것**을 떠올리는데, **우리가 하는
일은 그게 아니다.** 시스템은 **3단**이고 **우리는 마지막 하나만** 학습한다.

```
 마이크 소리
     │
     ▼
 ① 멜 스펙트로그램   1.06 MB   ← 남이 학습한 것. 한 줄도 안 건드린다
     │                            (소리를 «그림»으로 바꾼다)
     ▼
 ② 음성 임베딩       1.27 MB   ← 남이 학습한 것. 한 줄도 안 건드린다
     │                            (그림을 «숫자 1,536개»로 요약한다)
     ▼
 ③ 분류기            561 KB    ← 🔴 우리가 학습하는 것. 이것 하나뿐이다
     │                            숫자 1,536개를 보고 «플루이즈냐 아니냐»만 답한다
     ▼
  확률 0.0 ~ 1.0
```

| | |
|---|---|
| 우리가 학습하는 것 | **파라미터 약 15만 개짜리 분류기 하나** (3층 MLP · `1536 → 96 → 32 → 1`) |
| 남의 것 | 멜 스펙트로그램 + 임베딩 = **2.3 MB** (openWakeWord 사전학습 ONNX) |
| 🔑 비유 | **귀는 빌려 쓰고, «이 소리가 플루이즈인지»를 판단하는 법만 우리가 가르친다** |

> ### 🔑 그래서 나오는 결론 셋
>
> 1. **GPU가 필요 없다.** 15만 파라미터짜리 분류기 하나라 `sklearn`으로 CPU에서 돈다
>    (이 프로젝트는 V2에서 **torch를 의도적으로 제거**했다).
> 2. **«더 좋은 모델로 바꾸면 되지 않나»가 답이 아니다.** 바꿀 수 있는 건 ①②인데
>    **거기가 문제가 아니다.** ③이 본 **데이터**가 문제다.
> 3. **openWakeWord 공식 모델(`alexa`·`hey_jarvis`)도 ③과 같은 지위의 물건**이다.
>    «플루이즈»를 아는 기성 모델이 세상에 없어서 우리가 만드는 것이지,
>    **모델이 부족해서가 아니다.**

📌 근거 — [M7 §2](M7_웨이크워드_재구축.md) (2026-09-11 코드·모델 파일 실측)

## 2. ⚙️ 지금 어떻게 동작하나 — 한 바퀴

```
마이크 (16kHz)
   │
   ├─ 2초짜리 «창»을 0.6초마다 하나씩 잘라낸다
   │
   ├─ [에너지 관문] 너무 조용하면 여기서 버린다 (RMS 0.0015)
   │                 → 종일 무음일 때 헛일을 안 한다
   │
   ├─ [①②③ 통과] → 확률이 나온다              ⏱ 창 하나에 28.7 ms
   │
   ├─ [임계 비교] 확률이 임계 이상이면 «깼다»
   │
   └─ [쿨다운 2.5초] 한 번 깨면 2.5초 동안 다시 안 깬다
                      → 같은 «플루이즈»를 겹친 창들이 보고 세 번 깨는 걸 막는다
```

**임계(threshold)가 이 시스템의 손잡이**다 — 올리면 덜 깨고(오탐↓ 놓침↑),
내리면 더 깬다(오탐↑ 놓침↓). **이걸 어디에 둬도 목표에 못 간다**는 것이 지금 문제의 핵심이다(§3).

📌 지연 **28.7 ms**는 이미 충분하다 — 목표에도 «유지»라고 적혀 있고 건드릴 이유가 없다.

## 3. 📊 지금 무엇이 나쁜가 — 숫자 둘

| 무엇 | 지금 | 목표 | 어떻게 쟀나 |
|---|---|---|---|
| **안 불렀는데 깬다** (오탐 · FA) | 🔴 **74.7회 / 시간** | **≤ 1회** | 연속 오디오 **1.94시간** 실측 (2026-09-18) |
| **불렀는데 안 깬다** (놓침 · FRR) | **16.0%** | **≤ 10%** | 녹음 **119회** 재생 |
| 같은 것을 실제로 방에서 | 🔴 **80%** → **50%** | | 10번 불러서 (09-09 → 09-14) |
| 지연 | 28.7 ms | 유지 | — |

### 🚨 «놓침»이 두 숫자인 이유 — **섞으면 안 된다**

| 어떻게 쟀나 | 값 | 무엇을 잰 것인가 |
|---|---|---|
| **녹음 파일을 틀어서** (119회) | **16.0%** | 조용한 방 · 30cm · 휴대폰 마이크 |
| **실제로 방에서 불러서** (10번) | **80%** → **50%** | 노트북 마이크 · 실제 거리 |

**둘이 다른 게 결함이 아니라, 둘이 다른 것을 재고 있다.**
🚫 **«16%»를 «실기 숫자»로 말하면 안 된다** — [기준선 §5-C](../research/2026-09_웨이크워드_기준선.md)가
못 박아 둔 규칙이다. 발표에는 **나쁜 쪽인 실기 숫자**를 쓴다.

### 🔴 그리고 «손잡이로는 못 고친다»가 측정으로 닫혔다

임계를 **0.30부터 0.99까지** 전부 훑었는데, **가장 좋은 0.99에서도 오탐 26.3회**였고
그 대가로 놓침이 **35.9%**가 됐다. 목표(1회)에 **두 자릿수 배수로 못 간다.**

> 🔑 **«설정 하나로 고칠 수 있지 않을까»가 여기서 끝났다 — 재학습 말고 길이 없다.**

## 4. 🔍 원인은 하나다 — **학습 데이터에 실제 마이크 소리가 없다**

지금 모델이 학습에 쓴 것:

| | 무엇을 썼나 |
|---|---|
| 양성 (플루이즈) | `edge-tts` **합성 목소리 15종** — 전부 컴퓨터가 만든 소리 |
| 음성 (플루이즈 아님) | **같은 합성 목소리**로 만든 **40문장** |
| 증강 | 속도 · 음량 · **백색잡음** · 반사 1회 «흉내» |

**두 증상이 한 뿌리에서 나온다:**

- **실제 사람 목소리가 학습 분포 «밖»이다** → 불러도 안 깬다
- **실제 대화·소음이 학습 분포 «밖»이다** → 아무 소리에나 확률이 튄다
  🚨 분포 밖 입력에 모델은 «모르겠다»가 아니라 **`확률 1.000`** 을 낸다.
  실기 오탐이 전부 0.990~1.000인 것이 정확히 이 모양이다.

### 🔒 2026-09-09에 한 번 실패했고, **그 실패가 규칙이 됐다**

실제 녹음을 **양성에만** 넣고 학습했다. 그랬더니 모델이 «플루이즈냐»가 아니라
**«마이크에서 온 소리냐 합성이냐»** 를 배웠다 — 그게 **훨씬 쉽게 갈리는 축**이기 때문이다.
결과는 **마이크에서 온 것이면 뭐든 깨어남(86.7%)**.

> 🔒 **규칙: 실제 오디오는 양성·음성 «양쪽»에 들어가야 한다.**
> 한쪽에만 넣는 순간 그 모델은 **«마이크 탐지기»** 가 된다.

### 🚨 평가도 같이 틀렸다 — **«95%»가 거짓말이었던 이유**

검증셋도 **전부 합성음**이었다. **학습과 같은 편향을 가진 눈으로 채점**했으니
95%는 «합성음을 잘 분류한다»만 말한 것이고, 실기는 20%였다.

> 🔑 **M7에서 가장 중요한 한 줄** — 데이터를 고쳐도 **평가를 안 고치면 세 번째도
> «95%»를 보고 «끝났다»고 적는다.** 그래서 이번엔 **자를 먼저 만들었다**(아래 1단계).

## 6. ⏱️ 기간 — **학습은 짧고, 사람이 오래 걸린다**

### ① 학습 자체 — 노트북으로 충분하다 (2026-09-19 실측)

| 설정 | 창 수 | 걸리는 시간 | 메모리 |
|---|---|---|---|
| 기본값 | 6,300 | **약 7분** | 0.04 GB |
| 중간 | 13,000 | **약 16분** | 0.08 GB |
| 크게 | 36,400 | **약 45분** | 0.22 GB |

병렬화도 끝냈다 — 창 2,700개 기준 **1코어 168.6초 → 16스레드 53.4초(3.2배)**.
🔑 그리고 **코어 수를 바꿔도 결과가 완전히 같은지**를 테스트가 검사한다. 안 그러면
노트북에서 만든 후보와 서버에서 만든 후보가 **다른 물건인데 둘 다 «같은 설정»이라고 적히고**,
나중에 나란히 재도 원인을 못 가린다.

> ⬜ **GPU는 안 쓴다.** 서버를 빌린다면 보는 것은 **코어 수와 지속 전력**이지 GPU가 아니다.
> 노트북이 3.2배에서 멈춘 것도 코어 수가 아니라 **35 W 전력 한계** 때문이었다.

### ② 진짜 오래 걸리는 것 — **말뭉치와 사람**

| 무엇 | 크기 / 양 | 비고 |
|---|---|---|
| 말뭉치 내려받기 | **21 GB(압축)** → 푼 것 **47.5 GB · 195,000 파일** | 디스크 **80 GB** 필요 |
| ✅ AI Hub | 29.6 GB · 108,808 파일 | 스크립트가 못 받아 **사람이 받았다.** 🆕 **2026-09-22 — 이미 들어와 있다** |
| 🔴 **사람 목소리** | **20~30명** × 20~30회 | ⏳ **지금 6명** · 마감 **10/06** |

> ### 🔑 **임계 경로는 코드가 아니라 사람이다**
>
> 학습은 7분이고 파이프라인은 이미 다 됐다. **모자란 건 목소리뿐이고, 그건 당길 수가 없다.**
> 그래서 일정에서 이것 하나만 따로 본다.
>
> 🚨 **그리고 «몇 명»보다 «어떤 환경에서»가 중요하다** — 지금 6명이 **전부 «조용한 방»** 이다.
> 이대로 20명을 채우면 **«조용한 방에서 잘 되는 모델»을 한 번 더 만들게 된다.**
> 남은 인원은 **노트북 마이크 · 떨어진 거리 · 시끄러운 곳**이 섞이는 쪽이 값이 나간다.


바꾸려면 `--replace-runtime` 을 **명시해야** 하고, 그건 §7의 판정을 통과한 뒤에나 쓴다.

> ⚠️ **다만 이번 후보는 «최종»이 아니라 «자를 한 번 통과시켜 보는 것»이다.**
> 녹음이 **6명**이고 **전부 «조용한 방»** 이라서다. 그리고 녹음이 더 들어오면
> **`ingest_wakeword.py` 를 다시 돌려야** `.npy` 에 반영된다(지금 파일은 9/16자다).
>
> 🔑 **이 순서가 원래 계획 그대로다** — ① 노트북에서 후보 하나 만들고 → ② 재 보고 무엇을
> 바꿀지 정한 다음 → ③ 그때 서버를 잡는다. **20~30명을 다 모을 때까지 기다리는 게 아니다.**

## 7. ⚖️ «좋아졌다»를 어떻게 판정하나 — **여기서 틀리기 쉽다**

### 🚨 같은 «임계»에서 비교하면 **결론이 뒤집힌다**

예행에서 실제로 겪었다. 같은 두 모델을 **임계 0.80 한 지점**에서만 보면:

| 임계 0.80에서만 보면 | 현행 | 새 후보 | |
|---|---|---|---|
| 놓침 | 19.2% | **6.7%** | ← «개선!» 이라고 적게 된다 |
| 오탐 / 시간 | 133.6 | **243.7** | ← 그런데 오탐이 **2배 늘었다** |

**오탐을 같은 값에 맞춰 놓고** 놓침을 비교하면 이렇게 된다:

| 오탐/시간을 맞추면 | 현행 | 새 후보 | 누가 낫나 |
|---|---|---|---|
| ≈ 244 | 8.7% | **6.7%** | 새 후보 |
| ≈ 204 | 9.6% | **7.7%** | 새 후보 |
| **≈ 130** | **19.2%** | 23.1% | 🔴 **현행** |

🔑 **우리가 필요한 쪽은 오탐이 낮은 쪽(목표 ≤ 1회)인데, 거기서는 새 후보가 낫지 않다.**
**임계를 하나 고르면 어느 쪽이든 이기게 만들 수 있다 — 그건 비교가 아니다.**

### 🔒 그래서 되돌림 기준을 **미리** 정해 뒀다

- 같은 오탐/시간에서 **놓침이 현행보다 나쁘면 되돌린다**
- **오탐이 현행보다 나쁘면 즉시 되돌린다**
- 🔑 **코드가 이 순서를 강제한다** — 학습 결과는 `wakeword_model_candidate.npz` 에만 저장되고,
  실제 교체는 `--replace-runtime` 을 **명시해야** 일어난다

## 8. ❓ 자주 헷갈리는 것

| 질문 | 답 |
|---|---|
| **«놓침»이 16%야 80%야?** | **둘 다 맞다. 다른 걸 잰다.** 녹음 재생 16% · 실제 방 80%(→50%). 발표엔 **나쁜 쪽**을 쓴다 |
| **GPU 서버 필요한가?** | ❌ **필요 없다.** 학습하는 게 15만 파라미터 분류기 하나라 CPU로 7~45분. 서버를 빌린다면 **코어 수** 때문이지 GPU 때문이 아니다 |
| **그냥 상용(Porcupine)을 쓰면?** | 성능은 이길 수 있지만 **블랙박스라 캡스톤 기여가 사라진다.** 게다가 2026-09-21에 **가입 자체가 막혔다** — 회사 메일을 요구해 **학교 메일도 거절**됐다 |
| **더 좋은 모델로 바꾸면?** | 바꿀 수 있는 건 ①②(백본)인데 **거기가 문제가 아니다.** 엔진 7종을 조사했지만 **«학습을 피하는 길»이 목록 전체에 없었다** |
| **얼마나 좋아지나?** | 🚫 **약속하지 않는다.** 목표는 적었지만 **이 방·이 마이크에서 도달 가능한지는 아직 못 쟀다.** 그래서 **되돌림 기준을 먼저** 정했다 |
