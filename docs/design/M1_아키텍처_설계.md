> **작성일**: 2026-07-30
> **상태**: 제안 (Proposed) — 사용자 승인 대기
> **범위**: 맥락 처리 근본 해결 + 최종 구조 확정. "마지막 아키텍처 정리" 기회로 삼음.

## 1. 배경 & 문제 정의 (Problem Definition)

### 1.1 증상
"메모장 켜줘" 다음 "그거 꺼줘" 같은 **맥락 기반 후속 명령이 실패**한다. 첫 문장에 모든 정보가
담긴 단발성 명령만 안정적으로 동작한다.

### 1.2 근본 원인 진단 (Root Cause — 코드 근거)
과거 노트(7.6)는 원인을 "`astream` 호출 시 `thread_id`(config) 누락"으로 지목했으나,
**현재 코드와 불일치**한다. 실제 코드 근거는 다음과 같다.

- `run_async`/`stream` 모두 config에 thread_id 전달 중
  (`core/agent.py:320, 328, 659`).
- UI는 세션당 thread_id를 1회 생성해 재사용
  (`electron-ui/renderer/index.html:1252` → `1709, 1736`에서 재사용).
- 따라서 **thread_id는 세션 내내 일관**되며 원인이 아니다.

**진짜 원인**: LLM 앞단의 빠른 경로(커맨드 캐시 · 결정론적 라우터)가 명령을 처리한 뒤
`graph.ainvoke`를 거치지 않고 즉시 `return` 한다.

```
core/agent.py:296~301   cache.execute(entry) → return result_text   # 그래프 미경유
core/agent.py:307~309   _route_deterministic → return route_result  # 그래프 미경유
```

그 결과 캐시/라우터로 처리된 명령은 **LangGraph 대화기록(MemorySaver)에 누적되지 않는다.**
LLM은 자신이 본 적 없는 "메모장"을 이후 "그거"로 지칭당하니 맥락을 복원할 수 없다.

- 보조 요인: `memory/session.py`(SQLite)는 모든 대화를 저장하지만 **UI 표시·통계용**일 뿐
  LLM 입력으로 되먹임되지 않는다. 즉 맥락 복원에 기여하지 못한다.

> **핵심 통찰**: 맥락 버그는 "설정 누락"이 아니라 **구조적 결함**이다.
> 성능을 위한 다층 우회 경로와 대화기억이 **단일 상태로 통합되어 있지 않은 것**이 원인이다.
> → 미봉책(캐시 결과를 기억에 수동 append)으로도 고칠 수 있으나,
>   이번 마일스톤의 목표상 **구조를 통합**하여 근본 해결하는 편이 맞다.

## 2. 현행 아키텍처 평가 (As-Is Assessment)

### 2.1 강점 (유지할 것)
- **오프라인 우선(offline-first)**: 캐시·라우터로 API 없이 즉시 실행 → 저지연·저비용·오프라인 대응.
- **다층 방어**: 보안 필터(코드 레벨) → 캐시 → 라우터 → LLM. 실무적으로 견고.
- **의존성 관리**: 도구 31개가 `tool_registry` 한 곳에 등록, provider 추상화(`_build_llm`) 존재.
- **방어적 코딩**: 히스토리 오염 복구, 네트워크 오류 안내, 도구 결과 검증(T04) 등.

### 2.2 약점 / 한계 (개선 대상)
| # | 문제 | 영향 |
|---|------|------|
| A | 빠른 경로가 대화기억에 누적 안 됨 | **맥락 붕괴** (본 마일스톤 핵심) |
| B | 흐름 제어가 `if/return`으로 분산 (agent.py 700줄) | 가독성·테스트·확장성 저하 |
| C | 캐시 매칭이 `SequenceMatcher` 문자열 유사도 | 표현 변형에 취약, 오매칭 위험 |
| D | 위험 명령 "승인"이 프롬프트 부탁뿐 (강제력 없음) | Excessive Agency 위험 |
| E | 입력 보안만 존재, 출력/인젝션/민감정보 방어 없음 | OWASP 미대응 |
| F | 도구가 subprocess/ctypes 직접 구현 (Windows 결합) | 이식성·유지보수 부담 |
| G | 문자열 파싱(split/strip)으로 도구 결과 처리 | 구조화 부재, 취약 |

## 3. 목표 아키텍처 (To-Be) — 명시적 LangGraph StateGraph

`create_react_agent` + 수동 전처리(if/return)를 **하나의 명시적 상태 그래프**로 재구성한다.
모든 경로가 **단일 상태(messages)** 를 공유·갱신하므로 맥락이 근본적으로 통합된다.

### 3.1 노드 구성 (제안)

```
          ┌──────────────┐
  입력 →  │ input_guard  │  OWASP LLM01/02: 인젝션·민감정보·위험명령 차단
          └──────┬───────┘
                 │ (통과)
          ┌──────▼───────┐
          │  fast_path   │  intent/캐시(벡터) + 결정론적 라우터
          └──────┬───────┘
        (hit)     │        (miss)
     ┌────────────┴──────────────┐
     ▼                           ▼
┌──────────┐              ┌──────────────┐
│  tools   │◄─────────────│    agent     │  LLM ReAct 추론
└────┬─────┘   (tool_call) └──────┬───────┘
     │                            │
     ▼                            ▼
┌──────────────┐          ┌──────────────┐
│    hitl      │  위험 op → interrupt 승인 (LLM06)
└──────┬───────┘          └──────────────┘
       ▼
┌──────────────┐
│ output_guard │  OWASP LLM05 + reflection: 도구오류·환각 검증 후 응답
└──────┬───────┘
       ▼  END
```

- **input_guard**: 현 `security.py` 로직을 노드로. + 프롬프트 인젝션·민감정보 필터 추가.
- **fast_path**: 캐시/라우터를 **노드**로 이동. 히트 시에도 결과를 `state.messages`에 기록
  (AIMessage/ToolMessage로) → **모든 경로가 동일하게 맥락에 누적** (문제 A 근본 해결).
- **agent / tools**: LangGraph 표준 ReAct(에이전트↔ToolNode 루프).
- **hitl**: 삭제 등 위험 도구 호출 전 `interrupt()`로 사람 승인 (문제 D).
- **output_guard**: T04를 정식 reflection 노드로 승격 + 출력 검증 (문제 E, G).

### 3.2 상태 & 영속성
- `MessagesState` 확장(단일 `messages` + 필요 시 `pending_approval` 등 플래그).
- 단일 `checkpointer`(MemorySaver → 추후 SqliteSaver로 교체 시 **장기기억**까지 확장 가능).
- 이로써 `memory/session.py`의 이중 저장 문제(표시용/LLM용 분리)를 정리.

### 3.3 선택한 강의 개념의 배치
| 개념 | 배치 |
|------|------|
| LangGraph State/Node/Edge (Lab14) | 전체 파이프라인의 골격 |
| HITL (Lab19) | `hitl` 노드 (interrupt 승인) |
| OWASP Guardrail (Day5) | `input_guard` + `output_guard` 노드 |
| 벡터 캐시 (RAG, Lab10~12) | `fast_path`의 매칭을 임베딩 유사도로 |
| Reflection/Self-RAG (Lab21~24) | `output_guard`의 자가검증 |
| OutputParser/Pydantic (Lab06) | 도구 결과·라우팅 구조화 |

## 5. 단계별 구현 계획 (Phased Plan — SDLC 증분)

각 단계 = **설계 노트 → 구현 → 검증 → DEVLOG 기록**, 그리고 **수정 전 사용자 보고·승인**.

| Phase | 목표 | 산출물 | 검증 |
|-------|------|--------|------|
| **P0** (현재) | 진단 + 설계 확정 | 본 문서 | 사용자 승인 |
| **P1** | 맥락 근본 해결 = 그래프 골격 도입 | StateGraph(input_guard→fast_path→agent→tools→output_guard), 통합 memory | 후속 명령 맥락 테스트(캐시→후속) 통과 |
| **P2** | HITL 승인 흐름 | `hitl` 노드 + interrupt, UI 승인 처리 | 위험 명령 승인/거부 시나리오 |
| **P3** | OWASP 가드레일 강화 | input/output_guard: LLM01/02/05/06 | 인젝션·민감정보·오류출력 차단 케이스 |
| **P4** | 벡터 캐시 매칭 | 오프라인 임베딩 유사도 매칭 | 표현 변형 매칭 정확도 벤치 |
| **P5** (선택) | MCP 도구층 PoC + provider 품질 티어링 | 도구 1건 MCP화, 모델 선택 정책 | 통합/회귀 |

> P1이 "맥락 버그부터"라는 시작 지시와 "그래프 재설계"를 동시에 만족한다.
> 각 Phase는 독립적으로 배포 가능하며, 문제 시 이전 Phase로 롤백 가능.

## 6. 리스크 & 한계 (Risks & Limitations — 도메인 이해)

- **지연 예산(latency)**: 음성 UX 특성상 응답이 빨라야 함. 그래프 노드·가드레일·임베딩이
  지연을 추가함 → 빠른 경로(fast_path)를 반드시 유지하고, 가드레일은 경량 규칙 우선·LLM 판정 최소화.
- **오프라인 제약 vs 클라우드**: 벡터 임베딩·LLM 판정형 가드레일은 온라인 의존.
  → 오프라인에선 로컬 임베딩(sentence-transformers 등)·규칙 기반으로 **graceful degrade** 설계.
- **저사양 메모리**: 로컬 임베딩/로컬 LLM(Qwen·Gemma 조사분)은 RAM 부담.
  → 선택적 활성화, 기본은 경량 경로.
- **Windows 결합·테스트 한계**: PC 제어 도구는 Windows 전용이라 Linux CI에서 통합 테스트 불가.
  → 순수 로직(가드레일·라우팅·캐시)은 모델 목(mock)으로 단위 테스트, 도구는 Windows 수동/통합 테스트로 분리.
- **LLM 비결정성·도구 신뢰성**: reflection/output_guard로 실패를 성공처럼 응답하는 위험 차단.
- **MCP 생태계 성숙도**: 로컬 제어 MCP 서버 품질·보안 편차 → PoC로 검증 후 도입 판단.

## 7. 확장성 & 유지보수 전략 (Extensibility & Maintainability)

- **도구 추상화**: 도구를 "직접 구현 / MCP 서버" 어느 쪽이든 동일 인터페이스로 등록 →
  향후 subprocess 도구를 MCP로 무중단 교체 가능.
- **provider 추상화 유지·강화**: 작업 난이도에 따라 모델 티어링(경량=Gemini Flash / 복잡=상위 모델).
- **설정 주도(config-driven)**: 가드레일·캐시·임베딩 on/off를 `.env`/settings로 토글.
- **테스트 피라미드**: 단위(순수 로직, Linux) → 통합(Windows) → 회귀(`test_regression.py` 확장).
- **문서화**: 본 ADR + DEVLOG 누적으로 의사결정 이력 추적 가능(감사성).
