## 1. 무엇을 만드는가

> 사용자: *"블루투스 설정 어디 있어?"*
> Pluiz: *"화면에 표시했어요."* → **화면의 그 자리에 고리가 그려진다.**

`click_ui_element`가 **대신 눌러 주는** 것이라면, 포인팅은 **사용자가 직접 하게
돕는** 것이다. 접근성 보조 성격이라 **범용 에이전트가 대체하지 않는 자리**이고,
그래서 [ROADMAP](../ROADMAP.md)이 클라우드 동기화를 버리고 이걸 택했다.

### 1-1. 왜 싼가 — 새로 만드는 건 «그리는 창» 하나뿐이다

| 필요한 것 | 이미 있나 | 어디 |
|---|---|---|
| 화면에서 요소를 찾아 **화면 좌표**를 주는 함수 | ✅ | `locate_ui_element` (`tools/vision.py`) — `center`·`rect`·`size`·`label`·`window_rect` |
| 서버가 **먼저 말을 거는** 통로 | ✅ | 화면 감시 알림이 쓰는 WebSocket push (`core/screen_monitor._dispatch` → `main.py` → 렌더러) |
| always-on-top 투명 창 | ✅ | `electron-ui/main.js`의 `mainWindow` — **단 이건 못 쓴다**(§3-3) |
| **전체 화면을 덮는 클릭 통과 오버레이** | ❌ | **이것만 새로 만든다** |

---

## 2. 승인이 필요 없다 — 다만 «공짜»는 아니다

포인팅은 **아무것도 바꾸지 않는다.** 되돌릴 것이 없으므로 HITL 승인을 붙이지 않는다.
[절대규칙 9](../../CLAUDE.md)가 클릭에 좌표 인자를 금지한 이유(*되돌릴 수 없다*)가
여기엔 해당하지 않는다.

**그러나 화면 한 장이 외부 LLM으로 나간다.** `find_ui_element`와 **정확히 같은 비용**이고
새로 늘어나는 것이 아니다(같은 `locate_ui_element`를 부른다). 그래서 프라이버시
서사는 바뀌지 않지만, [ARCHITECTURE](../ARCHITECTURE.md)의 «화면을 외부 LLM에 전송»
목록에 이 도구도 **반드시 들어가야 한다.** 목록에서 빠지면 전송 도구가 조용히 하나 는다.

## 3. 설계 — 세 조각

### 3-1. 도구 하나: `point_at_element(target, window="", zoom=False)`

```
point_at_element("블루투스", window="설정")
  → locate_ui_element(...)          # find_ui_element와 **같은 경로**
  → 못 찾으면: 아무것도 그리지 않고 "찾지 못했다"                 (§4-3)
  → 찾으면:   dispatch({"type": "point", rect, label, zoom})
  → "'블루투스'를 화면에 표시했어요. (화면을 보고 추정한 위치예요)"
```

⚠️ **좌표를 인자로 받지 않는다.** `click_ui_element`가 `(target, window)`만 받는 것과
같은 이유다([절대규칙 9](../../CLAUDE.md)) — LLM이 좌표를 넘길 수 있으면 언젠가
지어내고, 포인팅에서 그건 **«틀린 곳을 자신 있게 가리키는» 도구**가 된다.

⚠️ **`zoom`은 bool이다.** 배율·영역을 인자로 열면 같은 문제가 생긴다.

### 3-2. 전달: 기존 WebSocket push를 그대로 쓴다

화면 감시 알림(`{"type": "notify"}`)이 **이미 서버→UI 단방향 통로**를 뚫어 놨다.
새 통로를 만들지 않고 `{"type": "point"}` 한 종류를 더한다.

```
tools/vision.point_at_element  →  _dispatch  →  main.py websocket  →  렌더러 switch
                                                                    →  ipcRenderer → main.js
```

⚠️ **렌더러를 거쳐 main 프로세스로 간다.** 창을 만드는 건 main 프로세스만 할 수 있고,
렌더러는 이미 그 WebSocket을 듣고 있다. 통로를 하나로 유지하는 편이 낫다 —
서버가 Electron main과 직접 말하는 두 번째 채널을 만들면 토큰·수명 관리가 두 벌이 된다.

### 3-3. Electron: **두 번째 창**을 만든다 (`mainWindow`를 쓰지 않는다)

`mainWindow`는 `width×height`가 정해진 **작은 대화 창**이고 `movable: true`다.
이걸 전체 화면으로 늘렸다 줄이면 **채팅 UI가 매번 튀고**, 사용자가 옮겨 둔 위치를 잃는다.

```js
pointerWindow = new BrowserWindow({
  ...screen.getPrimaryDisplay().bounds,   // 전체 화면
  frame: false, transparent: true,
  alwaysOnTop: true, skipTaskbar: true,
  focusable: false,        // ★ 포커스를 절대 뺏지 않는다
  show: false,
});
pointerWindow.setIgnoreMouseEvents(true, { forward: true });   // ★ 클릭 통과
pointerWindow.setAlwaysOnTop(true, 'screen-saver');
```

**`focusable: false`와 `setIgnoreMouseEvents`가 이 기능의 존재 조건이다.** 둘 중
하나라도 빠지면 **가리키려던 버튼을 우리가 덮어서 못 누르게 된다** — 도우려다
방해하는, 이 기능 최악의 실패다(§4-1).

## 4. ⚠️ 이 기능이 실패하는 세 가지 방식

**설계의 대부분이 여기에 있다.** 그리는 것 자체는 쉽다.

### 4-1. 포인터가 클릭을 가로챈다

전체 화면 always-on-top 창은 **기본적으로 화면 전체의 클릭을 먹는다.**
사용자는 «여기 있어요» 표시를 보고 눌렀는데 아무 일도 안 일어난다.

→ `focusable: false` + `setIgnoreMouseEvents(true, {forward:true})`.
→ **회귀 테스트로 못 잡는다.** mock은 배선만 보증한다 —
   [수동 테스트](../testing/MANUAL_TESTS.md)에 *"표시된 버튼을 실제로 눌러 본다"* 를 넣는다.

### 4-2. 안 사라진다

always-on-top 전체 화면 오버레이가 남으면 **화면을 영구히 덮는다.**
없느니만 못한 정도가 아니라 **PC를 못 쓰게 만든다.** 해제를 세 겹으로 둔다.

| | 해제 조건 | 왜 |
|---|---|---|
| ① | **8초 뒤 자동** | 아무도 아무 말 안 해도 사라진다. 마지막 방어선 |
| ② | **다음 턴이 시작될 때** | 새 명령을 내렸으면 이전 표시는 낡았다 |
| ③ | *"그만"* · 오버레이 클릭 | 사용자가 직접 |

> ⚠️ ①을 «사용자가 끄면 되니까»로 빼지 말 것. 화면 감시가 **어떤 이유로 멈추든
> 반드시 알린다**([BL-22](../BACKLOG.md))로 간 것과 같은 자리다 —
> **조용히 남는 경로를 만들지 않는다.**

### 4-3. 🚨 틀린 곳을 **자신 있게** 가리킨다 — 가장 위험하다

`find_ui_element`는 오늘 *"(화면을 보고 추정한 위치예요)"* 라는 **문장으로 단서를
단다.** 그런데 **화면에 그려진 사각형에는 단서가 없다.** 정확해 보인다.

Vision이 틀리면 사용자는 그 자리를 보고, 없고, **자기가 잘못 본 줄 안다.**
텍스트로 틀리는 것보다 나쁘다 — 그림이 더 권위 있게 보이기 때문이다.
[절대규칙 9](../../CLAUDE.md)가 클릭에서 막은 *"틀린 좌표를 정확히 클릭한다"* 의
**포인팅판**이다.

**세 가지로 막는다:**

1. **못 찾으면 아무것도 그리지 않는다.** 오버레이를 띄우지도 않는다.
   `locate_ui_element`가 이미 «없으면 지어내지 않는다»를 보증한다.
2. **정밀한 사각형을 그리지 않는다 — 고리(halo)를 그린다.**
   `rect`에 딱 맞는 테두리는 **가지지 않은 정밀도를 주장한다.** 중심 주변의
   부드러운 고리는 *"이 근처"* 라고 말한다. **표현이 확신의 정도와 일치해야 한다.**
3. **라벨을 표시에 붙여 보낸다** — `『블루투스』 여기인 것 같아요`.
   단서가 문장에만 있으면 화면을 보는 동안에는 안 보인다. **단서가 그림과 같이
   움직여야 한다.**

## 5. 🚨 우리 표시가 우리 눈에 찍힌다 — 설계 중 발견

**문서 어디에도 없던 충돌이고, 안 다루면 두 기능이 동시에 깨진다.**

전체 화면 always-on-top 창은 **스크린샷에 그대로 찍힌다.** 그래서:

| 무엇이 깨지나 | 어떻게 |
|---|---|
| `describe_screen` · `find_ui_element` · `visual_verify` | 캡처에 **우리 고리가 들어가** Gemini가 그걸 화면의 일부로 읽는다. 최악은 **자기가 그린 표시를 UI 요소로 되짚는** 것이다 |
| `watch_screen` | 프리필터가 **로컬 픽셀 비교**다. 오버레이가 뜨고 지는 것 자체가 **화면 변화**라 «변화 감지 → Vision 호출»이 돈다. **우리가 우리를 감시한다** |

두 번째가 특히 나쁘다 — 화면 감시는 **변화가 있을 때만 화면을 내보내는 것**이
설계의 핵심(전송량 방어)인데, 포인팅이 그 방어를 헛되게 만든다.

### 결정 — 서버가 «표시 중»을 알고 캡처를 막는다

포인팅을 띄우는 것도, 화면 감시를 도는 것도 **같은 서버 프로세스**다.
그래서 상태 하나로 해결된다.

```
pointer_visible_until : float      # 표시가 사라지는 시각(monotonic)
```

- **캡처 계열 도구**는 시작할 때 이 시각까지 **기다렸다가** 찍는다(최대 8초).
  «표시를 지우고 찍는» 것이 아니라 **표시가 끝나기를 기다린다** — 지웠다 다시
  띄우면 사용자 화면이 깜빡이고, 그 깜빡임이 또 변화로 잡힌다.
- **화면 감시 프리필터**는 이 구간의 프레임을 **비교에서 제외**한다.
  «변화 없음»으로 치는 게 아니라 **직전 기준 프레임을 유지**한다 —
  오버레이가 낀 프레임을 기준으로 삼으면 **사라질 때 또 변화로 잡힌다.**

> ⚠️ `setContentProtection(true)`(Windows에서 캡처 제외)를 **1차 수단으로 쓰지 않는다.**
> 동작이 Windows 버전에 따라 «제외»와 «검은 사각형»으로 갈리고, **검은 사각형이면
> 아무것도 해결되지 않는다**(오히려 화면 한복판에 검은 상자가 찍힌다).
> 위 상태 기반 방어를 먼저 넣고, 이건 **실측한 뒤에만** 덧붙인다.

## 6. 확대(zoom) — 같은 자산의 두 번째 얼굴

`zoom=True`면 고리 대신(또는 함께) **그 영역을 확대한 그림**을 오버레이에 띄운다.

- 원본은 **이미 찍어 둔 캡처**다. `locate_ui_element`가 캡처한 그 파일에서
  `rect` 주변을 잘라 3~4배로 키운다. **화면을 다시 찍지 않는다** —
  다시 찍으면 그 사이에 뜬 우리 오버레이가 들어간다(§5).
- 확대본은 오버레이 **가장자리**에 띄운다. 가리키려는 자리를 확대본이 덮으면
  §4-1과 같은 실패다.
- 접근성이 목적이므로 **배율은 고정**한다. 사용자가 조절하는 UI를 만들지 않는다 —
  2주 안에 포인팅을 제대로 만들려고 버린 것들이 있다([TASKS](../TASKS.md)).

## 7. 안 하는 것

- **여러 요소 동시 표시** — *"버튼들 다 표시해 줘"*. `locate_ui_element`가 하나만
  돌려준다. 여러 개를 그리면 «어느 게 그거냐»가 되어 도움이 안 된다.
- **따라다니는 포인터** — 창이 움직이면 표시도 따라가기. 좌표를 계속 다시 구해야 하고
  (Vision 호출 반복 = 화면 반복 전송) 8초짜리 표시에 값어치가 없다.
- **보조 모니터** — [BL-18](../BACKLOG.md)로 Vision이 **주 모니터만** 본다.
  좌표가 주 모니터 것이므로 오버레이도 주 모니터에만 띄운다. ⚠️ BL-18이 풀리기 전에
  보조 모니터로 넓히면 **틀린 화면에 그린다.**
- **클릭 유도** — *"거기 눌러 드릴까요?"* 를 자동으로 붙이지 않는다. 포인팅의 값어치는
  **사용자가 직접 하는 것**이고, 클릭이 필요하면 `click_ui_element`가 따로 있다.

## 8. 구현 단계

1. **순수 함수** (`tools/vision.py`) — `point_payload(loc, zoom) -> dict | None`.
   못 찾으면 `None`. 그래프·Electron 없이 테스트한다
2. **도구** `point_at_element` + `_dispatch` 배선 · 도구 목록 등록(39 → 40)
3. **서버 상태** `pointer_visible_until` + 캡처 대기 · 감시 프리필터 제외 (§5)
4. **Electron** — `pointerWindow` 생성 · `point` 메시지 처리 · 해제 3겹 (§4-2)
5. **확대** (§6) — 3까지 동작한 뒤에 붙인다
6. **문서** — ARCHITECTURE 도구표·전송 목록 · MANUAL_TESTS · TASKS · DEVLOG

> 망가져 있었다([BL-23](../BACKLOG.md)). 같은 실수를 여기서 반복하지 않는다.

## 9. 되돌리기

`point_at_element`를 도구 목록에서 빼면 끝난다 — LLM이 부를 수 없으면
오버레이 창은 만들어지지 않는다. Electron 쪽 코드는 남아 있어도 죽은 코드다.
§5의 캡처 대기는 `pointer_visible_until`이 항상 과거라 **자동으로 무해**해진다.
