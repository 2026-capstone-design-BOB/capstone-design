# BL-24 — 위험 호출이 **둘**일 때의 승인

> 📍 [문서 허브](../README.md) · 백로그 [BL-24](../BACKLOG.md) · 관련 [BL-20 ADR](BL-20_거부후_안전호출.md)
> **상태: ✅ 구현 완료** (2026-09-10) · `test_hitl_graph` **88 → 114**

**한 줄:** 배치에 위험 호출이 둘 있으면 질문은 **하나**만 나가고 승인하면 **둘 다** 실행된다.
질문이 **전부를 이름으로 부르게** 하고, 실행 가능한 집합을 **재발행으로 못 박는다.**

---

## 1. 문제

`hitl` 노드는 배치에서 **처음 걸린 위험 호출 하나**만 집는다.

```python
dcall = next((c for c in calls if c.get("name") in dangerous), None)
question = _confirm_question(dcall)          # ← 이 하나에 대해서만 묻는다
...
if verdict == "approve":
    return {"decision": "approved", ...}      # ← messages를 안 건드린다
```

승인하면 `tools` 노드(`ToolNode`)로 간다. 그런데 `ToolNode`는 **마지막 `AIMessage`의
`tool_calls`를 전부** 실행한다(BL-20에서 확인한 성질이다).

```
LLM:  [delete_file(a.txt), delete_file(b.txt)]
질문:  "'a.txt' 파일을 정말 삭제할까요?"
사용자: "네"
실행:  a.txt 삭제 ✓  b.txt 삭제 ✓   ← **b.txt는 승인한 적이 없다**
```

**사용자가 묻지 않은 삭제를 당한다.** 되돌릴 수 없고, 응답은 그 사실을 말하지 않는다.

> **왜 [즉시/위험]인가:** BL-20이 *"거부가 너무 넓다"* 였다면 이건 *"승인이 너무 넓다"* 다.
> **이쪽이 더 위험하다** — 넓은 거부는 «안 된 일»을 만들고, 넓은 승인은 **«되돌릴 수 없는 일»**
> 을 만든다. 절대규칙 9(«클릭 도구에 좌표를 주지 마라»)가 지키려는 것과 같은 자리다.

### 1-1. 왜 아직 사고가 안 났나

실기에서 관측된 적이 **없다.** 재현하려면 사용자가 *"a도 b도 지워줘"* 처럼
**둘을 명시**해야 하고, 계획 수립(M3)이 그런 명령을 보통 **단계로 쪼갠다.**
그래서 잠재 결함이지만, **터지면 되돌릴 수 없다.**

### 1-2. ⚠️ 「없는 대상」이 섞이면 지금도 새고 있다

`target_exists`는 `dcall` **하나만** 확인한다. 둘 중 하나가 없으면:

```
LLM:  [delete_file(없는것.txt), delete_file(있는것.txt)]
      → dcall = 없는것.txt → "찾을 수 없습니다"로 마감하고 **묻지 않고 끝난다**
      → 있는것.txt 는 마감만 되고 삭제되지 않는다
```

순서가 반대면(`있는것`이 먼저) **묻고, 승인하면 둘 다 실행**된다.
**같은 상황에서 배치 순서에 따라 결과가 달라진다.**

---

## 2. 현행 평가 — 쓸 수 있는 부품이 이미 있다

BL-20이 만든 **재발행 기계**가 그대로 답이 된다.

| 부품 | 하는 일 | BL-24에서의 쓸모 |
|---|---|---|
| `split_calls(calls, dangerous)` | (안전, 위험)으로 가른다 | **위험 목록 전체**를 얻는다 (지금은 `next()`로 하나만 본다) |
| `reissue_message(calls)` | 새 id로 다시 내보낸다 | **실행될 집합을 못 박는다** |
| `_close_calls(reason, hold_safe=)` | 매달린 호출을 마감 | 짝 불변식 유지(절대규칙 3) |
| `is_reissued(msg)` | 재발행분 표식 | 진행 근거를 두 번 세지 않는다(M3-1) |

> **BL-20의 교훈이 여기서도 그대로다:**
> *"조건문이 아니라 **메시지 모양**이 막는다."*
> 승인 후에 «이건 실행하고 저건 하지 마»를 조건문으로 거르려 하면, `ToolNode`가
> 그 조건을 안 본다. **마지막 `AIMessage`에 없으면 실행될 수 없다** — 그게 유일하게
> 믿을 수 있는 장치다.

---

## 3. 목표 구조

### 3-1. 질문이 **전부를 이름으로 부른다**

```
전:  "'a.txt' 파일을 정말 삭제할까요? (휴지통으로 갑니다)"
후:  "'a.txt' 파일과 'b.txt' 파일 2개를 정말 삭제할까요? (휴지통으로 갑니다)"
```

**한 번만 묻는다.** 위험 호출 수만큼 반복해서 묻는 안(§4-B)은 쓰지 않는다.

### 3-2. 승인해도 **물어본 것만** 실행된다

승인 분기가 **messages를 건드리지 않던 것**이 결함의 절반이다. 이제 건드린다:

```
approve → 원본 호출 **전부** 마감(짝 불변식)
        → [물어본 위험 호출 + 안전한 호출] 만 **새 id로 재발행**
        → ToolNode는 재발행분만 볼 수 있다
```

**«묻지 않은 것은 재발행되지 않으므로 실행될 수 없다».** 조건문이 아니라 구조다.

### 3-3. 없는 대상은 **묻는 목록에서 빠진다**

위험 호출을 **각각** `target_exists`로 확인한다.

| 상황 | 동작 |
|---|---|
| 전부 없음 | 묻지 않는다. `not_found` (오늘과 같다) |
| 일부만 없음 | **있는 것만 묻는다.** 없는 것은 «찾을 수 없습니다»로 마감하고 **재발행하지 않는다** |
| 전부 있음 | 전부 묻는다 |

> 이것이 §1-2의 «배치 순서에 따라 결과가 달라진다»를 없앤다.
> **응답은 두 가지를 다 말해야 한다** — 지운 것과, 없어서 못 지운 것.

### 3-4. 거부 경로는 **그대로 둔다**

BL-20이 이미 옳게 처리한다 — 위험한 것 전부 취소, 안전한 것만 재발행.
거부는 «위험한 것 하나에 대한 판단»이 아니라 **«물어본 것 전체에 대한 판단»** 이 되는데,
질문이 전체를 이름으로 불렀으므로 그게 맞다.

## 4. 대안 비교

| | A. 위험 호출 수만큼 **반복 질문** | **B. 한 번에 묶어 묻기 + 재발행** ⭐ | C. 배치를 통째로 거부 |
|---|---|---|---|
| 묻지 않은 실행 | 없다 | **없다** | 없다 |
| 부분 승인 | ✅ 가능 | ❌ 전부 또는 전무 | ❌ |
| 대화 횟수 | 위험 호출 수만큼 | **1회** | 0회 |
| 구현 크기 | 중 (interrupt 루프 + 상태) | **작다** (부품이 이미 있다) | 작다 |
| 위험 | 승인 피로 → 습관적 «네» | 목록이 길면 안 읽는다 | **정상 명령이 막힌다** |

**A를 버리는 이유:** 부분 승인은 **이 제품에서 쓸 일이 거의 없다.**
*"a도 b도 지워줘"* 라고 말한 사용자가 «a만»을 원하는 경우를 상정하는 것인데,
그러려면 사용자가 애초에 그렇게 말했을 것이다. 대신 **승인 피로**라는 실재하는 비용이
생긴다 — 두 번 세 번 물으면 읽지 않고 «네»를 누르게 되고, 그건 승인 절차 전체를
무력화한다. `_MAX_CONFIRM_ASKS = 2`로 재질문을 2회로 묶어 둔 것과 같은 판단이다.

**C를 버리는 이유:** *"a랑 b 지워줘"* 는 **정상 명령**이다. 막으면 기능이 준다.

> ⚠️ **A를 «나중에»로 남긴다.** 위험 도구가 늘어나(예: 이메일 전송) 부분 승인이
> 실제로 필요해지면 그때 다시 본다. 지금 넣으면 쓰지 않을 복잡도만 는다.

---

## 5. 결정

> **B — 질문이 위험 호출 «전부»를 이름으로 부르고, 승인 시 «물어본 것만»
> 재발행해 실행한다.** 없는 대상은 각각 걸러 묻는 목록에서 뺀다.
> 거부 경로(BL-20)는 손대지 않는다.
>
> 부분 승인은 **하지 않는다**(§4-A). 승인 피로가 승인 절차 자체를 무력화한다.

## 6. 단계별 계획

### 6-1. 질문 문구 — 여러 대상을 부른다
- `_confirm_question(dcall)` → `_confirm_question(dcalls: list)`.
  1개면 **오늘과 글자 그대로 같은 문장**을 낸다(회귀 방지의 핵심)
- 2개 이상: `'a.txt' 파일과 'b.txt' 파일 2개를 정말 삭제할까요? (…)`
- 3개 이상: `'a.txt' 외 2개 파일을 정말 삭제할까요? (…)` — 문장이 길어지면 안 읽는다
- ⚠️ **섞여 있으면**(파일+폴더, 삭제+클릭) 종류별로 나눠 말한다.
  「휴지통으로 갑니다」가 클릭에는 거짓이 되므로, 클릭이 섞이면 **각각의 결과**를 말한다
- 테스트: 1개일 때 기존 문구와 **완전 일치**

### 6-2. `hitl` — 위험 호출을 전부 본다
- `dcall = next(...)` → `_, risky_calls = split_calls(calls, dangerous)`
- `target_exists`를 **각 호출에** 적용 → `askable` / `missing`으로 가른다
- `missing`이 있고 `askable`이 비면 → 오늘의 `not_found` 경로
- 테스트: §1-2의 «배치 순서에 따라 결과가 달라진다»가 사라지는지

### 6-3. 🔒 승인 분기 — **재발행으로 못 박는다** (이 ADR의 핵심)
```python
if verdict == "approve":
    approved = reissue_message(askable + safe_calls)
    if approved is None:                     # 살릴 게 없으면 오늘과 같다
        return {"decision": "approved", "deletion_cancelled": False}
    msgs = _close_calls("승인 절차로 보류됐습니다. …", hold_safe=True)
    msgs.append(approved)
    return {"messages": msgs, "decision": "approved", "deletion_cancelled": False}
```
- ⚠️ **`missing`은 재발행에 넣지 않는다.** 넣으면 없는 파일을 지우려 든다
- ⚠️ 재발행분은 `is_reissued` 표식이 붙어 `turn_tool_call_count`가 **세지 않는다**.
  M3-1의 «못 한 단계 보고»가 조용해지지 않는지 확인한다(BL-20 §5와 같은 자리)
- 테스트: 위험 2개 중 1개만 물었을 때 **나머지가 실행되지 않는지**
  (mock `ToolNode`가 «마지막 AIMessage의 tool_calls»를 그대로 실행하도록 둔다)

### 6-4. 응답 — **없어서 못 지운 것을 말한다**
- `missing`이 있으면 그 사실이 응답에 남아야 한다. 조용히 빠지면
  이 저장소가 반복해서 데인 **«안 한 걸 말하지 않는 것»** 이 된다
- ⚠️ `deletion_cancelled` 플래그를 쓰지 않는다 — 그건 «거부»의 뜻이고 여기선 거부가 아니다

> ### 🚨 구현 중에 한 번 틀렸다 — **재발행 뒤에는 아무것도 오면 안 된다**
>
> 처음엔 «못 지운 것»을 재발행 **뒤에** `AIMessage`로 붙였다.
> 그러자 **그게 마지막 `AIMessage`가 돼서 `ToolNode`가 도구를 못 봤다** —
> 승인했는데 **아무것도 실행되지 않았다.** (테스트가 잡았다)
>
> **BL-20 §3-4가 «거부 사실은 문구가 아니라 플래그로»라고 한 것과 같은 이유였다.**
> 그때는 «접두 문구를 붙이면 output_guard가 두 번 말한다»가 이유였고,
> 이번엔 «메시지 순서가 실행을 결정한다»가 이유다. **결론이 같다.**
>
> 그래서 구현은 이렇게 됐다:
> - `missing_targets: list[str]` 상태 필드 + `missing_notice()` **접미**
>   (M3의 «못 한 단계» 접미와 같은 자리)
> - 원본 호출은 전부 마감하되 **사유는 호출마다 다르다** —
>   없는 것에 «이어서 실행됩니다»라고 적으면 거짓이 된다
> - 재발행 `AIMessage`가 **반드시 마지막**이다

## 7. 위험과 한계

| 위험 | 대응 |
|---|---|
| 1개일 때 문구가 미묘하게 바뀌어 **기존 승인 테스트가 깨진다** | 6-1에서 «1개면 완전 일치»를 테스트로 고정 |
| 목록이 길면 안 읽고 «네» | 3개 이상은 «외 N개»로 줄이고, **개수를 반드시 말한다** |
| 재발행이 `visual_verify`의 id 규약과 부딪힌다 | BL-20이 이미 «새 id» 규약을 세웠다. 같은 함수를 쓴다 |
| 부분 승인이 **정말로** 필요해지는 날 | §4-A를 다시 연다. 지금 넣지 않는 이유가 §4에 적혀 있다 |

**남는 한계:** 승인은 **«물어본 것 전체»에 대한 전부-또는-전무**다.
사용자가 *"a는 지우고 b는 두라"* 고 하려면 **말로 다시 명령해야** 한다
(그때는 `other_command` 경로가 받는다 — 이미 동작한다).
