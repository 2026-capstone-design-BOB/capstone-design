## 1. 배경 · 문제 정의

로드맵상 10월 항목은 **Plan-and-Execute + 개인화**이고, 선행조건(커스텀 LangGraph
그래프)은 M1-P1.5에서 이미 충족됐다. 그런데 탐색 중 확인한 사실이 이 작업의
**명분 자체를 바꿨다.**

### 1-1. 오늘 이미 4단계 복합 명령은 오류로 끝난다

`core/graph_agent.py:205`의 `recursion_limit: 10`은 이미 시스템을 **순차 도구 호출
3회**로 묶고 있다. 슈퍼스텝 산술:

| 슈퍼스텝 | 노드 |
|---|---|
| 1 | `input_guard` |
| 2 | `fast_path` |
| 3 | `agent` |
| 4 | `tools` |
| 5 | `agent` |
| 6 | `output_guard` |

**도구 1회에 6.** 이후 도구 1회마다 +2 (`tools` → `agent`). 즉 도구 3회 = 10 —
정확히 상한이다. **4단계 복합 명령은 `GraphRecursionError`를 낸다.**
그 예외는 `graph_agent.py:232`의 포괄 `except`에 잡혀 스레드를 지우고
(`_clear_thread`) *"명령 처리 중 오류가 발생했어요"* 로 끝난다.

> 이건 가정이 아니라 **이 기능이 대상으로 하는 바로 그 명령들의 현재 실패 방식**이다.
> `visual_verify`가 켜져 있으면 도구 1회마다 +3이라 상한은 더 빨리 온다.

### 1-2. 더 조용한 문제 — 몇 단계를 못 했는지 말할 수 없다

`"메모장 열고 크롬 닫아줘"` 에서 앞의 하나만 하고 성공했다고 답해도 **시스템이
그걸 알 방법이 없다.** 상태에 "무엇을 하기로 했는지"가 없기 때문이다.

이 프로젝트가 반복해서 데인 결함이 전부 같은 뿌리였다 — **확인하지 않고 됐다고
말하는 것.** BL-12(입력이 엉뚱한 창에 갔는데 성공 보고) · BL-15(뒷문장을 삼키고
성공 보고) · BL-19(도구를 부르지도 않고 "지켜볼게요"). **이건 그 계열의 마지막
판본이다.**

> **이 작업의 값어치는 "여러 단계를 실행한다"가 아니라 "몇 단계를 못 했는지 말할
> 수 있게 된다"에 있다.** 계획을 상태에 적는 유일한 이유가 그것이다.

## 3. 목표 구조

```
fast_path ─(decision=="to_plan")→ planner → agent ⇄ tools
          └(decision=="to_agent")→ agent          agent ─(계획 잔여)→ agent  ← 자기루프
```

### 3-1. 원칙

- **LLM 호출은 턴당 1회.** 계획을 세우고 **다시 세우지 않는다**(replan 없음).
  `visual_verify`가 *"판정도 재시도도 하지 않는다"*(`core/graph.py:847`)로 정한
  절제와 같다. replan은 실패 지점을 단계 수만큼 늘리는데, BL-19 조건에서 그
  확률은 곱해진다.
- **실행기를 새로 만들지 않는다.** 기존 `agent ⇄ tools` 루프가 한 단계씩 처리하고
  라우터가 되돌린다. **노드는 1개만 는다.**
- **단계 지시는 메시지가 아니라 SystemMessage 교체로 준다.** 절대규칙 6
  (HumanMessage를 넣으면 턴이 새로 시작된다)을 피하는 방법이 이미 코드에 있다 —
  `with_watch_directive`(`core/graph.py:556-567`). 같은 방식의
  `with_step_directive(msgs, plan, cursor)`를 만든다. **`state["messages"]`를 전혀
  건드리지 않고** 그 LLM 호출에만 붙는다. 따라서 `current_turn_messages()`의 턴
  경계가 계획 실행 내내 원래 발화 하나로 유지되고, Gemini의 "두 번째
  SystemMessage" 함정(`graph.py:559-561`)도 그대로 피한다.

### 3-2. 상태

`PluizState`에 두 필드. **리듀서 없음(기본 last-write-wins).**

```python
plan: list[str]      # 이번 턴에 실행하기로 한 단계들. [] = 계획 없음(=오늘과 동일)
plan_cursor: int     # 다음에 실행할 단계. cursor >= len(plan) 이면 완료
```

> ⚠️ `Annotated[..., operator.add]`를 붙이지 말 것 — 리듀서가 붙으면 planner의
> 쓰기가 '교체'가 아니라 '누적'이 되어 **지난 턴 계획이 이번 턴 뒤에 이어 붙는다.**
> `messages` 외의 필드는 기존 셋과 같이 마지막 쓰기가 이기는 게 맞다.

상수: `PLAN_MAX_STEPS = 2` (최소 출하본).

### 3-3. ⚠️ 이 설계에서 가장 헷갈리는 비대칭 — 반드시 지킬 것

**HITL 재개(`Command(resume=...)`)는 `input_guard`를 거치지 않는다.**

**(가) 그래서 계획이 승인 중단을 살아남는다 — 이게 의도다.**
`planner`가 쓴 `plan`/`plan_cursor`는 그 슈퍼스텝에서 이미 체크포인트에 커밋됐다.
2단계가 `delete_file`이라 `interrupt()`로 멈춰도 `"응"` 이후 끝까지 완주한다.

```
"메모장 열고 test.txt 삭제해줘"
 1 input_guard  plan=[] cursor=0 리셋
 2 fast_path    decision="to_plan"
 3 planner      plan=["메모장 열기","test.txt 삭제"] cursor=0   ← 여기가 결정적
 4 agent        step0 지시 → open_app
 5 tools        ToolMessage
 6 agent        도구 없음 → cursor=1
 7 agent        step1 지시 → delete_file
 8 hitl         interrupt() — 중단. plan·cursor=1이 체크포인트에 남는다
 ── 사용자 "응" → Command(resume) → hitl 노드부터 재실행 → approved → tools → …
```

**(나) 그래서 `other_command` 분기에서는 손으로 지워야 한다.**
`core/graph.py:938-942`는 의도적으로 `HumanMessage`를 넣어 새 턴을 시작하는데
`input_guard`를 안 탄다. 안 지우면:

> "메모장 열고 test.txt 삭제해줘" → 승인 질문 → 사용자가 `"네이버 열어줘"` →
> 삭제 취소 + 네이버 실행 — **그런데 `plan_cursor=1`이 살아 있어 새 명령을 처리할
> `agent`가 "지금은 2단계: test.txt 삭제" 지시를 받는다.**

**이건 이미 한 번 겪은 사고와 완전히 같은 모양이다** — 취소 플래그가 턴을 넘어
새어, 실제로 삭제해 놓고 *"삭제는 취소했어요"* 라고 답한 건
(`graph.py:930-932`, `tests/test_hitl_graph.py:153-165`).

| 분기 | 계획 처리 | 왜 |
|---|---|---|
| `approved` (:932) | 유지 | 같은 턴이 이어진다 |
| `not_found` (:911-913) | **유지** | 같은 턴이 계속되는 게 맞다 |
| `other_command` (:941-942) | **삭제** | 새 턴인데 `input_guard`를 안 탄다 (위) |
| `rejected` (:945-950) | 유지하되 **이어 실행하지 않는다** | `output_guard`로 가서 턴이 끝난다. 남은 단계는 정직 보고로 알린다 — 사용자가 "아니"라고 한 뒤에 계속 움직이면 안 된다 |

### 3-4. 정직한 실패

> **계획 수립 실패는 사용자에게 들리지 않는다. 계획 실행 실패는 반드시 들린다.**

**`planner`는 턴을 절대 죽이지 않는다.** 분해기 예외 / 산문만 반환 / 단계 0~1개 /
단계가 입력 원문과 동일 — 전부 `{"decision": "to_agent"}` 하나로 수렴해 **오늘과
완전히 동일한 단일 루프**로 진행한다. 로그(`get_logger("Plan")`)에만 남긴다.

*"계획을 세우지 못했어요"* 라고 말하지 않는 이유: 오늘도 이 명령들의 상당수는 단일
루프가 처리해 낸다. 실행은 성공하는데 실패를 예고하는 꼴이 되고, 사용자가 신경 쓸
필요 없는 내부 사정을 알리는 소음이다. `visual_verify`가 화면을 못 봤을 때 아무것도
붙이지 않는 것(`graph.py:866-869`)과 같은 절제다.

**계획을 세웠는데 다 못 했으면** `output_guard`가 상태만 읽어 후미 문구를 붙인다:

```
남은 것 = plan[plan_cursor:]     비어 있지 않으면 → " 다만 '크롬 닫기'는 못 했어요."
```

판정하지 않는다. 기존 `"삭제는 취소했어요. "` 접두(`:805·816·821`)와 **접두/접미로
자리를 나눠** 충돌을 피한다.

**출력은 JSON이 아니라 번호 목록으로 요청한다.** BL-19 조건에서 JSON 스키마 준수는
가장 먼저 무너지는 능력이다. `parse_plan`은 **판정이 아니라 추출**이므로 절대규칙
9(좌표를 지어내지 않는다)와 같은 계열의 절제이고, `classify_confirmation`
(`graph.py:146`)처럼 순수 함수로 빼서 직접 테스트한다.

### 3-5. 플래그 OFF = 그래프가 글자 그대로 예전과 같다

`plan_decompose`가 주입되지 않으면 **`planner` 노드도 엣지도 만들지 않는다.**
`visual_check`(`graph.py:1020-1029`)와 완전히 같은 패턴이다.
`recursion_limit`도 계획이 켜졌을 때만 `10 → 24`로 올린다.

`config/settings.py`에 `plan_enabled: bool = False` — **`vision_verify_enabled`(True)와
다르게 기본 꺼짐으로 간다.** 2026-09-04의 교훈("코드가 들어갔다"와 "동작한다"는
다르다) 그대로, 라이브 증거가 생기기 전엔 켜지 않는다.

## 4. 대안 비교

| | **(a) `fast_path`→`planner`→`agent`** | (b) `agent` 안에서 프롬프트로 | (c) plan-execute-**replan** 서브루프 |
|---|---|---|---|
| 추가 LLM 호출 | **1회/복합턴** | 0 | 1 + 단계마다 1 |
| 3단계 지연 추가 | ~3초 | 0 | ~12초+ → `agent_timeout=45` 초과 위험 |
| 동기/HITL (절대규칙 1) | ✅ 노드 하나, 전부 sync | ✅ | ⚠️ replan이 `interrupt` 이후 재실행되며 계획이 흔들림 |
| 턴 경계 (절대규칙 6) | ✅ 메시지를 넣지 않음 | ✅ | ⚠️ replan 결과를 messages에 넣고 싶은 유혹이 큼 |
| `recursion_limit` | 2단계 ≈ 10~14 | 오늘과 동일(=3콜에서 터짐) | 3단계 ≈ 20+ |
| 구조화 출력 실패(BL-19) | **계획 없음 → 오늘 경로 그대로** | 해당 없음 | 매 단계 replan이 실패 가능 = 실패 지점이 N배 |
| **무엇이 남는가** | **상태에 남은 단계가 있어 "2/3 했어요"를 말할 수 있다** | **아무 기록도 없음 — 부분 실패를 말할 수 없다** | 남지만 대가가 크다 |

## 5. 결정

**(a) — `fast_path`와 `agent` 사이에 `planner` 노드. replan은 없다.**

**(b)를 버린 이유가 이 결정의 핵심이다.** (b)는 이미 부분적으로 동작한다 — Gemini는
순차 도구 호출을 할 줄 안다. (b)가 못 하는 것은 **정직한 부분 실패 보고**뿐이고,
그게 §1-2에서 본 이 작업의 존재 이유다.

### 5-1. 의도적으로 손대지 않는 것들 (= 약해지기로 정한 것)

**조용히 약해지면 그게 BL-19과 같은 결함이 된다.** 그래서 여기 적고
[ARCHITECTURE.md](../ARCHITECTURE.md)에도 한계로 명시한다.

| 대상 | 영향 | 결정 |
|---|---|---|
| `_is_learnable` (`command_cache.py:582`) | 계획 턴은 도구 2개+ → `len(tool_calls) != 1` → **학습 안 됨** | **의도적.** 복합 표현을 캐시 패턴 하나로 학습하는 건 BL-15 재발이다. 나중에 "고치지" 말 것 |
| `visual_verified` (`graph.py:265`, `:983`) | 턴당 1회 → 2단계 모두 `type_text`면 두 번째는 화면 검증을 못 받는다 | **그대로.** 단계마다 리셋하면 Vision 8초×N이 `agent_timeout=45`를 넘긴다 |
| `detect_watch_lie` (`graph.py:570-619`) | 조건 ① "이번 턴 도구 0개"가 계획 턴에서 깨져 **감시 거짓말 그물이 무력화** | **감시 요청 턴은 아예 계획하지 않는다** (`_is_watch_request` 게이트). 그물을 약하게 만드는 대신 **기능을 포기한다** |
| `verify_output` (`graph.py:411-456`) | 턴 전체 범위 → 1단계 도구 오류 + 2단계 성공 응답이면 오류로 덮어씀 | **그대로.** "실패를 성공으로 말하지 않는다"가 우선이다 |
| `agent_timeout` (`settings.py:37`) | 계획 턴 최악 ≈ 35~40초. 45 안이지만 여유가 없다 | **올리지 않는다.** 라이브 실측 후 판단 |

### 5-2. 병렬 실행(로드맵 2번째 항목)은 미룬다

1. **상당 부분이 이미 공짜로 있는데 측정된 적이 없다.** Gemini는 한 AIMessage에
   tool_calls를 여러 개 담을 수 있고 `ToolNode`는 그것들을 **한 슈퍼스텝 안에서**
   실행한다. 새 기계를 만들기 전에 그게 실제로 일어나는지부터 재야 한다.
2. **먼저 고쳐야 할 결함이 있다** → [BACKLOG BL-20](../BACKLOG.md). 혼합 배치에서
   위험 도구 하나가 거부되면 안전한 호출까지 조용히 취소된다. 병렬을 정식 기능으로
   만들면 이게 상시 경로가 된다.
3. **절대규칙 1과 정면 충돌한다.** LangGraph `Send` 팬아웃 안에서의 `interrupt()`는
   sync 경로에서도 동작이 미묘하다. HITL은 이 프로젝트가 가장 비싸게 얻은 자산이다.
4. **이득이 작고 위험이 크다.** 한 대의 데스크톱을 만지는 OS 제어다. `open_app`을
   둘 동시에 하면 포커스 경쟁이 나고, 그게 정확히 BL-12 계열이다. 아낄 수 있는 건
   1초 미만이다.
5. **음성 명령은 대체로 본질적으로 순차다.** *"메모장 열고 거기에 써줘"* 는
   병렬화 자체가 불가능하다.

> **재검토 조건**: 순차 계획이 라이브에서 증거를 남긴 뒤, **읽기 전용 도구**
> (`get_running_apps`·`get_battery_status`·`get_current_time`)에 한해.

### 6-3. 구현하며 정한 것 (2026-09-05)

**`PLAN_MAX_STEPS`를 넘는 응답은 잘라 쓰지 않고 통째로 버린다.** 3단계를 2로 자르면
3번째 단계를 **모르는 채로** 턴이 끝나 "못 했다"고 말할 수도 없다 — §1-2에서 정한 이
기능의 존재 이유와 정반대다. 버리면 착지점이 §3-4대로 **오늘의 정상 경로**이고,
계획이 켜져 있으면 `recursion_limit`도 이미 24라 3단계 명령은 오늘보다 오히려 유리하다.

**게이트에서 부정어를 뺐다.** `is_compound_command`는 부정어(BL-02)와 다중 앱까지
포함하는데, `"크롬 말고 메모장 열어줘"` 는 복합처럼 보이지만 실행할 단계가 둘이 아니다.
`_is_plannable = is_compound_command and not has_negation and not _is_watch_request`.

**단계 완료 판정은 "도구를 안 불렀다"이다.** `agent`가 그 패스에서 tool_calls를 내지
않으면 커서를 전진시킨다. 커서가 **반드시** 전진하므로 자기루프는 최대 `len(plan)`회에서
끝난다(전진 없이 되돌리면 HITL 무한루프 사고와 같은 계열이 된다). 대가는 LLM이 그 단계에서
아무것도 안 하고 잡담만 해도 완료로 센다는 것이고, 그건 `[Plan] n/m 단계 완료` 로그로 남긴다.

## 7. 위험

1. **지연** — 오늘 단일 루프가 한 방에 처리하던 복합 명령에도 planner 왕복 ~3초가
   얹힌다. 음성 UX에서 3초는 크다. → 게이트를 좁게 두고 실측 후 판단. 넘치면
   planner를 "첫 agent 패스가 실패한 뒤"로 옮기는 대안이 남아 있다.
2. **반쯤 바뀐 세상** — 지금까지 어떤 노드도 한 턴에 되돌릴 수 없는 변경을 여러 번
   하지 않았다. 2단계에서 타임아웃 나면 `_clear_thread`(`graph_agent.py:230`)가
   기록까지 지운다. → `PLAN_MAX_STEPS=2` · 단계별 `[Plan]` 로그 · 정직 보고.
3. **BL-19 그 자체** — 이 기능은 "모델이 구조화된 목록을 낸다"에 의존하는데, 그게
   시간대에 따라 흔들리는 바로 그 능력이다. → 실패의 착지점이 **오류 메시지가
   아니라 오늘의 정상 경로**여야 한다. 계획이 안 돌면 사용자는 "계획"이라는 말을
   들을 일이 없다.
4. **HITL 경계 상태 누수** (§3-3) — 이미 한 번 똑같은 모양으로 사고가 났던 자리다.
   → 전용 회귀 테스트 [6].
5. **`recursion_limit` 상향의 부작용** — 24로 올리면 계획과 무관한 폭주 ReAct 루프도
   2.4배 오래 돈다. → **플래그가 켜졌을 때만** 올린다.
6. **게이트 정규식이 좁다** — `_COMPOUND_CMD`(`fast_path.py:33`)에 `지우고`·`찾아서`·
   `이후에`가 없다. 놓치면 = 오늘 동작(안전), 오탐하면 = 3초 낭비 후 정상 진행(안전).
   **양방향 오류가 전부 안전한 쪽**이라는 게 이 게이트의 장점이다.
7. **테스트 연극** — mock 92개가 초록인데 기능이 한 번도 켜진 적 없던 일(BL-19)이
   재발할 수 있다. → **기본값 OFF**, 라이브 증거 전까지 ON으로 바꾸지 않는다.

## 8. 후속 (범위 밖, 기록만)

**단계별 캐시 실행** — `plan`의 각 단계를 `fast_resolve(step)`에 먼저 통과시킨다.
`"메모장 열고 크롬 닫아줘"`처럼 두 단계가 모두 캐시 히트면 **LLM 호출 0회, ~0.2초.**

이게 이 기능이 진짜로 값어치를 하게 되는 지점이다. 오프라인 우선
([ROADMAP § 최종 시스템 목표](../ROADMAP.md)의 *"상용 시스템 대비 핵심 차별점"*)이
복합 명령까지 확장되는 **유일한 경로**이고, `has_uncovered_command`
(`command_cache.py:329`)가 만든 "부분만 이해함" 판정이 **단계 단위에서는 더 이상
문제가 아니게 되므로**(단계 하나는 정의상 단일 명령이다) **BL-15의 근본 해소**이기도
하다. 별도 ADR 가치가 있다.
